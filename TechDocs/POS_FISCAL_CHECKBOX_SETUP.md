# Первое включение фіскалізації (Checkbox) для магазина

Пошаговая инструкция для оператора/владельца. Пишется, потому что **ни один
магазин ещё не включал фискализацию в проде** — весь прогон (фазы 0–2б) шёл
на тестовом (`test`-ключ) аккаунте Checkbox и локальной/тестовой БД.
Контекст и архитектура — [POS_FISCAL_PRRO.md](POS_FISCAL_PRRO.md).

## 0. Проверить один раз перед первым магазином

Эти два пункта — инфраструктурные, разовые, не привязаны к конкретному
магазину.

### 0.1 `POS_SECRETS_KEY` задан в проде

Без него `PATCH /api/pos/fiscal/settings` отвечает 503, и включить
фискализацию невозможно (сообщение в UI прямо об этом говорит: «Сервер не
налаштовано для зберігання ключів ПРРО»). `RAILWAY_POS.md` этот ключ не
упоминает — это не забытая опечатка, просто фискализация появилась позже
той инструкции.

Проверить на Railway (сервис API → Variables), задан ли `POS_SECRETS_KEY`.
Если нет — сгенерировать и добавить (то же самое, что делает
`generateSecretsKey()` в `src/pos/core/secrets.ts`, только без сборки):
```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```
(32 байта в base64). **Записать этот ключ куда-то помимо Railway** — если он
потеряется, все уже сохранённые креды провайдеров в БД станут нечитаемыми
(AES-256-GCM, расшифровать без ключа нельзя).

### 0.2 Бэкенд задеплоен с миграцией 024

`024_pos_fiscal.sql` уже зарегистрирована в `src/pos/migrations.ts` и
накатывается автоматически при старте контейнера (`node dist/pos/migrate.js`
перед `node dist/index.js`, как и все остальные миграции) — отдельно
руками ничего гонять не нужно, если деплой идёт из актуального `main`.
Проверить постфактум:
```bash
psql "$DATABASE_URL" -c "select column_name from information_schema.columns where table_name='pos_fiscal_settings' limit 1;"
```
Пустой результат — миграция не применилась, деплой старый.

## 1. Получить настоящий (не sandbox) аккаунт Checkbox

То, чем проверялась фаза 2б — тестовый аккаунт с `license key`, начинающимся
на `test...`. Для реального магазина нужен **настоящий** договор с Checkbox
(my.checkbox.ua), настоящая касса (РРО) и касир — не тестовые.

С кабинета магазина понадобятся ровно два значения (форма в приложении
просит именно их):
- **Ліцензійний ключ** — со страницы кассы (Каси → обрана каса).
- **PIN-код касира** — со страницы сотрудника (Співробітники → обраний касир).

Дополнительно стоит уточнить у владельца магазина **код ставки ПДВ**
(«Код ставки за замовчуванням» в настройках) — числовой код (не буква:
placeholder в форме «напр. A» вводит в заблуждение, у Checkbox коды
числовые, напр. `8` для «Без ПДВ», `1`/`2` и т.п. для ставок НДС). Узнать
точный код можно через кабінет Checkbox (Налаштування → Ставки податку) или
попросив владельца прислать скрін.

## 2. Выпустить бандл `fiscal-checkbox` (если ещё не выпущен под текущую версию)

Проверить, есть ли уже релиз под текущую версию `pos/package.json`:
```bash
git tag -l "module-fiscal-checkbox-v*"
```
Если нужного тега нет — выпустить:
```bash
gh workflow run module-release.yml -f module=fiscal-checkbox
```
(или вручную: GitHub → Actions → «Module Release» → Run workflow → поле
`module` = `fiscal-checkbox`). Воркфлоу сам берёт версию из
`pos/package.json`, собирает, подписывает **прод-ключом**
(`PROD_KEY_ID` сверяется автоматически — джоб упадёт, если случайно
подписалось dev-ключом) и публикует на `module-builds`.

Проверить результат (~1–2 минуты):
```bash
gh run list --workflow=module-release.yml --limit 3
```
URL бандла после успеха:
```
https://cdn.jsdelivr.net/gh/merenkoff/tiktok-live@module-fiscal-checkbox-v<версия>/fiscal-checkbox/remote-entry.js
```
(версию подставить из `pos/package.json`, на момент написания — `1.1.0`).

**Этот шаг ничего не меняет ни для одного магазина** — просто кладёт файл
на CDN. Подключение — шаги 3–4.

## 3. Владелец: настроить провайдера в кабинете

Владелец (или админ от его имени) заходит в POS-кабинет магазина
(`/admin`) → Налаштування → секция «Фіскалізація (ПРРО)»:

1. **Провайдер** → выбрать «Checkbox».
2. Сохранить — после сохранения провайдера появится ссылка/секция для ввода
   кредов (карточка `fiscal-checkbox`, `/admin/fiscal` — уже видна в меню
   администратора, если модуль подключён, см. шаг 4; если нет — сохранить
   провайдера всё равно можно, креды впишутся позже).
3. На экране «Фіскалізація (Checkbox)» (`/admin/fiscal`) ввести:
   - **Ліцензійний ключ**
   - **PIN-код касира**
   
   и нажать «Зберегти дані доступу».
4. Нажать **«Перевірити з'єднання»**. Ожидаемый результат — «З'єднання
   успішне», имя касира из кабинета Checkbox. Если ошибка — см. раздел
   «Диагностика» ниже, **не продолжать** дальше, пока не увидите успех.
5. Вернуться в Налаштування → «Фіскалізація (ПРРО)»:
   - вписать **«Код ставки за замовчуванням»** (числовой код из п. 1);
   - включить **«Реєструвати чеки в ПРРО»** (чекбокс станет активным только
     если креди сохранены и связь проверена — до этого он задизейблен);
   - «Відкривати зміну автоматично» — включить, если хотите, чтобы первая
     продажа дня сама открывала зміну (рекомендуется, иначе кассир должен
     будет зайти на `/fiscal` и открыть зміну вручную перед первой
     продажей);
   - **«Джерело чека»** — что печатает касса: «Наш макет + фіскальний блок»
     (номер, дата, QR налоговой поверх привычного чека) или «Чек від
     провайдера, як є» (текст Checkbox один-в-один, как в его кабинете).
     Второй вариант — если магазину важно, чтобы бумажный чек совпадал с
     чеком в кабинете Checkbox; при сбое получения текста касса сама
     напечатает наш макет с фискальным блоком;
   - **«Ширина чекової стрічки»** — 58 мм или 80 мм, под какой рулон
     провайдер верстает свой текст. Это настройка магазина; принтер и рулон
     самой кассы по-прежнему выбираются на экране «Обладнання».
6. Нажать **«Зберегти ПРРО»**.

## 4. Подключить сам модуль `fiscal-checkbox`

Без этого шага экран `/admin/fiscal` из п. 3.3 недоступен, а после включения
тумблера в п. 3.5 продажи начнут падать (тумблер включён, но UI для смены/
чеков — `/fiscal` — не загружен). **Порядок важен: обычно проще сделать
шаг 4 раньше шага 3**, чтобы сразу видеть экран `/admin/fiscal`, но
технически шаг 3 без шага 4 тоже отработает молча (креды сохранятся через
API, просто без UI).

Налаштування → «Онлайн-модулі» → «+ Додати модуль»:
- **Ідентифікатор**: `fiscal-checkbox`
- **Джерело (URL remote-entry.js)**: ссылка из шага 2
- нажать «+ Додати модуль» **ещё раз**, чтобы подтвердить черновик (форма
  двухступенчатая — первый клик открывает поля, второй фиксирует запись в
  список; если пропустить второй клик, запись не попадёт в список и
  сохранение внизу её не отправит — известная ловушка, см.
  `POS_FISCAL_PRRO.md`, находки фазы 6);
- убедиться, что запись появилась в списке модулей на странице;
- нажать общую кнопку **«Зберегти»** формы настроек.

Кассиру нужно перезайти (следующий вход), чтобы модуль подгрузился —
это указано прямо в подсказке над секцией.

## 5. Проверка перед реальными продажами

1. Зайти под кассиром (или владельцем) → «Каса» → должна появиться пункт
   меню **«Зміна» / «Фіскалізація»** (иконка Receipt).
2. `/fiscal` → «Відкрити зміну» (если не включён автооткрытие) → убедиться,
   что смена открылась (в кабинете Checkbox тоже должна отобразиться
   открытая смена на реальной кассе).
3. Пробить одну тестовую продажу на минимальную сумму через обычную кассу.
   В ответе продажи должно быть `fiscal.status: 'done'` и настоящий
   `fiscal_code` — то же самое видно в «Чеках» у этой продажи (бейдж
   фіскалізації).
4. Свериться в кабинете Checkbox (`my.checkbox.ua`), что чек реально
   появился.
5. Если тест ок — можно возвращать смену в обычный режим работы (закрывать
   вручную вечером, или доверить крону — свою смену крон закроет сам не
   позже чем через 23.5 часа после открытия).

## 6. Офлайн-режим: прогон на тестовой кассе (фаза 8б, шаг 0)

Офлайн-режим (`offline_mode` в настройках ПРРО, [POS_FISCAL_OFFLINE.md](POS_FISCAL_OFFLINE.md))
пока **не** включать в проде — продажи офлайн и реплей ещё не реализованы
(фазы 2–3). Что уже можно и нужно сделать — прогнать офлайн-API Checkbox на
**тестовой** кассе и закоммитить ответы как фикстуры:

```bash
CHECKBOX_SANDBOX_LICENSE_KEY=test… CHECKBOX_SANDBOX_PIN=… npm run fiscal:sandbox:offline -- --ask --go
```

- без флагов — только чтение: касир, `cash-registers/info`, счётчик и первые
  пять неиспользованных кодов;
- `--ask` — плюс `ask-offline-codes?count=20&sync=true` (запрос к ДПС; коды не
  тратятся, пока не использованы);
- `--go` — полный цикл: `go-offline` одним кодом → `sell-offline` одной позиции
  следующим кодом (без `control_number` в запросе) → `go-online` → опрос
  `info.offline_mode` до 3 минут → перечитать чек. Нужна **открытая смена**;
  скрипт отказывается работать с ключом, который не начинается с `test`.

Скрипт печатает главное — есть ли в ответе `sell-offline` поля `control_number`
и `tax_url` — и пишет каждый ответ в `src/__tests__/fixtures/checkbox/offline_*.json`.

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| «Сервер не налаштовано для зберігання ключів ПРРО» | `POS_SECRETS_KEY` не задан в проде | См. п. 0.1 |
| «Для провайдера «Checkbox» у цій версії застосунку немає модуля» | Деплой бэкенда старше PR фазы 2б (`providers/checkbox` не зарегистрирован) | Обновить деплой backend-сервиса на Railway |
| «Перевірити з'єднання» → «ПРРО не налаштовано» / 409 | Креды не сохранены (пустые поля) | Вернуться к п. 3.3 |
| «Перевірити з'єднання» → ошибка авторизації | Неверный license key или PIN, либо это тестовые (sandbox) креды на проде | Перепроверить в кабинете Checkbox — Каси/Співробітники |
| Тумблер «Реєструвати чеки в ПРРО» задизейблен | Ещё не сохранены креды, или не выбран провайдер | Сначала п. 3.3–3.4, потом п. 3.5 |
| Пункт меню «Фіскалізація» не появился после логина | Модуль не подключён (шаг 4) или требуется перезайти | Проверить список «Онлайн-модулі», перелогиниться |
| Продажа падает 503 `fiscal_unavailable` | Смена не открылась (сеть/креды) или автооткрытие выключено | `/fiscal` → открыть смену вручную, посмотреть support_code в ответе |
| Продажа проходит, но `fiscal.status` не `done` | См. `support_code` в ответе (`FS-...`) — расшифровка кодов в `src/pos/fiscal/errors.ts` | По `support_code` можно понять причину без логов сервера |

## На заметку про версии модуля

URL релиза в `pos_stores.module_remotes` — **конкретная версия**, не
«последняя». Если позже выйдет новая версия `fiscal-checkbox` (баг-фикс,
фича), её нужно будет **заново выпустить** (шаг 2) и **заново вписать новый
URL** в каждый магазин, который его использует (шаг 4) — это не подхватится
само. Для этого есть **супер-админка `/super`** ([POS_SUPER_ADMIN.md](POS_SUPER_ADMIN.md),
пароль `POS_SUPER_PASSWORD`): панель «Перенацілити модуль» подставляет новый
URL во все выбранные магазины разом, с проверкой подписи манифеста.
