## 1. Чи є демо- або тестовий ПРРО для інтеграторів? Чи тестувати можна лише на власному зареєстрованому ПРРО з CHECKHEAD.TESTING = true?

Демо чи тестової каси для інтеграції окремо не надається. Можете використовувати TESTING = true.

## 2. Як відкрити тестову зміну через WEB API? У команди OpenShift немає ознаки TESTING. Чи правильно, що тестова зміна відкривається лише першим RegisterCheck з AutoOpenShift = true і TESTING = true?

Тестову зміну можна відкрити, передавши "TESTING = true" в тілі запиту.

```json
{
    "Command": "OpenShift",
    "NumFiscal": "****",
    "KeyPin": "****",
    "KeyGuid": "****",
    "TESTING": true
}
```

## 3. Чи приймають KeyGuid і KeyPin усі команди, зокрема RegisterCheck, OpenShift, CloseShift і GetCheck? Чи достатньо передати їх разом із NumFiscal?

Для "GetCheck" не обов'язково передавати параметри KeyGuid і KeyPin. Достатньо "RegistrarNumFiscal": "ФН Каси" та "NumFiscal": "ФН чека". Для інших вказаних команд достатньо буде KeyGuid і KeyPin.

## 4. Чи є обмеження доступу до WEB API за IP-адресами або вимога клієнтського TLS-сертифіката?

Додаткових обмежень за IP-адресами або вимог щодо клієнтського TLS-сертифіката не передбачено. Проте доступ може бути обмежений для IP-адрес із країн, щодо яких діють відповідні обмеження.

## 5. Які формати ключів КЕП підтримуються, якщо працювати без KeyGuid: .dat, .pfx, .jks, Smart ID?

Усі вищезазначені формати ключів підтримуються.

## 6. Чи є повний перелік ErrorCode? Це рядок-назва (наприклад, InconsistentRegistrarState) чи число? Які коди Cashalot додає понад перелік ДПС?

Окремого повного переліку немає. Доступні коди помилок наведені в специфікації Cashalot та специфікації ФСКО.

Додатково декілька прикладів. "ErrorCode": "DocumentValidationError" - стосується неприйнятного формату поданого документу. Далі в "ErrorMessage" буде опис помилки. До прикладу, якщо відкрити зміну тестово та пробувати надалі фіскальний чек без тестової ознаки провести:

```json
"ErrorCode": "DocumentValidationError",
"ErrorMessage": "Значення ознаки тестового нефіскального документа (TESTING: False) не дорівнює значенню ознаки зміни, що містить тестові документи (True), для поточної зміни"
```

Інший приклад, якщо зміна була не закрита та відбувається спроба відкритя нової:

```json
"ErrorCode": "ShiftAlreadyOpened",
"ErrorMessage": "Зміну на ПРРО наразі відкрито"
```

Або ж навпаки спроба закриття зміни, яка вже була закрита:

```json
"ErrorCode": "ZRepAlreadyRegistered",
"ErrorMessage": "Для поточної зміни наразі зареєстрований Z-звіт"
```

Помилка UndefinedRegistrarState у випадку, якщо не вдається знайти касу чи визначити її стан.

```json
"ErrorCode": "UndefinedRegistrarState",
"ErrorMessage": "Локальний стан ПРРО не визначений. Необхідно отримати стан ПРРО командою 'TransactionsRegistrarState'"
```

Під час інтеграції, якщо помилка буде незрозуміла по опису, можете звернутись за уточненням (одразу прохання надавати тіло запита та відповідь, за винятком чутливих даних).

## 7. Які ліміти запитів (на ПРРО або на обліковий запис) і рекомендовані тайм-аути? Скільки зазвичай триває RegisterCheck?

Окремих лімітів на поточний момент не передбачено. Час реєстрації чека зазвичай становить близько 400-800 мс, однак може відрізнятися залежно від навантаження та зовнішніх сервісів.

## 8. Що відповідає RegisterCheck, якщо повторно надіслати той самий чек з тим самим CHECKHEAD.UID, наприклад після тайм-ауту, коли відповідь не дійшла: той самий NumFiscal, помилку (яку саме) чи буде зареєстровано другий чек?

Якщо надіслати той самий UID, то буде 400 Bad Request

```text
Код помилки: 13 DuplicatedRequestUid
Повторно надісланий запит із зазначеним UID
```

Додатково звертаємо увагу, що UID необхідно передавати в корені JSON, на одному рівні з параметрами Command, KeyPin, KeyGuid, NumFiscal та Check, а не в CHECKHEAD.

```json
{
    "Command": "RegisterCheck",
    "UID": "6d69bd4d-8cb8-4838-81d9-1265998ff2e4",
    "KeyPin": "****",
    "KeyGuid": "****",
    "NumFiscal": "****",
    "Check": {
        "CHECKHEAD": {
            "DOCTYPE": "SaleGoods"
        }
    }
}
```

## 9. Звідки брати ставки й літери податків для CHECKTAX і LETTERS? Чи перевіряє їх Cashalot або ФСКО за даними кабінету? Літери писати кирилицею (А, Б) чи латиницею?

Літери писати тільки кирилицею. Рекомендовано використовувати ті ж самі NAME і LETTERS в CHECKTAX для каси, які використовувались раніше, якщо каса вже працювала. Якщо ні, то рекомендуємо взяти приклади з Кабінету користувача.

Додаткових перевірок з боку Cashalot або ФСКО по літерам не ведеться, тому це має опрацьовуватись на стороні системи.

ФСКО поверне помилку реєстрації документа у випадку, якщо виявить розбіжності між податковими сумами в CHECKTAX та даними товарних позицій.

Не рекомендується змінювати літеру податкової ставки у відкритій зміні, а також використовувати однакову літеру для різних податків в межах однієї зміни.

## 10. Чи обов'язкові UNITCD і UNITNM у рядку чека? Які коди одиниць ставити для г, кг і мл? Для шт ми бачили 2009, для л — 138.

Параметри UNITCD і UNITNM не є обов'язковими, однак рекомендовано їх передавати. Якщо вони передаються, необхідно вказувати одночасно і код, і назву одиниці виміру.

Коди можна переглянути і в Кабінеті користувача в картці товару у відповідному довіднику для одиниць вимірювання: г - 0303, кг - 0301, мл - 0144. А також у відповідному нормативному акті Класифікатор системи позначень одиниць вимірювання та обліку ДК 011-96

## 11. Який PAYFORMCD і PAYFORMNM ставити для безготівкової оплати переказом за QR-кодом (IBAN), а не карткою?

У структурі чека (xsd) немає обмежень за кодами:

```xml
<!-- Код форми оплати (числовий): 0–Готівка, 1–Банківська картка, 2-Попередня оплата, 3-Кредит, ..., 100000-Безготівковий платіжний інструмент, ... -->
```

Для безготівкових оплат, що не є оплатою карткою, можемо рекомендувати такий варіант, який використовується в Cashalot:
`<PAYFORMCD>306</PAYFORMCD>` та відповідний `<PAYFORMNM>` (у вашому прикладі це `<PAYFORMNM>Переказ за QR-кодом (IBAN)</PAYFORMNM>`).

## 12. Якої ширини в символах текстова візуалізація (Visualization без VisAs…)? Чи можна отримати її під стрічку 58 мм (32 символи) і 80 мм (48 символів)?

Ширина передається у піксельному розмірі, не в символьному. За замовчуванням ширина 440px.

## 13. Який формат NumFiscal у документа, зареєстрованого в офлайн-режимі (Offline = true)? Чи повертаються для нього Url і QrCode одразу, чи лише після надсилання на ФСКО?

Фіскальний номер документа, що виданий офлайн, має таку структуру:
`<Номер офлайн сесії>.<Локальний номер документа в офлайн сесії>.<Контрольне число>`. Локальний номер документа в офлайн сесії починається з 1 і збільшується послідовно.

Приклад фіскального номера офлайн-документа: “82563.25.6127”.

Так, Url і QrCode одразу надаються.

Не рекомендується виконувати операції по одній і тій самій касі одночасно з різних пристроїв, оскільки це може призвести до порушення послідовності локальної нумерації документів та унеможливити подальшу реєстрацію офлайн-сесії.

## 14. Чи може облікова система сама подати документ, створений офлайн на своєму боці (CHECKHEAD.OFFLINE = true, ORDERTAXNUM), коли в каси немає інтернету взагалі? Чи офлайн можливий лише всередині сервера Cashalot, коли недоступний ФСКО?

При використанні WebAPI робота в офлайн-режимі можлива за умови доступності сервера Cashalot.

Якщо службу FS API розгорнути на власному сервері або робочому комп'ютері як локальний сервер, звернення до сервера Cashalot для цієї взаємодії не знадобиться. Відповідно, робота не залежатиме від доступності сервера Cashalot.

## 15–16. Відповідь розробки (дослівно)

> Доброго вечора!
> На поточний момент фіксуємо відсутність зв'язку з сервером ФСКО ДПС, перехід в офлайн режим відбувається по всіх касах, для яких було дозволено роботу в офлайн-режимі формою 1-ПРРО при реєстрації каси.
> Якщо ваша каса підтримує роботу в офлайн-режимі, ви можете продовжувати здійснювати розрахункові операції до відновлення зв’язку із сервером ДПС. Якщо фіскальний сервер став доступним в режимі онлайн завершення режиму роботи офлайн і повернення до режиму роботи онлайн здійснюється для кожного ПРРО окремо, під час обробки команд "Запит стану ПРРО", "Реєстрація фіскального чека" тощо.

Що з цього випливає (наш висновок, не їхні слова):

- `Available: false` 27.10 — **реальний збій ФСКО на боці ДПС**, не стан нашої сесії. Отже й наші тайм-аути на `fs.tax.gov.ua` того ж дня **не доводять** allowlist: сервер міг просто лежати. Питання 15 (чи впустить ФСКО довільну адресу) лишається відкритим — повторити пробу, коли ФСКО повернеться (`Available: true`).
- Поки ФСКО недоступний, документ реєструється в офлайн-сесії Cashalot — але лише для ПРРО, якому **форма 1-ПРРО дозволила офлайн**. Без цього дозволу реєстрація під час збою ДПС неможлива. Це пункт для ранбука (розділ 1) і для CA0.
- Повернення в онлайн — на першій команді після відновлення (`TransactionsRegistrarState`, `RegisterCheck`), окремо для кожного ПРРО; нічого спеціального робити не треба, `ServerState` перед зміною перевіряти не обов'язково.
