# Checkbox API — Чеки передплати та післяплати (`prepayment-receipts`)

Джерело: https://wiki.checkbox.ua/uk/api/pre-payment, знято 2026-10-25.
Сторінку створено 04.06.2024, востаннє оновлено 16.09.2026 (поля
`created-at` / `updated-at` сторінки). Wiki.js віддає вміст сторінки в
серверному HTML, тому текст знято звичайним `curl`, без браузера. Схеми
взято з `openapi-2.106.4.json`, коди помилок — з таблиці на
https://wiki.checkbox.ua/uk/api.

Навіщо: це крок 2 часткового погашення боргу «під запис»
([G3_DEBTS.md](../../../grocery/G3_DEBTS.md) §11). У магазині з ПРРО внесок
можна прийняти лише як фіскальний документ.

## Методи

| Метод | Що робить | Відповідь |
|---|---|---|
| `POST /api/v1/prepayment-receipts` | Створює чек передплати й разом із ним ланцюжок | `ReceiptModel` (201) |
| `POST /api/v1/prepayment-receipts/{relation_id}` | За OpenAPI: «Створення додаткових чеків передплати та чека післяплати». Вікі описує лише чек післяплати | `ReceiptModel` (201) |
| `GET /api/v1/prepayment-receipts/{relation_id}` | Стан ланцюжка | `PrePaymentReceiptInfo` |
| `GET /api/v1/prepayment-receipts/search` | Список ланцюжків, див. нижче | сторінка `BasePrePaymentReceiptInfo` |
| `POST /api/v1/prepayment-receipts/{relation_id}/return` | Повертає **весь** ланцюжок | масив `ReceiptModel` |

Параметри `search`: `from_date`, `to_date`, `desc`, `search` («Пошук по
номеру замовлення»), `cash_register_id`, `status`, `limit`, `offset`.

Заголовки в усіх методах ті самі, що в звичайних чеках:
- `X-Client-Name` і `X-Client-Version` (обов'язкові);
- `Authorization`;
- `X-Device-ID` (необов'язковий, «для блокування дублікатів»).

## Створення чека передплати

Дослівно з вікі:

> Метод для створення чека передплати. Створення чека передплати дозволено
> тільки у відкритій касовій зміні. У відповідь буде повернуто масив даних
> чека передплати із "pre_payment_relation_id" — унікальним ідентифікатором
> чеків (номером замовлення) передплати і післяплати в системі checkbox.
> Вказування кастомного "pre_payment_relation_id" — не передбачене. Сума
> платежів чека не може дорівнювати сумі всіх товарів.

### Тіло запиту (`PrePaymentReceiptPayload`)

Тіло — це звичайний продаж:
- `id` — UUID чека, обов'язковий;
- `cashier_name`, `departament`;
- **`goods`** (обов'язкові) — та сама `GoodItemPayload`, що в `/receipts/sell`:
  - `good{code, name, price, tax[], barcode, excise_barcodes, uktzed}`;
  - `quantity` у тисячних;
  - `discounts[]` на рядку;
- `delivery`, `discounts[]` на чек, `bonuses[]`;
- `payments[]` (`CASH` / `CASHLESS`) — сума, внесена зараз;
- `rounding` (застаріле), `rounding_mode` (`ROUND_10` / `ROUND_50`);
- `header`, `footer`, `barcode`, `order_id`, `related_receipt_id`;
- `previous_receipt_id`, `callback_url`, `ettn`;
- `custom_relation_id` — рядок 10..256 символів.
  - Повтор Checkbox відхиляє з кодом `prepayment.relation_id_not_unique`.
  - Чи стає це значення номером ланцюжка, вікі не каже («кастомний
    `pre_payment_relation_id` не передбачений»). Відповість пісочниця.

### Відповідь (приклад з вікі, скорочено)

Товар продано за 195,00, знижка на чек 50,00, разом 145,00. Покупець вніс
100,00 карткою.

- Позиція в чеку **одна**: «Передплата за замовленням #1717502471» на 100,00
  (`quantity` 1000, `sum` 10000).
  - `taxes: []` і на позиції, і в чеку.
  - `total_sum` = 10000, `type: "SELL"`.
- Самі товари є лише у футері, який складає Checkbox (наш футер іде в кінці):

  ```
  Замовлення: 1717502471
  1.Вино ігристе біле … 0,125
  - ціна: 195.00 грн
  - кількість: 1.000 од
  Знижка на чек: -50.00 грн
  Залишилось сплатити: 45.00 грн
  Всього: 145.00 грн
  Якийсь футер
  ```
- `"pre_payment_relation_id": "1717502471"` — номер ланцюжка. Його видає
  Checkbox.
- Як і будь-який чек, відповідь приходить зі `status: "CREATED"`, а
  `fiscal_code` і `tax_url` з'являються після `DONE`.

## Чек післяплати

Дослівно з вікі:

> Метод для створення чека післяплати. Обов'язковим для створення чека
> післяплати є передача в заголовках унікального ідентифікатору замовлення в
> системі checkbox — "pre_payment_relation_id". Без цього параметру чек
> післяплати не може бути створено.

Вікі перелічує `relation_id` серед заголовків, але і в її прикладі `curl`, і
в OpenAPI номер ланцюжка стоїть у шляху: `/prepayment-receipts/1717511111`.

### Тіло запиту (`AfterPaymentReceiptPayload`)

- `id` — за вікі, «генерація та передача UUID v4 чека на стороні інтеграції є
  обов'язковою»;
- `cashier_name`, `departament`;
- `rounding` / `rounding_mode`;
- `delivery`, `payments[]`, `header`, `footer`.

**Товарів у тілі немає** — вони беруться з ланцюжка.

Як Checkbox вирішує, що робить запит — додаткову передплату чи післяплату, — не
описано. Очевидне припущення:
- сума менша за залишок — ще одна передплата;
- сума дорівнює залишку — післяплата.

Що буде із сумою, більшою за залишок (готівка з рештою), невідомо. Відповість
пісочниця.

### Відповідь (приклад з вікі, скорочено)

Залишок 45,00 покупець доплатив карткою.

- Позиції — **справжні товари** з податками: `price` 19500, `sum` 19500,
  податок «А» з `value`.
- `total_sum` = 4500 — це залишок.
- `discounts`:
  - `DISCOUNT` «Знижка» −5000;
  - **`PRE_PAYMENT`** «Передплата за замовленням #1717511111» −10000.
- Футер:

  ```
  Попередньо отримано за чеками передплати: 100.00 грн
  1.TEST-L-HCwN: 100.00 грн
  ```

  `TEST-L-HCwN` — фіскальний номер чека передплати.

## Стан ланцюжка (`PrePaymentReceiptInfo`)

Поля:
- `id`, `relation_id`;
- суми: `paid_sum`, `total_sum`, `left_to_pay`, `paid_by_cash_sum`;
- `last_returned_receipt_at`, `receipt_chain_count`, `is_debt_receipt`;
- `pre_payment_status` — один із:
  - `PARTIAL_PAID`;
  - `FULL_PAID`;
  - `CANCELLED`;
  - `PARTIAL_CANCELLED`;
- `created_at`, `updated_at`;
- `receipt_chain` — ідентифікатори чеків:
  `{pre_payment_receipts[], after_payment_receipt, returned_receipts[], returned_receipts_mapping}`;
- `receipts_chain` — ті самі чеки повністю:
  `{pre_payment_receipts[], after_payment_receipt}`.

`pre_payment_receipts` — **масив**, тобто чеків передплати в ланцюжку може бути
кілька.

Приклад з вікі:
- `paid_sum` 14500, `total_sum` 14500, `left_to_pay` 0;
- `receipt_chain_count` 2;
- `pre_payment_status: "FULL_PAID"`;
- `is_debt_receipt: null`.

Що означає `is_debt_receipt`, ні вікі, ні OpenAPI не пояснюють.

## Повернення ланцюжка

Дослівно з вікі:

> Повернення ланцюжка чеків передплати та післяплати. Якщо замовлення було
> повністю виконано та статус має FULL_PAID — буде створено 2 чеки повернення
> (на чек передплати та післяплати). У разі, якщо було створено тільки чек
> передоплати — буде створено 1 чек поверенння.

Тіло (`ReturnPrepaymentChainPayload`):
- `cashier_name`, `departament`;
- `rounding` / `rounding_mode`;
- `delivery`;
- `skip_total_cash_validation` (типово `false`);
- `check_ettn` (типово `false`).

Ні товарів, ні сум у тілі немає: повернути можна **лише весь ланцюжок**.

Відповідь у прикладі вікі — два чеки `type: "RETURN"`:
1. Повернення післяплати:
   - справжній товар з `is_return: true`;
   - `total_sum` 4500, знижки `DISCOUNT` і `PRE_PAYMENT`;
   - `related_receipt_id` = чек післяплати.
2. Повернення передплати:
   - позиція «Передплата за замовленням #…» з `is_return: true`;
   - `total_sum` 10000;
   - `related_receipt_id` = чек передплати.

## Коди помилок

| Код | Коли |
|---|---|
| `prepayment.already_paid` | Чек післяплати, коли весь ланцюжок уже сплачено |
| `prepayment.already_processed` | Фіскальна дія над уже опрацьованим ланцюжком |
| `prepayment.already_returned` | Повернення, коли весь ланцюжок уже повернуто |
| `prepayment.daily_limit` / `prepayment.daily_limit_return` | Повернення передплати готівкою понад денний ліміт |
| `prepayment.has_goods_to_return` | «Чек передплати містить товари для повернення» |
| `prepayment.need_to_remove_ettn` | До ланцюжка прив'язана ЕТТН |
| `prepayment.relation_id_not_unique` | Повторний `custom_relation_id` |
| `prepayment.sum_equals_total_sum` | Сума передплати дорівнює сумі всього ланцюжка |
| `prepayment.sum_equals_zero` | Сума платежів не передана |
| `prepayment.sum_too_large` | Сума платежів перевищує максимальне значення |
| `receipt.cash_register_identity` | Передплату й післяплату створено на касах різного типу |
| `receipt.return_prepayment` | Чек передплати намагаються повернути як звичайний чек |
| `receipt.already_exists` | Переданий `id` чека вже існує |
| `reject_last_receipt.prepayment` | «Неможливо відмінити чек з передплатою» |

## Наслідки для нас

1. **Чек внеску — чек передплати.** У ньому одна позиція «Передплата за
   замовленням #N» на внесену суму, без податків. Товар видно лише у футері.
2. **Чек, що закриває рядок, — чек післяплати.** У ньому справжній товар із
   податками та знижка `PRE_PAYMENT` на суму всіх внесків.
   - Товари задано при відкритті ланцюжка, тому один чек післяплати закриває
     лише товари свого ланцюжка.
   - Якщо одна оплата закриває кілька рядків, документів буде кілька.
3. **Повертається лише весь ланцюжок.** Скасувати один внесок із кількох
   одним документом неможливо, бо часткового повернення в API немає.
   - Тому в магазині з ПРРО «Скасувати внесок» означає скасувати **всі**
     внески на цей товар.
   - Якщо товар уже закрито, те саме повернення охоплює й чек післяплати.
     Це збігається з правилом «повертається лише цілим рядком».
4. **Номер ланцюжка видає Checkbox.** Знайти ланцюжок після тайм-ауту можна
   двома способами:
   - через `GET /receipts/{наш id}` → `pre_payment_relation_id`;
   - через `custom_relation_id`, якщо пісочниця покаже, що він стає номером
     ланцюжка.
5. **Відкриті питання** — їх перевіряє
   `src/pos/fiscal/providers/checkbox/sandbox-prepayment.ts`
   (`npm run fiscal:sandbox:prepayment -- --go`):
   - друга передплата в тому самому ланцюжку;
   - готівкова післяплата з рештою;
   - готівкова післяплата з `ROUND_50`: що робить округлена сума — закриває
     ланцюжок чи стає ще однією передплатою;
   - знижка на рядку всередині ланцюжка;
   - сума вагового рядка (Д8);
   - повторне відкриття з тим самим `id`;
   - платіж у сплачений і в повернений ланцюжок;
   - чи переживає ланцюжок закриття зміни (`--across-shifts`).
