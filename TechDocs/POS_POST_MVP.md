Документ «на потім»: ідеї після стабільного MVP (каса + складські документи + заглушки в приході). **Не робити в поточному спринті.**

## P1. GTIN enrichment (підказка назви)

**Звідки:** відкладено з плану receipt placeholders — у MVP заглушка лише вручну.

### Навіщо

Після скану/вводу штрихкоду, якщо товару немає в каталозі, опційно підказати назву/бренд з реєстру GS1 — продавець швидше заповнює форму заглушки. **Не блокує** створення, якщо lookup порожній або офлайн.

### Джерела (UA-релевантні)

- [Verified by GS1](https://www.gs1.org/services/verified-by-gs1) — глобальний lookup GTIN (ліміти / enterprise API)
- [GEPIR GS1 Україна](https://newgepir.gs1ua.org/) — хто власник штрихкоду; даних по kidswear мало і часто лише company, не «бодик 74»
- Окремого відкритого каталогу «весь дитячий одяг України» немає

### Продуктові правила

- Працює лише як **підказка** у флоу «Створити новий товар» у приході (і опційно в ProductsPage)
- Успіх → prefill `name` (і barcode); юзер може змінити
- Немає в базі / помилка / ліміт → тихий fallback, форма заглушки як зараз
- Не створює товар автоматично без підтвердження
- Не залежить від Square Auto Create / їхньої retail-бази
- Feature flag / store setting: `gtin_lookup_enabled` (default off), щоб не палити квоти

### Технічний начерк (коли дійдемо)

1. Backend: `GET /api/pos/catalog/gtin-lookup?code=` — server-side proxy (ключ API не на клієнті)
2. Кеш відповідей у Redis/Postgres по GTIN (TTL дні/тижні)
3. UI: після «Нічого не знайдено», якщо query схожий на EAN → кнопка «Шукати в GS1» або auto-attempt з індикатором
4. Тести: mock HTTP; hit/miss/timeout; prefill; feature flag off

### Ризики

- Покриття UA kidswear / опт / ноунейм — низьке
- Платні ліміти Verified by GS1
- Юридичні/ToS для комерційного використання даних

### Критерій готовності

Скан невідомого EAN → (якщо GS1 знає) назва підставилась у форму заглушки; якщо ні — звичайне ручне створення без помилки для юзера.
