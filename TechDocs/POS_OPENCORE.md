# POS open-core: платформа відкрита, онлайн-модулі приватні

Дизайн-док і точка відновлення для переходу на **open-core**: відкрита платформа
(source-available, OwnNet 1.1) + приватні вихідники онлайн-модулів (пропрієтарна
ліцензія). Разом із гейтом роздачі бандлів (`TechDocs/POS_LICENSING.md`, фаза 2D)
це і є «посилити захист від клонів» без Closed System у самій платформі.

> Пов'язане: `TechDocs/POS_LICENSING.md` (лицензування, moat, гейт 2D),
> `TechDocs/POS_MODULE_REMOTE_SIGNING.md` (підпис бандлів),
> `TechDocs/POS_MODULE_PLATFORM_VERSION.md` (`PLATFORM_VERSION` / `minHostPlatform`).
>
> Ревізія 2026-11-07: план перевірено по коду `main` (`6acb0c1`) — розділ
> «Що знайшло ревью» (§10) перелічує, що змінилося проти першої версії і чому.

## 1. Мета й модель

- **Відкрита репа (`merenkoff/tiktok-live`, OwnNet 1.1):** платформа, бекенд і
  «коре» модулі. Хто форкне — отримає **робочий магазин одягу** + можливість
  писати **власні** модулі під інші вертикалі. Платформа самодостатня.
- **Приватне (пропрієтарна ліцензія):** онлайн-модулі (клієнтські бандли), що дають
  вертикалі квітів/кафе/продуктів, столи, борги, прямий ефір і ПРРО-кабінети.
  Форкер їхніх **вихідників** і **зібраних бандлів** не отримує.

**Чому це не порушує OwnNet 1.1 (аргумент):**
1. Ви — **власник (Steward)**, а не ліцензіат; лицензія обмежує тих, хто бере код
   у вас, а не вас. Open-core / dual-licensing — стандарт (GitLab, Sentry, MySQL).
2. «No Closed Systems» (§1.12/§5.3) — це про kill switch / lock-in / anti-repair /
   прихований трекінг. Приватні модулі — ніщо з цього: **точки розширення
   відкриті**, будь-хто пише свої модулі (як пропрієтарний плагін до відкритого
   редактора — розширення VS Code).
3. **Ключова умова, яку треба тримати:** відкрита платформа лишається **реально
   робочою сама по собі** (vertical-clothing + «збери свій модуль»). Не
   перетворюйте clothing на огризок — тоді все чисто.
4. **Гейт роздачі не відбирає видане** (§8.3): §1.12 прямо виводить з-під «Closed
   System» лише ті license-compliance checks, що «do not disable software the user
   already lawfully runs». Гейт вирішує, чи **видати нову** версію, і ніколи не
   забирає ту, яку магазин уже отримав. Це ж правило записане в
   `POS_LICENSING.md` («Межі»).

**Застереження щодо історії:** усе, що вже лежить у публічній історії репи й на
гілці `module-builds`, лишається доступним під OwnNet. Захищається **майбутнє**.
Чужих вкладів у код немає (у `git log` — лише власник, Claude і боти), тож
закривати можна весь код модулів; inbound-грант §6 тут нічого не обмежує.

## 2. Що відкрито / що приватно (точний розподіл)

Статично в хост вшито **лише `vertical-clothing`** (`pos/src/modules/registry.ts`
import). Решта вертикальних/онлайн-модулів — **remotes**, вантажаться по URL у
рантаймі (`import()`); хост їхніх вихідників не імпортує (перевірено: поза самими
модулями на них посилаються лише `vite.<id>-remote.config.ts`, `vitest.config.ts`
і e2e — див. §4).

**Лишається ВІДКРИТИМ:**
- Увесь **бекенд `src/`** — зокрема серверні групи роутів `moduleId: null`:
  `debts`, `tables`/`rounds`/`bills`, `bottles`, `fiscal/*`, `kitchen`,
  `guest-orders`, `waiter-calls`, `public-menu`, `live` (`src/pos/pos.routes.ts`).
  **Серверна логіка вертикалей лишається відкритою** — приватні лише клієнтські
  бандли. (Див. §6 «що це НЕ захищає».)
- Платформа: `@pos/platform`, хост-оболонка, `registry`/slots/`verticals.ts`,
  `remoteVerify`, `sign-remote.mjs`, публічні ключі підпису (`remoteSigningKeys.ts`).
- **Бандл-коре модулі** (ship у хості, лишаються відкриті): `vertical-clothing`,
  `products`, `stock`, `returns`, `stocktake`, `customers`, `staff`, `analytics`,
  `settings`, `gtin-enrichment`, `qr-payment`, `catalog-checkout`, `hardware`,
  `live-selling`.

**Кандидати в ПРИВАТНЕ** (online-only remotes, shell ships no code):
`tiktok-live`, `fiscal-checkbox`, `fiscal-cashalot`, `vertical-flowers`,
`vertical-cafe`, `vertical-grocery`, `tables`, `debts` — і бібліотека
**`fiscal-core`** (Р3): її імпортують лише два ПРРО-бандли (відносно,
`../../fiscal-core/...`), хост — ні. Цінність ПРРО — у провайдер-адаптерах
(`src/pos/fiscal/providers` у бекенді) і бандлах, сам `fiscal-core` без секретів;
приват разом із ПРРО — просто найпростіше для збірки.

## 3. Механіка: де живуть приватні вихідники

Два робочі варіанти; вибір — Р2 (§7). Обидва вимагають спершу кроків O-1…O-2.

### 3.1. Варіант B — submodule

Одна приватна репа `liveshop-modules` з 9 теками (8 модулів + `fiscal-core`),
змонтована submodule у **новий** шлях `pos/src/modules-private/` (submodule
монтує корінь репи в один шлях, а `pos/src/modules/` зайнятий відкритими модулями):

```
git submodule add git@github.com:merenkoff/liveshop-modules.git pos/src/modules-private
```

Ціна в щоденній роботі — **висока**:
- кожна наскрізна зміна (сервер + модуль + гайди в одному PR, як ДК5-Б/Г чи Г3)
  стає **двома PR у двох репах + зсувом вказівника submodule**, і вони мусять
  мерджитися в правильному порядку — проти правила «без стекових PR»;
- кожен `git worktree` (а ми працюємо в `.claude/worktrees/*`) потребує
  `git submodule update --init`, а коміт у submodule — push **до** батьківського;
- приватна репа **не тестується сама по собі**: тести її модулів імпортують хост
  (`MODULES` з `registry`, `test/utils`), тож її CI мусить клонувати публічну
  репу й монтувати себе всередину — залежність перевернута.

### 3.2. Варіант D — приватний монорепозиторій + експорт відкритої частини

Джерело правди — **приватна** репа з усім кодом (як зараз, плюс модулі). CI на
кожен пуш у `main` **експортує** дозволені шляхи в публічну `merenkoff/tiktok-live`
(схема Copybara / ShipIt: фільтр шляхів, коміти переносяться з авторами й
повідомленнями, приватні теки й будь-яка згадка в них відсікаються).

- Один PR на зміну, як зараз; worktrees без submodule; тести модулів бігають
  поруч із хостом без жодних трюків.
- Головний мінус експорту — вхідні PR від сторонніх, які треба імпортувати назад,
  — нас не стосується: сторонніх контриб'юторів немає.
- Ризик — протекти приватний шлях у публічну репу помилкою фільтра. Захист:
  allowlist шляхів (не denylist) + перевірка в CI експорту, що в результаті немає
  жодної теки зі списку приватних і жодного рядка `modules-private`.
- Railway може деплоїти з приватної репи напряму (або далі з публічної — вона
  містить увесь бекенд і хост).

### 3.3. Чого не робимо
(A) 8 окремих приватних реп = 8 submodule — забагато; (C) subtree — вихідники
лишаються у відкритій репі, мета не досягається.

## 4. Інвентар: що зламається при переносі теки

Перевірено по коду `main`. Хост-білд і рантайм від цих тек не залежать (remotes по
URL), але **самі модулі** тягнуть хост відносними шляхами, і перенос теки в інший
шлях їх ламає. Повний список (а не лише `../../`):

| Звідки | Що імпортують | Де |
|---|---|---|
| усі 8 `manifest.ts` | `../registry` (тип `RemoteModuleDescriptor`), `../lazyWithRetry` | runtime |
| усі `remote-entry.ts` | `../../platform/version` (`POS_APP_VERSION`) | runtime, **див. нижче** |
| `vertical-*`, `tables`, `debts` | `../../platform/icons` | runtime |
| `tiktok-live` | `../../../lib/urls` | runtime |
| `vertical-grocery` | `../../lib/vertical` | runtime |
| ПРРО-бандли, `vertical-*`, `debts` | `../../../types`, `../../types` (`src/types.ts`, `modules/types.ts`) | лише типи |
| `fiscal-core` | `../../../offline` | runtime |
| ПРРО-бандли | `../../fiscal-core/*`, `../fiscal-core/types` | runtime (їде разом, Р3) |
| тести модулів | `../constants`, `../verticals`, `../featureSlots`, `../navGroups`, `../registry` (`MODULES`), `../../platform/version` (`PLATFORM_VERSION`), `test/utils`, `test/msw/server` | лише тести |

**Чому НЕ через `@pos/platform`.** Перша версія плану пропонувала вивести ці
імпорти через barrel. Це ламає дві речі:
1. `remote-entry.ts` бере `POS_APP_VERSION` **відносно навмисно**: це версія
   **модуля**, вшита при його збірці (так модуль повідомляє свою версію в
   телеметрію й діагностику — див. коментар у `tiktok-live/lib/diagnostics.ts`).
   Через barrel він мовчки став би повідомляти версію **каси**.
2. Нові runtime-експорти barrel = зміна поверхні = підняти `PLATFORM_VERSION`
   (`platform/surface.test.ts`) = `minHostPlatform` модулів росте = спершу
   оновлювати каси. Для суто структурної зміни це зайве.

Тому O-1 — **алиас на етапі збірки**, не barrel: `@host/*` → `pos/src/*` у
`tsconfig` `paths` і `resolve.alias` кожного `vite.<id>-remote.config.ts` та
`vitest.config.ts`; модульні `../registry` → `@host/modules/registry` тощо. Код,
який сьогодні вшивається в бандл, вшивається й далі — поведінка не змінюється.
**Критерій готовності O-1:** усі 8 бандлів, зібрані до й після, **побайтно
однакові** (за винятком підпису/часу в маніфесті, якщо він там є — тоді
порівнюємо `remote-entry.js` і чанки).

Інші посилання на теки модулів, які правляться в O-4:
- `pos/vite.<id>-remote.config.ts` — вхід `src/modules/<id>/remote-entry.ts` і
  `moduleCss(...)` (ПРРО-конфіги тягнуть `./src/modules/fiscal-core/**`);
- `pos/package.json` — `build:<id>-remote`, `serve:<id>-remote`,
  `check:<id>-css-coverage`;
- `pos/vitest.config.ts` — 21 файл приватних модулів у `coverage.include`;
- `pos/scripts/check-module-css-coverage.mjs` — шлях для `tables`;
- `.github/workflows/module-release.yml` — перевіряє
  `pos/src/modules/${module}/remote-entry.ts`;
- `CLAUDE.md` і `TechDocs/*` — шляхи `pos/src/modules/<id>/` згадуються всюди.

## 5. CI, збірка, секрети

- **Публічний e2e без приватних вихідників падає ЦІЛИМ джобом**, не окремими
  спеками: `webServer.command` у `pos/playwright.config.ts` збирає шість приватних
  remotes одним ланцюжком `&&`. Вісім спеків читають приватні бандли з
  `dist-remotes/`: `debts`, `tables`, `tablet`, `vertical-cafe`, `vertical-flowers`,
  `vertical-grocery`, `florist-bench`, `fiscal-cashalot`. До переносу:
  `webServer` збирає лише відкриті remotes (`stocktake`, хост), а ці вісім спеків
  переїжджають у приватний CI (варіант B) або запускаються тільки там, де
  приватні теки є (варіант D — у приватній репі, з тим самим конфігом).
- PR із форків секретів не отримують, тож жоден публічний CI не має залежати від
  доступу до приватного.
- **Хост-білд відкритої частини лишається зеленим** без приватних тек: хост
  статично імпортує лише `vertical-clothing`. `test:coverage` переживе відсутні
  файли в `coverage.include`, але список треба прибрати (O-4).
- `check-platform-boundary.mjs` — єдина гвардія від другої копії стор у бандлі
  модуля. Вона мусить **ганяти й приватні теки** — у приватному CI (варіант B) або
  як зараз (варіант D).
- **Module Release** переїжджає туди, де вихідники: тег, версія з
  `pos/package.json`, збірка, підпис прод-ключем. Варіант B: workflow у приватній
  репі клонує публічну як батька (deploy key) — версію бере з неї. Варіант D:
  workflow як є, лише в приватній репі.
- Публічні ключі підпису лишаються у відкритій `remoteSigningKeys.ts`; приватний
  ключ — як і зараз, лише в CI (`POS_REMOTE_SIGNING_KEY`). Клон не підробить
  бандл під вашим ключем.

## 6. Що це захищає, а що НІ (чесно)

Захищає: **вихідники** онлайн-модулів (майбутні версії) і — лише разом із §8 —
**зібрані бандли** від нелицензованих інсталяцій.

НЕ захищає:
- **Серверна логіка вертикалей лишається відкритою** (`src/pos/*`: debts, tables,
  bottles, fiscal, guest-orders). За відкритим API форкер у теорії може **сам
  переписати** клієнтські UI (дорожче, але реально).
- **Бандл отримує кожна лицензована каса**, тож лицензований клієнт може його
  скопіювати. Гейт зупиняє хотлінк із нелицензованих клонів, не копіювання.
- Те, що вже в публічній історії репи й на гілці `module-builds`, лишається
  доступним.

**Де основна цінність.** Оскільки сервер відкритий, а бандл однаково роздається,
найбільше дає **закрита роздача** (§8: бандли не на публічному CDN + гейт + підпис).
Закриті вихідники (§3) додають захист від «форкнути й супроводжувати» — це
найдорожчий і найризикованіший крок, тому він останній (§9).

## 8. Гейт роздачі бандлів (частина 2, дизайн)

Мета: `the-live.shop` віддає **підписані бандли модулів** (і вже зроблений фід
оновлень десктопу, 2D-A) лише **лицензованим** інсталяціям; клон без валідної
ліцензії лишається з платформою (clothing), але без ваших онлайн-модулів.

### 8.1. Бандли мусять піти з публічного CDN

Сьогодні Module Release комітить зібране в **публічну** гілку `module-builds`, а
jsdelivr роздає її за тегом:
`https://cdn.jsdelivr.net/gh/merenkoff/tiktok-live@module-<id>-v<ver>/<id>/remote-entry.js`.
Проксі, що бере бандл **з цієї ж адреси** (перша версія гейта, PR #399), нічого не
закриває: адресу видно з шаблону й тегів, і її можна взяти напряму, мимо гейта.

Тому для приватних модулів:
- Module Release публікує збірку **не в публічну гілку**, а в закрите сховище —
  рекомендація Р6: том Railway API (він уже є, `data/pos-uploads`; окрема тека
  `data/module-bundles/<id>/<ver>/`), куди workflow заливає файли через
  owner-only ендпоінт із секретом CI; альтернатива — ассети релізів приватної
  репи, які сервер тягне з токеном і кешує;
- гейт роздає **звідти**; jsdelivr лишається тільки для відкритих модулів
  (`stocktake`, …) і для вже виданих старих версій;
- старі теги на `module-builds` лишаються публічними — це історія (§1); захист
  стосується версій, зібраних після переносу.

### 8.2. Токен — у шляху, не в заголовку

Браузер **не може** додати `X-License-Key` до `import()`: у `registry.ts` хост
спершу робить `fetch` (перевірка підпису), а тоді окремий
`import(/* @vite-ignore */ url)`, і цей запит заголовків не несе. Чанки бандл
вантажить **відносними** шляхами, тож токен у query-параметрі до них не дійде.

Рішення — токен **у шляху**:
`GET /api/modules/<token>/<id>/<ver>/<file>`.
- Відносні імпорти чанків зберігають префікс шляху, тож токен доходить до всіх
  файлів бандла — однаково на вебі, планшеті й десктопі (Rust теж просто бере URL).
  Це важливо саме для чанків: `remoteVerify.ts` хеш-перевіряє лише
  `remote-entry.js` і `style.css`, а лінива сторінка модуля — окремий чанк, тож
  гейт, що закриває тільки вхід, лишив би сторінки відкритими.
- Токен — короткоживучий підпис сервера (`store`, `exp`, ключ — як
  `issuePrintLink` у QR-меню), видається з логіном і `/me` разом із
  `module_remotes`; хост підставляє його в URL при завантаженні. `module_remotes`
  у БД зберігає URL без токена.
- Сервер перевіряє токен і що магазин має право на цей модуль; відповідь —
  байти **дослівно**, тож Ed25519-підпис бандла не ламається.
- За прапором `LICENSE_MODULE_GATE` (дефолт off = віддає без перевірки токена).
- Підпис бандла лишається (хост перевіряє) — гейт керує **видачею**, не довірою.

Це зміна хоста (підставити токен у URL) — для вебу й планшета вона їде з
деплоєм, для десктопу — з POS Release; до того десктоп вантажить зі старих URL.

### 8.3. Гейт не відбирає видане (§1.12)

- Гейт вирішує, чи видати **нову** версію. Версію, яку магазин уже отримав, він
  віддає й далі, навіть коли ліцензія закінчилась.
- Десктоп і так тримає модулі в дисковому кеші (`liveshopmodule://`). Веб і
  планшет перекачують модуль на кожному завантаженні, тому «видане» треба
  пам'ятати **на сервері**: таблиця `(store_id, module_id, version, issued_at)`;
  токен для такої пари видається завжди.
- Інакше кафе з простроченою ліцензією посеред зміни втратить столи й каталог —
  саме те, що §1.12(a) називає Closed System.
- Коли саме припиняється видача **нових** версій — умова оферти (Р7), задокументована
  й погоджена клієнтом.

## 10. Що знайшло ревью (2026-11-07) і що змінилося

1. **Бандли лишались публічними** — гейт проксював ту саму jsdelivr-адресу, яку
   можна взяти напряму. → §8.1, Р6, крок O-3.
2. **`X-License-Key` не доходить із браузера** до `import()` і чанків. → токен у
   шляху, §8.2.
3. **Barrel `@pos/platform` для O-1** підмінив би версію модуля версією каси й
   підняв би `PLATFORM_VERSION`. → алиас збірки `@host/*` з побайтною перевіркою, §4.
4. **Інвентар імпортів був неповний** (лише `../../`): бракувало `../registry`,
   `../lazyWithRetry` у всіх маніфестах, тестових `../constants`/`../verticals`/
   `../featureSlots`/`../navGroups`, `fiscal-core` → `offline`. → таблиця §4.
5. **Публічний e2e падав би цілим джобом** через ланцюжок `&&` у `webServer`. → §5, O-2.
6. **Приватна репа як submodule не тестується сама** і подвоює PR. → варіант D, §3.2, Р2.
7. **Кожен файл модулів має заголовок OwnNet** — після переносу копія, що
   витекла, формально лишилась би під OwnNet. → Р8, O-6.
8. **§1.12 вимагає не вимикати вже видане.** → §8.3, Р7.
