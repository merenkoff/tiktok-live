# POS open-core: платформа відкрита, онлайн-модулі приватні

Дизайн-док і точка відновлення для переходу на **open-core**: відкрита платформа
(source-available, OwnNet 1.1) + приватний репозиторій онлайн-модулів (пропрієтарна
ліцензія), підключений як **git submodule**. Разом із гейтом роздачі бандлів
(`TechDocs/POS_LICENSING.md`, фаза 2D) це і є «посилити захист від клонів» без
Closed System у самій платформі.

> Пов'язане: `TechDocs/POS_LICENSING.md` (лицензування, moat, гейт 2D),
> `TechDocs/POS_MODULE_REMOTE_SIGNING.md` (підпис бандлів).

## 1. Мета й модель

- **Відкрита репа (`merenkoff/tiktok-live`, OwnNet 1.1):** платформа, бекенд і
  «коре» модулі. Хто форкне — отримає **робочий магазин одягу** + можливість
  писати **власні** модулі під інші вертикалі. Платформа самодостатня.
- **Приватна репа (нова, пропрієтарна ліцензія):** онлайн-модулі (клієнтські
  бандли), що дають вертикалі квітів/кафе/продуктів, столи, борги, прямий ефір і
  ПРРО-кабінети. Форкер їхніх **вихідників** не отримує.

**Чому це не порушує OwnNet 1.1 (аргумент):**
1. Ви — **власник (Steward)**, а не ліцензіат; лицензія обмежує тих, хто бере код
   у вас, а не вас. Open-core / dual-licensing — стандарт (GitLab, Sentry, MySQL).
2. «No Closed Systems» (§1.12/§5.3) — це про kill switch / lock-in / anti-repair /
   прихований трекінг. Приватні модулі — ніщо з цього: **точки розширення
   відкриті**, будь-хто пише свої модулі (як пропрієтарний плагін до відкритого
   редактора — розширення VS Code).
3. **Ключова умова, яку треба тримати:** відкрита платформа лишається **реально
   робочою сама по собі** (vertical-clothing + «збери свій модуль»). Не
   перетворюйте clothing на огризок — тоді все чисто.

**Застереження:** закривати можна лише **свій** код (чужі контрибуції покриває
inbound-грант §6); це захист **майбутнього**, не того, що вже в публічній історії.

## 2. Що відкрито / що приватно (точний розподіл)

Статично в хост вшито **лише `vertical-clothing`** (`pos/src/modules/registry.ts`
import). Решта вертикальних/онлайн-модулів — **remotes**, вантажаться по URL у
рантаймі (`import()`), хост їхні вихідники НЕ імпортує.

**Лишається ВІДКРИТИМ:**
- Увесь **бекенд `src/`** — зокрема серверні групи роутів `moduleId: null`:
  `debts`, `tables`/`rounds`/`bills`, `bottles`, `fiscal/*`, `kitchen`,
  `guest-orders`, `waiter-calls`, `public-menu`, `live` (`src/pos/pos.routes.ts`).
  **Серверна логіка вертикалей лишається відкритою** — приватні лише клієнтські
  бандли. (Див. §6 «що це НЕ захищає».)
- Платформа: `@pos/platform`, хост-оболонка, `registry`/slots/`verticals.ts`,
  `remoteVerify`, `sign-remote.mjs`, публічні ключі підпису (`remoteSigningKeys.ts`).
- **Бандл-коре модулі** ( ship у хості, лишаються відкриті): `vertical-clothing`,
  `products`, `stock`, `returns`, `stocktake`, `customers`, `staff`, `analytics`,
  `settings`, `gtin-enrichment`, `qr-payment`, `catalog-checkout`, `hardware`,
  `live-selling`.

**Кандидати в ПРИВАТНЕ** (online-only remotes, shell ships no code):
`tiktok-live`, `fiscal-checkbox`, `fiscal-cashalot`, `vertical-flowers`,
`vertical-cafe`, `vertical-grocery`, `tables`, `debts`.

**Рішення власника (§7):** `fiscal-core` — спільна залежність обох ПРРО-бандлів.
`fiscal-checkbox`/`fiscal-cashalot` імпортують його **відносно** (`../fiscal-core/...`).
Тому якщо провайдер-модулі йдуть у приват, а `fiscal-core` лишається відкритим,
відносний імпорт зламається. Варіанти: **(а)** винести `fiscal-core` у приват
разом із ПРРО-модулями (найпростіше для збірки) — рекомендую; **(б)** лишити
відкритим і вивести його через alias `@pos/platform`. Цінність ПРРО — у
провайдер-адаптерах (`src/pos/fiscal/providers` у бекенді + приватні бандли), сам
`fiscal-core` без секретів.

## 3. Механіка: git submodule

Submodule монтує **корінь репи** в один шлях. `pos/src/modules/` зайнятий
відкритими модулями, тож туди один приватний репозиторій не змонтувати.

**Рекомендований розклад (B):** одна приватна репа `liveshop-modules` з 8 модулями
у власних підтеках, змонтована submodule у **новий** шлях, напр.
`pos/src/modules-private/`. Хост модулі статично не імпортує, тож змінюються лише
**конфіги збірки**, не рантайм:

```
git submodule add git@github.com:merenkoff/liveshop-modules.git pos/src/modules-private
```

Альтернативи (не рекомендую): (A) 8 окремих приватних реп = 8 submodule — забагато;
(C) subtree — вихідники лишаються у відкритій репі, мета не досягається.

**ВАЖЛИВО (перевірено по коду):** приватні модулі **таки** імпортують хост
**відносними** шляхами, не лише через alias. Знайдено climb-out імпорти (`../../`)
у хост: `types` (`src/types.ts`), `platform/version`, `platform/icons`, `lib/urls`,
`lib/vertical`, `test/utils`, `test/msw/server`, і ПРРО-модулі тягнуть `fiscal-core`.
Перенос теки **зламає** ці імпорти. Тож O-1 — не косметика: треба **прохід по
імпортах** — вивести їх через alias `@pos/platform` (бажано) або додати tsconfig/vite
alias на нові шляхи. Поки це не зроблено, submodule-перенос не збереться.

## 4. Що саме змінити (інвентар посилань)

Хост-білд і рантайм **не** залежать від цих тек (remotes по URL). Правити треба
лише збірку бандлів. На кожен із 8 модулів:

- `pos/vite.<id>-remote.config.ts` — шлях входу `src/modules/<id>/remote-entry.ts`
  → `src/modules-private/<id>/remote-entry.ts`.
- `pos/package.json` — скрипти `build:<id>-remote`, `serve:<id>-remote`,
  `check:<id>-css-coverage` (аргументи `src/modules/<id>`).
- `pos/vitest.config.ts` — include/exclude, що згадують `vertical-flowers`,
  `vertical-cafe`, `vertical-grocery`, `tables`, `debts`.
- `pos/scripts/check-module-css-coverage.mjs` — шлях для `tables`.
- Юніт-тести всередині тек модулів переїжджають разом із ними (у приватну репу);
  e2e (`pos/e2e/debts.spec.ts` тощо) лишаються у відкритій, але потребують
  зібраного приватного бандла в CI.

`fiscal-checkbox`/`fiscal-cashalot` css-coverage також тягнуть `fiscal-core` — якщо
той лишається відкритим, нічого не ламається (приватний бандл + відкритий dep).

## 5. CI, збірка, секрети

- **Хост-білд відкритої репи без submodule має лишатися зеленим.** Хост статично
  імпортує лише `vertical-clothing`, тож `pos npm run build` і більшість тестів
  проходять без приватної теки. Перевірити, що жоден відкритий тест не імпортує
  приватний модуль (вони online-only — не повинні).
- **CI, що БУДУЄ приватні бандли** (Module Release), потребує доступу до приватної
  репи: deploy key / PAT у секретах Actions, `submodules: recursive` у checkout.
- **Форкер без доступу** отримує порожню теку submodule — його `build:<id>-remote`
  впаде (нема вихідників), але сам POS (clothing) збереться й працюватиме.
- Публічні ключі підпису лишаються у відкритій `remoteSigningKeys.ts` (хост
  перевіряє підпис бандла); приватний ключ підпису — як і зараз, лише в CI
  (`POS_REMOTE_SIGNING_KEY`). Клон не підробить бандл під вашим ключем.

## 6. Що це захищає, а що НІ (чесно)

Захищає: **вихідники** 8 онлайн-модулів (майбутні версії) — форкер їх не бачить і
не супроводжує.

НЕ захищає само по собі:
- **Серверна логіка вертикалей лишається відкритою** (`src/pos/*`: debts, tables,
  bottles, fiscal, guest-orders). За відкритим API форкер у теорії може **сам
  переписати** клієнтські UI (дорожче, але реально).
- **Зібрані бандли на jsdelivr — публічні URL** (роздаються вашим же касам). Ховання
  вихідників не заважає форкеру вантажити ваші **публічні збірки** в рантаймі. Щоб
  закрити це — **гейт роздачі** (§8).
- Те, що вже в публічній історії репи, лишається доступним.

Повний ефект = приватні вихідники (**§3–5**) + гейт роздачі бандлів (**§8**) +
існуючий moat підпису (бандл не підробити) + юридичний важіль (OwnNet + договір).

## 8. Гейт роздачі бандлів (частина 2, дизайн)

Мета: ваш `the-live.shop` віддає **підписані бандли модулів** (і вже зроблений фід
оновлень десктопу, 2D-A) лише **лицензованим** інсталяціям; клон без валідної
ліцензії лишається з платформою (clothing), але без ваших онлайн-модулів.

- **Проксі з гейтом:** `GET /api/modules/:id/*` на the-live.shop — перевіряє
  ліцензійний токен (`requireValidLicense`, уже є в 2D-A), тоді віддає/проксує
  підписаний бандл із поточного джерела (jsdelivr/реліз). Без валідної ліцензії →
  403. За прапором `LICENSE_MODULE_GATE` (дефолт off = прозорий проксі, нуль змін).
- **Репойнт `module_remotes`** магазинів на гейтований URL (супер-адмін).
- **Per-deployment токен:** як і для 2D-B, щоб гейт бив per-install, каса/хост має
  слати свій токен (логін → `X-License-Key`); без цього гейт на рівні сервера
  розрізняє лише «є валідний токен у запиті / нема».
- Підпис бандла лишається (хост перевіряє) — гейт керує **видачею**, не довірою.

Деталі enforcement і Tauri-частина — спільні з `POS_LICENSING.md` 2D-B.
