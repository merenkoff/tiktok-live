# API працює одним процесом

Довідка й точка відновлення для питання «а якщо реплік стане більше». Перевірено **2026-09-30**
(читанням конфігурації Railway, `curl` і коду; нічого не змінювалось). Виникло з фази Q4
`TechDocs/POS_QR_MENU.md` («спільний кеш і лімітер, якщо буде більше одного інстансу»): розвідка
показала, що умова не виконується й виконатись не може, доки API тримає том. Тому Q4 — це цей
документ, а не код.

## Що перевірено на проді

Проєкт Railway `LiveShop`, середовище `production`, сервіс `tiktok-live` (API):

| Факт | Значення |
|---|---|
| Реплік | **1** (`multiRegionConfig`: `europe-west4-drams3a` → `numReplicas: 1`) |
| Том | `tiktok-live-volume`, 5000 МБ, `/app/data/pos-uploads` (фото товарів, логотипи закладів) |
| Чому це стеля | Документація Railway (`volumes/reference`, «Caveats»): «Replicas cannot be used with volumes» |
| Redis | **немає**: у проєкті чотири сервіси (POS, Admin, Postgres, tiktok-live). У змінних API лишились `REDIS_HOST` і `REDIS_PORT`, але вони ні на що не вказують |
| Redis у коді | `src/` його не імпортує. `ioredis` і `bullmq` лише лежать у `package.json`; `docker-compose.yml` піднімає Redis тільки локально |
| Домени | `the-live.shop` → порт **3000**, відповідає (`/health` 200). `www.the-live.shop` і `tiktok-live-production-de3d.up.railway.app` → порт **8080**, відповідають **502** (`connection refused`) — застосунок слухає `API_PORT`, а не 8080 |
| Проксі | `server: railway-hikari`, без Cloudflare перед `the-live.shop` |

Щоб перевірити знову: Railway MCP (`describe-service` для `tiktok-live`), дашборд сервісу
(Settings → Deploy → Replicas, Volumes) або `curl -I https://the-live.shop/health`.

**Отже:** підняти другу репліку API сьогодні не можна. Спільний кеш, Redis і розподілений лімітер не
мають споживача, і додавати їх «про запас» означало б нову інфраструктуру й нову точку відмови без
користі. У документах і коментарях раніше стверджувалось протилежне («Redis уже в стеку», «на Railway
може бути більше однієї репліки») — це було хибно, виправлено разом із цим документом (див. «Що ще
згадує Redis» нижче).

## Порядок робіт, коли репліки знадобляться

1. **Винести файли з тома.** Фото товарів і логотипи (`src/pos/uploads.service.ts`,
   `pos.plugin.ts`) у об'єктне сховище (Railway Bucket або S3-сумісне), `/pos-uploads/*` — редірект чи
   проксі. Без цього репліки неможливі за визначенням; усе нижче безглузде раніше.
2. Redis-сервіс у проєкті + `REDIS_URL`; інтерфейс сховища для лімітера.
3. **Один модуль-лімітер** замість трьох копій (`qr.routes.ts`, `guest-orders.service.ts`,
   `superAuth.ts`), з витісненням, інжектованим годинником і `reset()` для тестів; реалізація в
   пам'яті лишається для тестів і локалки.
4. `invalidatePublicMenu` через pub/sub (або короткий TTL і відмова від миттєвості — тоді
   документувати, що «стоп» доходить до 30 с).
5. `revokedTokens` і `SessionManager`: або липка сесія до одного інстансу, або стан у Redis.
6. Advisory-lock на `reconcileQrPayments`, `refillAllStores` і на міграції старту.
7. Оновити цей документ і прибрати «одна репліка» з `CLAUDE.md`.

## IP клієнта за проксі Railway

Сьогодні `request.ip` — адреса проксі (в `src/api.ts:35` немає `trustProxy`), тож жоден ліміт «за IP»
не працює, а блокування супер-адміна спільне для всіх. Що відомо й що ні:

- Edge Railway бачить справжній IP (`srcIp` у HTTP-логах) і передає застосунку `X-Real-IP` (документація
  «Specs & Limits», «Request Headers»). `X-Forwarded-For` там **не названо**; чи додається він і чи
  перезаписує edge підроблений клієнтом заголовок — **не підтверджено**.
- Хибне налаштування (`trustProxy: true` при відсутньому XFF або зайвому хопі) дозволяє клієнту
  підмінити свій IP заголовком і обійти будь-який ліміт.

**Рішення (2026-09-30):** коли лімітер буде потрібен, IP береться за env **`TRUST_PROXY_HOPS`**
(число хопів для Fastify `trustProxy`), **за замовчуванням 0** — поведінка без змінної не
змінюється. Перед тим як виставити її на Railway, перевірити на проді: у логах Fastify `remoteAddress`
має стати публічним IP клієнта, а запит із підробленим `X-Forwarded-For: 1.2.3.4` — не потрапити в нього. Не
вийшло — читати `X-Real-IP` напряму, і лише після такої самої перевірки.

## Найдорожчі неавтентифіковані запити (вхід для майбутнього лімітера)

Зараз на гостьових ендпоїнтах **немає жодного ліміту**, крім per-table у `guest-orders`.
Токен — 144 біти, ключ столу — 72 біти, тож перебір безглуздий; ризик — вартість запиту.

| Ендпоїнт | Ціна одного запиту |
|---|---|
| `GET /m/:token/tables` | токен + стіл + `listMenuTables` + `verifyPrintLink`, потім **синхронний рендер QR на кожен стіл** на event loop, без кешу — найдорожчий |
| `GET /m/:token/qr` | те саме з одним QR |
| `GET /m/:token` | рендерить усе меню щоразу, навіть коли JSON у кеші |
| `GET /api/pos/public/menu/:token/bill` | ~6 запитів у БД |
| `…/orders*` | до 3 запитів у `guestContext`, `expireStaleGuestOrders` (UPDATE по магазину) на кожне читання, по 2 запити на рядок (до 30) |
| довільний невідомий токен | 1 запит у БД, негативного кешу немає (пул на 20 з'єднань спільний із касами) |

Правила для майбутнього ліміту: гості кав'ярні сидять за одним Wi-Fi (один NAT-IP), а `menu.js`
опитує кожні 30 с (меню) і 20 с (рахунок), тож ліміт на **всі** запити з IP вдарить по чесних
гостях — обмежувати треба **промахи** (404/невалідний ключ) і **дорогі** маршрути (`/tables`, `/qr`).
Відповідь — **429**, а не 404: `menu.js` на 404 перезавантажує сторінку й ховає рахунок, на інші
статуси мовчить.

## Інше, що знайдено дорогою

- `POST /api/pos/auth/staff/pin` і `/auth/owner/login` не мають жодного throttle: 4–6 цифр PIN
  перебираються. Це відсутній контроль, не питання реплік; винести окремою задачею.
- Зміна вертикалі магазина супер-адміном (`PATCH /api/pos/super/stores/:id` → `setStoreVertical`,
  `super.service.ts:132,254`) не викликає `invalidatePublicMenu`, хоча коментар біля `findMenuStore`
  (`menu.service.ts:466-468`) каже, що магазин без кухні перестає публікуватись: меню може жити ще до
  15 с (токен) плюс 15 с (меню). Дрібне.
- `Dockerfile:40-42` каже «Railway injects PORT», але `src/index.ts` читає `API_PORT`; порт у
  доменах Railway (3000 чи 8080) має збігатись із тим, що слухає процес.
