# POS — вигляд меню (nav customization)

Магазин може змінити **назву, порядок та іконку** пунктів навігації у себе:
бічної панелі каси (і нижньої панелі на телефоні) та лівого меню адмінки.
Екран власника — `/admin/appearance` («Вигляд меню»).

Це **тільки вигляд**. Які модулі взагалі є в магазині — це `enabled_modules`
(чеклист на «Налаштуваннях») і `module_remotes`; жодне налаштування вигляду не
може додати пункт, прибрати його чи перенаправити кудись інше.

---

## 1. Модель даних

`pos_stores.nav_overrides jsonb NOT NULL DEFAULT '{}'` (міграція `033`).

```jsonc
{
  "catalog-checkout:cashier-primary:/register": { "label": "Продаж", "icon": "ShoppingCart" },
  "customers:cashier-primary:/customers":      { "order": 0 }
}
```

Ключ — `<moduleId>:<location>:<path>`:

* **moduleId** і **path** — те, чим пункт є;
* **location** (`cashier-primary` | `admin-sidebar`) у ключі тому, що один модуль
  законно ставить **той самий** маршрут у два меню під різними назвами
  (`products` → «Товари» і в сайдбарі, і в рейці каси у власника), і
  перейменування одного не повинно чіпати друге.

У ключі немає `visible` — два пункти одного модуля, що різняться лише
аудиторією (`returns` показує `/admin/sales` вебвласнику і `/sales` решті), уже
різняться маршрутом, тож налаштовуються окремо.

Дві властивості, на яких тримається дизайн:

1. **Розріджений (sparse).** Override несе лише ті поля, які власник справді
   змінив. Модуль, що пізніше сам себе перейменує, пересуне чи змінить іконку,
   усе одно доїде до магазину, який чіпав тільки порядок.
2. **Інертний, коли не влучив.** Ключ на модуль або маршрут, якого вже немає,
   нічого не змінює і нічого не ламає — ні міграції, ні чистки. І навпаки: пункт
   без override лишається рівно таким, яким його оголосив модуль.

Тому «відновити типове» = **видалити** ключ, а не записати в нього дефолт.

## 2. Бекенд

| Місце | Що робить |
|---|---|
| `migrations/033_pos_store_nav_overrides.sql` | колонка + коментар |
| `src/pos/core/nav.ts` | `sanitizeNavOverrides`, `NAV_OVERRIDE_KEY_RE`, ліміти |
| `src/pos/routes/store.routes.ts` | `PATCH /api/pos/store` (owner-only) |
| `src/pos/analytics.service.ts` | `mapStore` / `StorePatch` / jsonb-запис |
| `src/pos/core/auth.ts`, `auth.service.ts` | їде в `AuthResponse.store.nav_overrides` |

Санітайзер пропускає тільки вигляд: ключ за регуляркою, `label` ≤ 40 символів
після `trim`, `icon` — голе ім'я іконки меню, ключ `NAV_ICONS` (`^[A-Za-z0-9]+$`; історично — імена lucide, тепер вони ведуть на гліфи `design/icons`), `order` —
ціле в межах ±10000, не більше 64 записів; запис, у якому не лишилося жодного
поля, викидається (порожній `{}` зберігався б вічно, не означаючи нічого).

Він **навмисно поблажливий** щодо того, який саме пункт названо ключем: перелік
nav-пунктів належить клієнтському білду, якого бекенд не знає і не мусить знати
— магазин може працювати на новішій збірці POS або мати online-only модуль, про
який бекенд ніколи не чув. Override, що не влучив, інертний на будь-якому
клієнті.

`nav_overrides` їде разом із логіном (не тільки в `GET /store`), бо десктоп-каса
при холодному офлайн-старті відновлює всю сесію з кешованого `pos_auth` — і меню,
що там повертається до заводських назв, це рівно той момент, коли касиру цього не
треба.

## 3. Клієнт

| Місце | Що робить |
|---|---|
| `pos/src/modules/navOverrides.ts` | `navItemKey`, `applyNavOverride`, `collectNavEntries`, `pruneNavOverrides` — чисті, без React |
| `pos/src/modules/selectNav.ts` | `selectNavItems(..., overrides)` — єдине місце, де це застосовується |
| `pos/src/modules/useNavOverrides.ts` | читає `auth.store.nav_overrides` |
| `pos/src/components/Nav.tsx` | тільки рендерить |
| `pos/src/offline/{db,auth-local}.ts` | `navOverrides` у кеші `staffUnlock` |
| `pos/src/pages/admin/AppearancePage.tsx` | екран власника |
| `pos/src/modules/settings/manifest.ts` | маршрут `/admin/appearance` + пункт меню |

Порядок у `selectNavItems` важливий: спершу фільтри (модуль увімкнений, шел,
`ownerOnly`, `visible()`), **потім** overrides, **потім** сортування. Тому
override не може ані додати пункт, ані показати той, який контекст ховає.
Сортування стабільне, тож пункти, яких власник не пересував, лишаються в порядку
реєстру серед однакових `order`.

Оскільки overrides застосовуються в хості, **online-only модулі (`tiktok-live`
тощо) отримують це безкоштовно** — їхній код нічого про це не знає.

Обмеження, яке варто знати: у десктоп-каси заглушка ще не завантаженого
online-only модуля (`placeholderDescriptor`) бере `to` з `routePath` для **всіх**
своїх nav-пунктів, тож її ключ може не збігтися з ключем справжнього дескриптора
(`tiktok-live:admin-sidebar:/live` проти `…:/admin/live`). Тоді заглушка
показується з типовою назвою — тимчасовий стан «ще не завантажено», не помилка.

## 4. UX екрана

* **Сегментований перемикач** «Каса» / «Адмінка» — одне меню за раз.
* **Живий перегляд** поруч зі списком: та сама темна рейка каси, намальована з
  тих самих `NavItem`, що їх отримає каса. Для адмінки — текстовий сайдбар без
  іконок, бо він таким і є.
* **Перетягування** + кнопки «Вище/Нижче» (клавіатура і доступність — не опція).
* **Перейменування** прямо в рядку: порожнє поле = типова назва (вона стоїть
  плейсхолдером), тож скинути назву можна, просто стерши текст.
* **Вибір іконки** — тільки з `NAV_ICONS` (`pos/src/platform/icons.ts`), тобто з
  того, що застосунок уміє намалювати: ім'я, якого в білді немає, мовчки впало б
  до запасного гліфа на касі.
* **Підказка про аудиторію** в рядку: «лише власник», «лише десктоп-каса», «лише
  бічна панель» — власник із ноутбука налаштовує і ті пункти, яких сам не бачить.
* **«Відновити типове»** — на рядок і на все меню; пересунути пункт назад на
  своє місце теж не лишає сліду (`withOrder` тоді стирає `order`, а не пише
  дефолт).
* Кнопка «Зберегти» неактивна, поки нічого не змінено; поруч — «Скасувати зміни»
  і нагадування, що каси підхоплять це після наступного входу.

Іконки свідомо не пропонуються для `admin-sidebar`: те меню їх не малює, а
контрол, який нічого не робить, — гірше за його відсутність.
