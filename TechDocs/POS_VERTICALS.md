# POS: вертикалі продажів (одяг / квіти / кафе)

Дизайн-документ і **точка відновлення роботи**. Таблиця фаз унизу — оновлюйте її,
коли фаза лягає.

## 1. Навіщо

POS будувався навколо одного способу продажу — магазин одягу: варіант товару має
розмір і колір, продається поштучно, екран каси показує плитки товарів і вибір
варіанта. Усе інше (оплата, чек, ПРРО, повернення, склад, аналітика) до цього
байдуже.

Продукт має обслуговувати й інші типи роздрібу. Найближчий — квітковий магазин
(орієнтир Posiflora: стебла, довжина, країна, згодом букети зі списанням
компонентів), далі — кафе (техкарти, модифікатори). Тому **вертикаль** стає
явним поняттям: вона задає схему атрибутів товару, дозволені одиниці виміру та
який модуль малює каталог на екрані продажу.

## 2. Модель

Одна колонка `pos_stores.vertical` (міграція `034`) — id вертикалі. Набір
вертикалей живе **в коді** (`src/pos/verticals/`), а не в CHECK-констрейнті:
нова вертикаль не має вимагати міграції, рівно як і новий провайдер ПРРО
(`isFiscalProviderId`). Значення, якого збірка не знає, деградує до `clothing`
на читанні (`verticalOrDefault` + `logger.warn`) — логін магазину не падає
ніколи.

```
VerticalDefinition {
  id, title,
  attributes: AttributeSpec[],   // key, label, type, options?, unitSuffix?, required?, inLabel?, inSearch?
  units,                         // units[0] — за замовчуванням
  labelOf(attrs) → string,       // правило підпису варіанта
  productKinds                   // ['simple'] зараз; 'composite' зарезервовано
}
```

`VerticalPublicConfig` — те, що їде на клієнт: схема й одиниці, **без функцій**.
Клієнт рендерить поля за схемою і читає готовий `label` із сервера; сам він
підписів не збирає (до цієї роботи таких композиторів було чотири, з трьома
різними роздільниками).

### Хто змінює

Тільки супер-адмін (`PATCH /api/pos/super/stores/:id`). Власник бачить тип
магазину read-only в «Налаштуваннях». Причина: вертикаль визначає схему
атрибутів каталогу, який власник уже наповнив; зміна перебудовує підписи всіх
варіантів (міграція `035` додає цей перерахунок у ту саму транзакцію, поруч із
`UPDATE`). Колонки свідомо немає в `STORE_PATCH_COLUMNS` — саме це робить її
недоступною власницькому `PATCH /store`, який до того ж відповідає 400 на
`vertical` у тілі.

### Модуль вертикалі

Клієнтський id — `vertical-<id>`. `vertical-clothing` **вбудований** у застосунок
(див. §3), решта приїжджає онлайн-модулем через `pos_stores.module_remotes`, як
`tiktok-live`. Правило `assertSingleVerticalRemote` (`src/pos/core/modules.ts`,
близнюк `assertSingleFiscalRemote`): не більше одного запису `vertical-*`, і він
має збігатися з колонкою. Інакше каса завантажила б модуль, якого екран продажу
ніколи не спитає. `vertical-clothing` заборонений як запис узагалі — це fallback,
і магазин не повинен мати способу його втратити.

## 3. Екран продажу — слот, а не маршрут

`/register` лишається за вбудованим core-модулем `catalog-checkout`. Його
сторінка — **каркас**: кошик, оплата, обробка відмов ПРРО, екран успіху, друк
чека, скасування щойно пробитого. Каталог (теги-папки, пошук, сканер, плитки,
вибір варіанта) постачає активна вертикаль через `ModuleDescriptor.sales.Catalog`
— за зразком `ModuleDescriptor.offline`: модуль сам себе не реєструє, він дані,
які читає хост.

Чому не «вертикаль володіє маршрутом `/register`»:

- `/register` зашито в хості тричі (`homePath`, редірект `Guard`, fallback
  індексу `/admin`);
- колізії root-маршрутів вирішуються мовчки порядком масиву — bundled завжди
  перемагає remote;
- **веб не рендерить заглушку** для невдалого online-only модуля: ні пункту меню,
  ні маршруту. Магазин, чий єдиний екран продажу — remote, при недоступному CDN
  лишився б без каси;
- оплату, чек і ПРРО довелося б експортувати з платформи.

Резолвер бере `vertical-<store.vertical>` серед `allModules()`; якщо його немає,
він ще не завантажений (`pending`) або впав при рендері — каталог береться з
`vertical-clothing`. Тобто каса продає завжди.

## 4. Атрибути й одиниці (фаза 2)

`pos_variants.size/color` → `attributes jsonb` + похідна збережена `label` +
`unit`. `label` перераховується сервісом на кожному записі варіанта, тому пошук,
`ORDER BY`, звіти складу й дедуп плейсхолдерів працюють по звичайній колонці.
Міграція `035` заповнює обидві точно сьогоднішнім правилом одягу
(`concat_ws(' / ', color, size)`), тож жоден наявний магазин не побачить іншого
підпису; `036` прибирає старі колонки вже після деплою.

`quantity` лишається INTEGER у базовій одиниці (250 г = 250). Це навмисно:
`quantityMilli` у ПРРО, `i64` у Rust-друку і виведення знижки в payload Checkbox
розраховані на цілі одиниці. Дробові кількості (NUMERIC) — окрема майбутня
робота, не потрібна ні квітам (стебла), ні першій ітерації кафе.

## 5. Готовність до наступних вертикалей

Квіти (букет = квіти + витратні, авто-списання при продажу) і кафе (техкарта з
інгредієнтів, модифікатори) потребують **одного й того самого** механізму —
складеного товару з компонентами, що списуються. Механізм побудовано у фазі
6a (міграція `037`, `src/pos/composites.service.ts`) — див. §7e. Кафе
відрізнятиметься лише вкладеністю (напівфабрикат усередині страви), яка зараз
свідомо заборонена.

## 6. Як додати вертикаль

1. `src/pos/verticals/<id>.ts` — визначення; додати в `BUILT_IN`
   (`src/pos/verticals/index.ts`).
2. `pos/src/types.ts` `VerticalId` + `pos/src/lib/vertical.ts` `VERTICAL_OPTIONS`
   (паритет пінить `pos/src/lib/vertical.test.ts`).
3. Модуль `pos/src/modules/vertical-<id>/` з `sales.Catalog`, `remote-entry.ts`,
   `lib/hostPlatform.ts`; `pos/vite.vertical-<id>-remote.config.ts`; скрипти
   `build:`/`serve:`/`check:…-css-coverage` у `pos/package.json`.
4. Seed (`src/pos/seed.ts`, opt-in через env) і e2e за зразком
   `pos/e2e/stocktake.spec.ts`.
5. Супер-адмін: тип магазину + запис `vertical-<id>` у `module_remotes`.

## 7d. Фаза 5 — що саме лишилося

`migrations/036_pos_drop_variant_size_color.sql` **написано, але свідомо не
додано до `POS_MIGRATIONS`** (`src/pos/migrations.ts`). Це не недогляд:

- міграції накочуються **до** того, як піднімається новий образ. У вікні між
  ними старий бекенд 1.x усе ще виконує `SELECT v.size, v.color` і пише їх при
  кожному редагуванні варіанта;
- саме тому `035` тільки додає колонки — щоб те вікно було нешкідливим. Якщо
  зареєструвати `036` у тому самому релізі, він впаде в те саме вікно і кожен
  запит каталогу поверне 500, поки новий образ не підніметься.

Порядок такий:
1. Задеплоїти поточну гілку (міграції `034`+`035`, бекенд і клієнт 2.0.0).
2. Переконатися, що прод працює на новому образі.
3. **Наступним** релізом: додати `'036_pos_drop_variant_size_color.sql'` у
   `POS_MIGRATIONS`, задеплоїти. Він повторює backfill (ловить рядки, які
   старий бекенд міг записати між кроками) і лише потім робить DROP.
4. Реліз `pos-release` з `bump: major` → 2.0.0; далі `module-release` для
   `stocktake`, `tiktok-live`, `fiscal-checkbox`, `vertical-flowers` і
   `POST /super/module-remotes/repoint` для кожного магазину — збірки 1.x
   читають `item.size` і показуватимуть самі назви товарів.

## 7e. Що вже лежить (фаза 6a)

Складений товар — це варіант, зібраний з інших варіантів. Де лежить його
залишок, каже `pos_products.stock_mode` (міграція `037`):

- **`own`** — зібрали заздалегідь, рахується на власному рядку `pos_stock`.
  Продаж такого **не чіпає** компонентів: їх уже списав документ виробництва.
- **`derived`** — збирається в мить продажу. Власного залишку немає: доступність
  рахується з компонентів, продаж списує компоненти.

Обидва режими одразу, бо флорист тримає обидва водночас: готові букети в
холодильнику й такі самі букети «на замовлення» з тієї ж картки каталогу.

Склад висить на **варіанті**, а не на товарі: букет S / M / L — це один товар,
розміри якого відрізняються саме кількістю стебел.

### Правило, на якому все тримається

Те, що продаж **фактично** списав, зберігається у `pos_sale_item_components`
(на **одну** одиницю складеного, тому часткове повернення — точна арифметика).
Скасування й повернення відмотують **цей знімок**, а не поточний рецепт. Причини
дві:

1. рецепт редагується. Букет, повернутий через тиждень після того, як флорист
   переробив його з 5 стебел на 9, інакше повернув би на склад чотири троянди,
   яких у ньому ніколи не було;
2. букет, зібраний на касі «на льоту» (фаза 6c), **не має** рецепту в каталозі —
   єдине місце, де існує його склад, це сам чек.

Наявність рядків знімка — ще й сигнал: відмотування ніколи не дивиться на
`stock_mode`, тому списання і повернення не можуть розійтися.

### Що заборонено на запис (і чому)

- компонент не може сам бути складеним — це робить цикли неможливими без
  рекурсивної перевірки; вкладені напівфабрикати — фаза кафе;
- `derived` без складу — продавав би товар із повітря;
- `derived` із власним залишком на старті — залишок, якого ніхто ніколи не
  побачить;
- перехід у `derived`, поки на полиці є залишок, і перехід у `simple`, поки
  склад не очищено — обидва мовчки губили б дані, тож це рішення власника.

### Відоме обмеження

Повернення похідного букета повертає компоненти на склад. Фізично зібраний букет
назад на стебла не розбереш — але арифметика має зійтися, а магазин, який
повернений букет викидає, оформлює на нього списання. Скасування чека (void)
таким питанням не є взагалі: його роблять за секунди до збирання.

## 7f. Документ виробництва (фаза 6b, бекенд)

П'ятий тип складського документа — `production` (префікс `ВР`, міграція `038`,
яка лише розширює CHECK). Це друга половина `stock_mode='own'`: флористка зранку
збирає десять букетів, і кожен забирає стебла з полиці й кладе на неї зібраний
букет. Далі продаж такого букета — звичайний рух власного залишку, який
компонентів **не чіпає** (їх уже забрало виробництво).

- рядки документа називають **тільки** вироблений складений товар; списання
  компонентів виводиться зі складу при проведенні (`produceComposite`);
- собівартість зібраного — сума собівартостей компонентів. Її ніхто не вводить
  руками: введена перезаписалась би, тож `addLine` її й не приймає;
- рядок на похідний складений або на простий товар відхиляється **при
  додаванні**, а не при проведенні: власник має дізнатися про помилку, поки
  чернетка ще на екрані;
- сторнування відмотує **записані рухи** (`pos_stock_movements` за цим
  документом), а не сьогоднішній рецепт — те саме правило, що й у повернення
  чека, і з тієї ж причини. Стебла повертаються `receipt`, букети йдуть
  `writeoff`, тож звіт руху сходиться по причинах;
- якщо частину букетів уже продали, сторнування падає на «Insufficient stock» і
  відкочується цілком — розібрати назад те, що поїхало з магазину, не можна.

## 7g. Адмінка складених товарів (фаза 6b, клієнт)

- **Картка товару** (`pos/src/modules/products/`): у формі створення зʼявився
  вибір «Що це за товар» — звичайний / складений «збирається при продажу» /
  складений «збираємо заздалегідь». Для складеного під кожним варіантом стоїть
  `CompositionEditor`; у похідного поле «Залишок» замінене поясненням, бо
  власного залишку в нього немає. У списку товарів складений має бейдж, а
  колонка «Залишок» для похідного читається «Можна зібрати».
- **Склад** пропонує складники з `componentOptions` — усі активні варіанти
  товарів, які самі **не** складені (те саме правило одного рівня, що й на
  сервері, тож цикли неможливі), мінус сам товар, який редагують. Редагується й
  зберігається **цілком**, як і мішок атрибутів: інакше «прибрати складник» не
  виражалося б.
- **Екран виробництва** (`/admin/stock/production`, модуль `stock`) — свій, а не
  ще один `type` у `StockActionPage`: вибір іде не з усього каталогу, а лише з
  того, що магазин збирає заздалегідь, і на екрані потрібні склад і «чи
  вистачить», про що редактор рядків приходу нічого не знає. Похідний букет у
  списку не зʼявляється взагалі.

## 7h. Букет «на льоту» (фаза 6c, бекенд)

Рядок чека може нести **власний** склад: `CompleteSaleItemInput.components`.
Це букет, який касир зібрав біля прилавка — картка каталогу («Букет на
замовлення») є, а рецепт у неї лише типовий.

Механізм той самий, що й у каталожного букета, тому нижче по течії нічого не
змінилося: склад рядка перевіряється тими самими правилами
(`validateComponents`, спільний із редактором каталогу), лягає в
`pos_sale_item_components` і звідти ж відмотується при поверненні. Єдине місце,
де взагалі існує рецепт такого букета, — сам чек; саме тому фаза 6a поклала
знімок туди.

Три речі, які тут легко зробити навпаки:

1. **Рядок зі складом не зливається** з іншим рядком того самого варіанта.
   Звичайні рядки, як і раніше, зводяться по `variant_id`; два букети «на
   замовлення» з однієї картки — це два різні букети, і злиття викинуло б один
   із двох рецептів.
2. **Ціну рахує сервер**: сума цін складників × кількість. Її ніхто не надсилає —
   ціна рядка, яку касир задає вільно, це діра, якої не видно в жодному чеку.
   Флорист і так рахує по стеблу, а справжня знижка виражається звичайними
   знижками на рядок і на кошик.
3. Власний склад приймає **тільки** похідний складений товар. У зібраного
   заздалегідь уже є свій залишок, а простому товару нема що збирати.

`GET /sales/:id` тепер віддає `items[].components` — для каталожного букета це
зручність, для «на льоту» єдине джерело.

Обидва додатки адитивні на дроті, тож `POS_API_VERSION` лишається 2.

## 7i. Демо-магазин квітів (міграція 039)

Магазин `demo-flowers` — це **дані в міграції**, а не сид: він має приїхати з
деплоєм, а не з тим, хто згадає запустити `pos:seed`.

Що всередині: 16 товарів-стебел і зелені на **20 варіантів**, 3 витратні
матеріали, 5 букетів (2 зібрані заздалегідь — `own`, 3 збираються при продажу —
`derived`), 5 міток із рядком категорій і два **проведені документи
виробництва**, якими зібрані букети справді забрали свої стебла з полиці.
Тому арифметика демо сходиться: залишок стебла = завезено − пішло в холодильник.

Три рішення, які варто знати:

- **Картинки** — плоскі SVG у `public/demo-flowers/` (перегенерувати:
  `node scripts/gen-demo-flowers.mjs public/demo-flowers`). `public/` уже
  роздається з `/`, тож вони їдуть усередині образу: не потрібен ні том для
  завантажень, ні 90 КБ base64 у міграції. Це ілюстрації, не фотографії —
  ліцензувати нічого. Справжнє фото власник завантажує в картці товару.
- **`module_remotes` міграція не пише.** URL бандла — це рішення деплою, а не
  дані: `localhost:5007` у кожній базі відправив би бойові каси шукати модуль на
  машині касира. Локально його ставить `POS_SEED_VERTICAL_FLOWERS=1 npm run
  pos:seed` (тепер це лише `registerFlowersModule`), у проді — супер-адмін.
- **Підписи варіантів написані руками**, бо SQL не може викликати `labelOf`.
  Захист подвійний: склад букетів шукається за цим самим підписом, тож
  розʼїхавшись, міграція падає з явним `RAISE EXCEPTION` про те, якої саме
  частини не знайшлося; а `src/__tests__/pos.demo-flowers.test.ts` перевіряє
  кожен підпис через справжнє правило вертикалі.

⚠ Міграція вставляє **демо-дані в кожну базу**, куди її накотять, включно з
продом, і створює реальні логіни з відомими паролями
(`owner@flowers.shop` / `owner123`, PIN 0000 і 1234). Вони бачать лише свій
магазин, але це справжні акаунти. Прибрати:
`DELETE FROM pos_stores WHERE slug = 'demo-flowers';` — решта каскадиться.
Повторний запуск нічого не дублює: блок виходить, якщо магазин уже є.

## 8. Ланцюг даних (де шукати при правках)

`pos_stores.vertical` → `core/auth.ts getAuthByToken` (явний SELECT) →
`PosAuthContext.vertical` → `auth.service.ts toAuthResponse` →
`AuthResponse.store.vertical` → `pos/src/types.ts` (optional: старий кеш) →
`offline/db.ts StaffUnlockRow.vertical` (неіндексоване — без Dexie-bump) →
`offline/auth-local.ts` (`saveStaffUnlock`, `updateStaffUnlockStoreFlags`,
`sessionFromUnlock` → `DEFAULT_VERTICAL`). Плюс `GET /store` через
`analytics.service.ts mapStore`.

Каса, якій змінили вертикаль, поки вона офлайн, продає на закешованій до
наступного онлайн-логіну; далі `useAuthStore` перерезолвить слот без
перезавантаження, а зміну `module_remotes` підхопить наявний банер
«Перезавантажити».
