# Роль «Маркетолог»: меню, столи й QR-меню без доступу до грошей

Дизайн-док і **точка відновлення** треку МР (фази МР0–МР4, таблиця в §6).

Запит власника від 2026-11-07 виник у «Шаблі» (`shablya`, вертикаль café + модуль `tables`). Закладу потрібна
людина, яка веде меню й QR-меню, але не бачить виторгу, складу, ПРРО й співробітників. Що їй треба:

1. **Каталог.** Назва, опис, фото, ціни, порції (варіанти), галочки для гостя: алергени, позначки
   («Хіт», «Новинка»…), склад, калорії й інші цифри, «Не показувати в QR-меню». Поки що — усі поля картки,
   зайві приберемо потім.
2. **Столи.** Редагувати зали й столи й друкувати наклейки з QR.
3. **Налаштування — лише QR-меню:** публікація й адреса меню, профіль закладу (логотип, адреса, години,
   соцмережі), корковий збір, збір відгуків «і так далі».
4. **Вхід за PIN, як у касира, але одразу в кабінет.**
5. **Роль несе вертикаль café** — у бутику чи квітковому її немає.

Рішення власника зібрано в §5 (з нашою рекомендацією до кожного); вгадувати їх не можна. Кожна фаза коду
отримує свій затверджений план і свій PR.

## 1. Що є зараз (розвідка коду 2026-11-07)

### 1.1 Ролі

- Ролей дві: `'owner' | 'seller'`. Сервер — `src/pos/types.ts:14` (`PosRole`), база —
  `migrations/002_pos_schema.sql:25`, вбудований безіменний CHECK (Postgres називає його
  `pos_staff_role_check`; жодна пізніша міграція його не чіпає). Клієнт — `pos/src/types.ts:5`, офлайн —
  `pos/src/offline/db.ts:36`.
- Роль **не лежить у сесії**: `getAuthByToken` (`src/pos/core/auth.ts:45`) щоразу читає `pos_staff.role`.
  Змінена роль діє з наступного запиту.
- Вхід за PIN (`attemptPinLogin`, `src/pos/auth.service.ts:228`) бере **першого** активного співробітника,
  чий хеш збігся: без фільтра ролі й без `ORDER BY`. Двох людей з одним PIN ніщо не забороняє.
- Власник теж може увійти за PIN. На вебі його тоді веде на `/register` (`pos/src/pages/LoginPage.tsx:108`).
- Співробітника створює лише `createSeller` (`auth.service.ts:321`). Роль там жорстко `'seller'`, а
  `POST /staff` приймає тільки `{display_name, pin}`. `setStaffActive` вимикає тільки `role = 'seller'`.

### 1.2 Охоронці на сервері

- `ensurePosAuth` — будь-який співробітник. `ensurePosOwner` — `role !== 'owner'` → 403.
  `ensureModule(id, {owner?})` — те саме плюс 404, якщо модуль вимкнено. Інших перевірок ролі, крім двох
  дрібних (знижка покупця, `chain_parked`), немає.
- Кожна поверхня з запиту зараз **лише для власника**:
  - товари, фото (`POST /uploads`), варіанти, теги, модифікатори, техкарти, уцінки —
    `ensureModule('products', {owner: true})` (`products.routes.ts`, `modifiers.routes.ts`);
  - зали й столи — `ensurePosOwner` (`tables.routes.ts:174–244`); `GET /halls` і всі `/bills*` — для
    будь-кого;
  - `GET/PATCH /store/public-menu`, `…/rotate`, `GET/PATCH /store/profile`, `POST /store/logo` —
    `ensurePosOwner` (`public-menu.routes.ts`);
  - відгуки `GET /feedback*`, `…/handled` — власник; «Бачу» офіціанта — будь-хто.
- Підписане посилання для друку QR із ключами столів (`?p=`, 6 год) видає **лише** `GET /store/public-menu`
  у полі `print`. Без нього друкуються QR без ключів (гість бачить меню, але не свій рахунок і не замовляє).
- `GET /store` відкритий будь-якому співробітнику й віддає всю таблицю магазину, включно з IBAN/ЄДРПОУ для
  QR-оплати.
- API товарів віддає закупівельну ціну (`cost_cents`) і залишок, а `PATCH /variants/:id` змінює й ціну
  закупівлі.

### 1.3 Клієнт

- Єдиний перемикач — `ModuleDescriptor.ownerOnly` (`pos/src/modules/types.ts:261`). Плюс **увесь `/admin`
  обгорнуто в `<Guard ownerOnly>`** (`pos/src/modules/renderRoutes.tsx:163`), що б не казав модуль.
- `homePath`: власник на вебі → `/admin`, решта → `/register`.
- Сторінки, які потрібні маркетологу, розкидано по модулях: `products` (owner-only: товари, модифікатори,
  техкарти, уцінки), `settings` (owner-only: `/admin/settings` і `/admin/appearance`), `analytics`
  (owner-only: головна `/admin` — це **грошова** панель «Сьогодні», і там само `/admin/reviews`), `tables`
  (віддалений модуль; редактор залів `HallEditorPage` закритий тільки обгорткою `/admin`).
- `SettingsPage.tsx` — одна велика форма: назва, QR-оплата, GTIN, друк, заокруглення, ПРРО, `PublicMenuCard`
  і `StoreProfileCard` (лише для café), TikTok LIVE, модулі. Обидві картки QR-меню ховаються самі на 403.
- `AdminLayout` на кожній сторінці тягне `/fiscal/attention`, передзамовлення, каталог і «мало на складі».
- `navOverrides.ts:88` перебирає ролі жорстким списком `['owner','seller']`.
- Офлайн-вхід десктопа (`pos/src/offline/auth-local.ts`) кешує роль і перевіряє PIN без фільтра ролі.

### 1.4 Вертикаль

`VerticalDefinition` нічого рольового не має. «Ресторан» — це `cafe` + модуль `tables`; кухня — `kitchen: true`
лише в `cafe`, на дроті `dishFacts`.

## 2. Задум

Нова роль **`marketer`** («Маркетолог»). Головне правило: **за замовчуванням маркетологу заборонено все**,
а маршрути, які йому потрібні, дозволяють його явно. Інакше він отримав би всі 72 маршрути
`ensurePosAuth` — пробивати продажі, відкривати рахунки, рахувати склад, читати IBAN — просто викликавши API
своїм токеном.

### 2.1 Сервер

- **Міграція `098`**: розширити CHECK `pos_staff.role` до `('owner','seller','marketer')` (`DROP CONSTRAINT IF
  EXISTS pos_staff_role_check` + `ADD`; файл перезапускається на кожному старті, тож він ідемпотентний).
  `002` CHECK не перевидає (`CREATE TABLE IF NOT EXISTS`), тож пастки «дві міграції додають одне обмеження»
  тут немає — тест повторного прогону це підтвердить.
- **`src/pos/core/roles.ts`** — одна таблиця «роль → можливості»:
  `owner` — усе; `seller` — як зараз (усе, що `ensurePosAuth`); `marketer` — лише
  `menu.catalog`, `menu.tables`, `menu.public`, `menu.feedback` (точний склад — рішення М4–М8).
- **Охоронці.** `ensurePosAuth(req, reply, { allow?: Capability })`: маркетолог проходить **лише** там, де
  маршрут назвав можливість, яка в нього є; інакше 403 «Маркетолог працює лише з меню». Те саме для
  `ensurePosOwner` і `ensureModule(..., { owner: true, allow })`: власник як завжди, маркетолог — якщо `allow`.
  Продавця це не чіпає.
- **Що відкривається маркетологу** (за рекомендаціями §5):
  - `GET /me`, `GET /catalog`, `GET /tags`, `GET /halls` — так (вони вже для будь-кого, тепер — з `allow`);
    стоп-лист `POST /kitchen/stop-list/:id` — ні (М6);
  - товари: список і картка, створення, зміна, фото, варіанти (ціна, порція, штрихкод), теги, модифікатори,
    архів/повернення — **без** техкарт, уцінок, імпорту техкарт і без закупівельної ціни й залишку (М4):
    сервер вирізає `cost_cents`/залишок з відповіді й відмовляє на їх зміну;
  - зали й столи: `GET/POST/PATCH/DELETE /halls*`, `/tables*`, `PATCH /tables/positions`;
  - QR-меню: `GET/PATCH /store/public-menu` (без `…/rotate` і, можливо, без частини перемикачів — М5),
    `GET/PATCH /store/profile`, `POST /store/logo`; поле `print` у відповіді — йому теж;
  - відгуки: `GET /feedback*`, `…/handled` — без телефону гостя (М7).
- **Вертикаль несе роль.** `VerticalDefinition.staffRoles: readonly StaffRole[]` (`cafe`: `['marketer']`,
  решта — `[]`), на дроті `VerticalPublicConfig.staffRoles`. Сервер відмовляє створити маркетолога в магазині,
  чия вертикаль його не має, і відмовляє маркетологу у вході, якщо вертикаль змінили (М3).
- **Співробітники.** `POST /staff { display_name, pin, role? }` (`role` — `seller` за замовчуванням або роль з
  `staffRoles` вертикалі); `setStaffActive` — для всіх, крім власника; `PATCH /staff/:id { role }` між
  продавцем і маркетологом (М9).
- **PIN унікальний у магазині.** Створення й зміна PIN відмовляють, якщо такий PIN уже має інший активний
  співробітник (порівняння з хешами — людей у закладі одиниці). Без цього продавець і маркетолог з одним
  PIN входили б випадковою роллю. Наявні дублікати не чіпаємо, але вхід бере їх у сталому порядку
  (`ORDER BY id`).

### 2.2 Клієнт (хост)

- `PosRole` += `'marketer'`. `Guard` приймає `roles`; обгортка `/admin` пускає власника й маркетолога, а
  кожна сторінка — лише якщо її модуль/маршрут дозволяє роль: `ModuleDescriptor.roles?` (за замовчуванням
  `ownerOnly` → `['owner']`, інакше всі, крім маркетолога) і `roles?` на окремому маршруті й пункті меню.
- `homePath(marketer)` = `/admin/products`; головна `/admin` (грошова панель) для нього перенаправляє туди.
- **Вхід.** Вкладка «Продавець · PIN» після входу йде за `homePath(role)`, а не завжди на `/register`. На
  пристрої без запам'ятованого коду магазину вкладка просить код (зараз відкривається лише вкладка власника).
- **Меню кабінету маркетолога:** Товари, Модифікатори, Столи, QR-меню, Відгуки. Немає посилання «Каса».
  `AdminLayout` не тягне для нього ПРРО, передзамовлення й склад.
- **Товари.** Ті самі сторінки; для маркетолога сховано закупівельну ціну, залишок, техкарти, уцінки, друк
  цінників — те, що сервер йому однаково не віддасть.
- **«QR-меню»** — нова сторінка `/admin/qr-menu` у модулі `settings` для власника й маркетолога:
  `PublicMenuCard`, `StoreProfileCard` (з корковим збором), перемикач відгуків. У власника ці картки
  лишаються й у «Налаштуваннях» (або переїжджають — М10).
- **Відгуки** `/admin/reviews` — маршрут дозволяє маркетолога; головна analytics — ні.
- **Співробітники.** Власник обирає роль «Продавець» / «Маркетолог» (другу — лише там, де вертикаль її несе)
  і бачить роль у списку.
- **Десктоп і планшет.** Маркетолог працює тільки у веб-кабінеті: каса й планшет офіціанта відмовляють йому
  у вході словами («Маркетолог працює у веб-кабінеті: pos.the-live.shop») і не кешують його PIN для офлайну.
- `navOverrides.ts` перебирає три ролі.

### 2.3 Модуль `tables`

Редактор залів живе у віддаленому модулі. Його адмін-маршрут має сказати, що маркетолог дозволений
(`roles: ['owner','marketer']`), тож потрібен **Module Release `tables`**. Старий бандл поля не має — тоді
маркетолог просто не бачить «Столи», нічого не ламається. Новий символ хоста не потрібен: поле опційне,
`PLATFORM_VERSION` лишається 23 (перевіримо `platform:snapshot`).

## 3. Що свідомо поза треком

- Журнал «хто що змінив у меню» (у товарах немає автора змін) — окремо, якщо попросять.
- Тонке налаштування прав власником (галочки по кожному розділу) — ні: одна фіксована роль простіша й
  зрозуміліша. Склад прав міняємо в `roles.ts`, коли власник скаже «приберіть ось це».
- Маркетолог в інших вертикалях — ні (вимога власника), але `staffRoles` дозволить додати одним рядком.

## 4. Безпека

- PIN із 4 цифр тепер відкриває кабінет, а не лише касу. Захист від підбору вже є (`pos_stores.pin_*`:
  5 промахів — блок, 10-й — година, `TechDocs/POS_PIN_ATTEMPTS.md`), і він на магазин, тож перебір PIN
  маркетолога блокує й касирів — як і зараз для перебору будь-якого PIN. Пропонуємо для маркетолога PIN
  **від 6 цифр** (М2).
- Заборона за замовчуванням (§2.1) — головний запобіжник: нові маршрути автоматично закриті для маркетолога.
  Тест обходить усі зареєстровані маршрути Fastify токеном маркетолога і перевіряє, що відкриті лише ті, що
  в білому списку.

|---|---|---|
| М1 | Назва ролі в інтерфейсі | «Маркетолог» |
| М2 | Довжина PIN маркетолога | Від 6 цифр (у продавця лишається 4) |
| М3 | Вертикаль змінили з café на іншу, а маркетолог лишився | Вхід відмовляє словами; власник бачить його в «Співробітниках» і може вимкнути |
| М4 | Закупівельна ціна, залишок, техкарти (фудкост), уцінки | Не показувати й не давати змінювати. Ціни продажу, порції, усі поля для гостя — так |
| М5 | Перемикачі QR-меню | Маркетолог: опублікувати меню, коротка адреса, рахунок для гостя, відгуки, профіль, корковий збір. **Лише власник:** замовлення з телефону, «одразу на кухню» й ліміт, виклик офіціанта (це робота залу, а «одразу на кухню» вимагає підтвердження ризиків від власника), нове посилання меню (`rotate` робить недійсними всі надруковані QR) |
| М6 | Стоп-лист | Ні: це робота кухні, на касі він уже є |
| М7 | Відгуки | Читати й позначати «опрацьовано» — так, але без телефону гостя |
| М8 | Архівувати товар | Так (поряд є «Не показувати в QR-меню», але прибрати страву з меню взагалі — теж робота з меню) |
| М9 | Міняти роль наявного співробітника | Так, між продавцем і маркетологом; власника — ні |
| М10 | Картки QR-меню у власника | Окрема сторінка «QR-меню» для обох; у «Налаштуваннях» власника лишити посилання на неї замість карток |
