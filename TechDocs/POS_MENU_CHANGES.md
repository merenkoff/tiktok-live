# Історія змін меню — хто що змінив

Запит власника 2026-11-12 (після ролі «Маркетолог», `POS_MARKETER_ROLE.md` §3 — там цей журнал був
записаний як «окремо, якщо попросять»). Меню тепер змінює не лише власник: маркетолог, а продавець —
мітки. Власник має бачити, хто й коли змінив ціну, опис чи алергени.

## 1. Що записується

Один рядок `pos_menu_changes` (міграція `101`) на кожен запис, що змінив меню:

| Що | Маршрути |
|---|---|
| Картка товару | `POST /products`, `PATCH /products/:id`, `POST /products/:id/archive`, `…/restore` |
| Варіанти | `POST /products/:id/variants`, `…/variants/batch`, `PATCH /variants/:id`, `POST /variants/:id/archive` |
| Мітки товару | `PUT /products/:id/tags`, `POST /tags/:id/assign` (рядок на кожен товар) |
| Модифікатори товару | `PUT /products/:id/modifier-groups` |
| Група модифікаторів | `POST`/`PATCH`/`DELETE /modifier-groups…`, `POST /modifier-groups/:id/modifiers`, `PATCH`/`DELETE /modifiers/:id` |

У рядку: хто (`staff_id`, а ще ім'я й роль, як вони були тоді — рядок лишається читабельним, коли
людину видалили), коли, дія (`create` / `update` / `archive` / `restore` / `delete`), назва й список
змін `{ field, variant?, from?, to? }`.

## 2. Правила

- **Різницю рахує сервер** (`src/pos/menu-changes.ts`, `diffProduct` / `diffGroup`): маршрут читає картку
  до запису і після, і порівнює. Клієнт не каже, що змінив, тож журнал показує те, що лежить у базі,
  хоч би з якого екрана й ким було записано.
- **Не зміни меню:** залишки (рухаються з кожним продажем), стоп-лист (день кухні), `needs_review`,
  часові мітки. Запис, що нічого не змінив, не пише рядка.
- **Журнал ніколи не ламає запис.** Помилка читання чи вставки — лише `logger.warn`.
- **Мітки й модифікатори — назвами**, які були в момент запису (`loadProductNames`), бо мітку можуть
  видалити.
- **Читає лише власник:** `GET /api/pos/menu-changes?entity=&entity_id=&limit=&offset=` (`products`,
  `owner: true`). У рядках є закупівельна ціна й імена співробітників, тому маркетологу й продавцю — 403
  (маршрут без `allow`, тест-обхід `pos.marketer.test.ts` це й тримає).
- `listProducts(storeId, onlyIds?)` — щоб журнал читав одну картку, а не весь каталог двічі.

## 3. Чого свідомо немає

- Уцінки (`/markdowns`) — у них свій журнал (`pos_markdowns` + знімок до/після), тут їх не дублюємо.
- Змін, зроблених міграціями чи суперадміном (імпорт ChoiceQR, імпорт техкарт) — вони не проходять через
  ці маршрути. Імпорт техкарт можна додати, якщо попросять.
- Відкату «повернути як було» — журнал лише показує.
- Зберігання без обмеження: рядки малі; чистку можна додати, коли знадобиться.

## 4. Клієнт

Хостовий модуль `products` через `api.posRequest` (платформа не змінилась):

- `/admin/products/history` — «Історія змін меню» всього магазину або однієї картки (`?product=<id>`),
  «Показати ще» по 50; кнопка «Історія змін» на списку товарів (не для маркетолога).
- Картка товару — блок «Історія змін» під формою: 5 останніх і «Уся історія»; перечитується після
  кожного збереження. Мовчить, якщо сервер старіший або запит не вдався.
- Слова — `lib/menuChangeWords.ts` (поле → підпис, копійки → «60,00 ₴», коди алергенів і позначок →
  назви, невідоме поле — як є).
