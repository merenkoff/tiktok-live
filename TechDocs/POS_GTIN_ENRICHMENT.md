## 1. Продуктові правила

| Правило | Деталі |
|--------|--------|
| Лише **підказка** | Prefill `name` у формі заглушки; юзер може змінити / очистити |
| Не блокує | Немає в базі / офлайн / ліміт → тиха форма |
| Не auto-create | Товар у каталог тільки після «Провести» |
| Кеш без TTL | `filled_at` / `updated_at`; замість eviction за часом — ручне очищення власником (§6) |
| Ручна правка липка | `manual` — найвищий пріоритет; автоматичний пошук її не перезаписує |
| Feature flag | `pos_stores.gtin_lookup_enabled` default **true** |

### Ключ кеша — канонічний GTIN-14

`pos_gtin_cache.gtin` — це **GTIN-14, доповнений нулями зліва**. Доповнення нулями не
змінює контрольну цифру, тому всі представлення одного товару (`4820000000017` EAN-13,
`04820000000017` GTIN-14, UPC-A, EAN-8) лягають в **один** рядок. Справжня
indicator-цифра (`14820000000014` — ящик того ж товару) лишається окремим кодом.

`normalizeGtin` повертає обидві форми:

| Поле | Що це | Де вживається |
|---|---|---|
| `canonical` | GTIN-14 | ключ кеша, `pos_gtin_lookup_events.gtin` |
| `display` | коротка форма (EAN-8 / EAN-13 / GTIN-14) | URL зовнішніх провайдерів, показ користувачу |

До міграції `018` ключем була змішана форма, і один товар міг лежати в кеші двічі.
Ремонт живе у функції `pos_gtin_canonicalize()` — ідемпотентна, її можна викликати
повторно на будь-якій базі.

## 2. Реалізовані джерела

| Джерело | Як | Квота | Бакет `pos_gtin_provider_budget` |
|---------|-----|--------|---|
| Власний `pos_gtin_cache` | server | ∞ | — |
| Open Products / Food / Beauty Facts | **клієнт** (CORS `*`) | 1 скан ≈ 1 req | — |
| UPCitemdb trial | **server** proxy | 100/день на IP | `shared` — один на деплой |
| [upc.dev](https://upc.dev/) Free | **server** + `UPC_DEV_API_KEY` | 100/день на ключ | `key:<sha256[..16]>` — свій у кожного ключа |

Лічильник ключується тим, що тарифікує **провайдер**, а не `store_id`: два
магазини на спільному `UPC_DEV_API_KEY` справді ділять одну квоту вгорі. Слот
резервується до запиту (щоб конкурентні lookup-и не проскочили ліміт) і
повертається, якщо запит не долетів — таймаут, обрив, `5xx`. На `4xx` не
повертається: `429` означає, що квоту витрачено, `401/403` — що ключ хибний.

UPCitemdb **немає** CORS для наших origin — клієнтські квоти для нього неможливі без proxy.

## 4. Flow

```
скан/EAN у stub
  → GET cache
  → parallel Open*Facts (browser) → POST ingest
  → POST quota-providers (upcitemdb ∥ upc_dev)
  → miss → ручна назва
```

Merge priority (default):  
`manual` > `open_products_facts` > `upc_dev` > `upcitemdb` > `open_beauty_facts` > `open_food_facts`  
Override: `GTIN_SOURCE_PRIORITY` (якщо в переліку немає `manual`, він додається першим).

`manual` веде свідомо: назву, яку набрала людина з товаром у руках, наступний
автоматичний пошук перезаписувати не має права. Раніше `manual` стояв **останнім**,
і виправлення касира жило рівно до наступного скану того ж штрихкоду.

Merge атомарний: `ingestGtinResults` — один `INSERT … ON CONFLICT (gtin) DO UPDATE`,
де умова `INCOMING_WINS` повторює `isBetterCandidate` проти збереженого рядка, а
перелік пріоритетів їде в SQL масивом, щоб `GTIN_SOURCE_PRIORITY` лишався єдиним
джерелом правди. Без цього два одночасні lookup обидва читають до-стан, і виграє
той, що записав другим — тобто пріоритет вирішувався таймінгом. Гарантія зафіксована
в `src/__tests__/pos.gtin-concurrency.test.ts`.

## 5. Виправлення та очищення запису (owner)

Кеш **спільний для всіх магазинів** інсталяції, тож помилкова назва — помилкова для
всіх. Сторінка `/admin/gtin` (модуль `gtin-enrichment`, owner-only, web) дає:

| Дія | API | Що відбувається |
|---|---|---|
| Виправити | `PATCH /api/pos/gtin/:code` `{name, brand?}` | запис як `manual` → назва більше не перезаписується автоматично; знімає блок |
| Очистити | `DELETE /api/pos/gtin/:code` | **tombstone**: дані обнуляються, `blocked_at` виставляється |
| Розблокувати | `PATCH /api/pos/gtin/:code` `{blocked: false}` | автоджерела знову можуть наповнити запис |
| Знайти | `GET /api/pos/gtin/cache?q=&limit=&offset=&blocked=1` | пошук по штрихкоду (точний або підрядок) чи по назві/бренду |

Чому tombstone, а не `DELETE` рядка: після простого видалення наступний скан підтягнув
би з тих самих зовнішніх джерел ту саму помилкову назву. Заблокований рядок лишається,
і `ingestGtinResults` відмовляється його заповнювати (`WHERE blocked_at IS NULL` на
upsert-і) — це прикриває і скан, і
`learn/batch` (повертає `skipped: blocked`), і dump-seeding, бо всі три йдуть через
одну функцію.

`GET /gtin/:code` для заблокованого коду відповідає `200 {found:false, blocked:true}`,
а не `404` — клієнт має знати, що fan-out робити не треба, інакше він марно витратить
квоту провайдера.
