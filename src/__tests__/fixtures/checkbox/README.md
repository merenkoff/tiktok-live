# Реальные пары запрос/ответ Checkbox (снято 2026-09-09 на песочнице)

Снято вручную через `curl` против `api.checkbox.in.ua` на тестовом аккаунте
(`X-License-Key` начинается с `test`, `is_test: true` во всех ответах).
Not from the OpenAPI spec — the spec only documents shapes, not which HTTP
status/`code` each failure actually returns. Это то, ради чего фаза 2б
дожидалась песочницы.

Токены в `signin_success.json` — заглушки: реальный access_token, который
вернул sandbox, **не имеет `exp`-клейма** (см. находку ниже), поэтому не
коммитим рабочий bearer-токен навсегда в git.

## Находки, которые меняют дизайн адаптера

1. **`GET /cashier/shift` возвращает `null`**, когда смены нет — не только до
   первого открытия, но и **после закрытия**. Нет отдельного статуса
   `"CLOSED"` для уже закрытой смены, которую можно было бы прочитать полем
   `status`.
2. **Открытие и закрытие смены асинхронные.** `POST /shifts` → `202` со
   статусом `CREATED`; нужно поллить `GET /cashier/shift` до `"OPENED"`.
   `POST /shifts/close` → `202` со статусом `CLOSING`; конечное состояние —
   `null` от `GET /cashier/shift` (без промежуточного `"CLOSED"`, который можно
   было бы увидеть). В песочнице оба перехода уложились в ~2 c.
3. **Продажа чека тоже асинхронная.** `POST /receipts/sell` → `201` сразу,
   но `status: "CREATED"`, `fiscal_code: null`. Нужно поллить
   `GET /receipts/{id}` до `status: "DONE"` (тогда появляются `fiscal_code`,
   `tax_url`). В песочнице тоже уложилось в ~2 c.
4. **Большинство ошибок несут структурированный `code`**, не только
   свободный текст — спека боялась зря:
   - `receipt.already_exists` (400) — дубликат `id` чека
   - `shift.not_opened` (400) — продажа без открытой смены
   - `cashier.invalid_credentials` (403) — неверный PIN
   - `cash_register.invalid_license_key` (401) — неверний `X-License-Key`
   - `base.credentials` (401) — недействительний/просроченный bearer-токен
   - `validation.custom` (422) — единственный случай **без** машиночитаемого
     кода на верхнем уровне; детали — в массиве `detail[].loc`/`.type`
5. **`X-License-Key` обязателен почти на всех эндпоинтах**, не только на
   `signinPinCode` — его отсутствие само по себе даёт `422 validation.custom`
   ("Обов'язкове поле не заповнено").
6. **JWT `access_token` не содержит `exp`.** `auth_expired` (если он вообще
   наступает) не определяется декодированием токена на клиенте — нужно либо
   ловить его как обычный `401`, неотличимый от `auth_rejected` по коду
   (`base.credentials` на оба случая), либо искать другой сигнал.
7. **429 не удалось воспроизвести** шестью быстрыми подряд `receipts/sell` —
   организация тестового аккаунта сконфигурирована `receipts_ratelimit_count:
   3, receipts_ratelimit_interval: 1`, но это, похоже, троттлит *обработку*
   (переход `CREATED → DONE`), а не приём запроса (`POST` всё равно ответил
   `201`). Значит `rateLimit.ts`'ный **клиентский** лимитер (2 чека/сек, из
   wiki) остаётся единственной защитой от 429 — полагаться, что сам Checkbox
   мгновенно откажет лишний запрос, нельзя.
8. **`/cashier/tax` — per-organization.** У тестовой организации `is_vat:
   false`, поэтому единственный код — `8` («Без ПДВ»). Реальный магазин-
   плательщик НДС увидит больше кодов (20%, 7%, 0% и т.д.) — форма настроек
   обязана подтягивать список, а не захардкоживать один код.
