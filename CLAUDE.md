# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repo layout — three independent apps, one Postgres

This repo actually contains **three separately-deployed apps** that share one Postgres database:

- **root (`src/`)** — Fastify + TypeScript backend. Owns the DB, serves the REST/WebSocket API for both LIVE automation and POS. Deployed as its own Railway service. **One replica by design**: it mounts the uploads volume (`data/pos-uploads`) and Railway forbids replicas on a service with a volume, so every in-process cache, limiter and session map (guest menu cache, guest-order limits, super-admin login lock, ПРРО runtime, LIVE `sessionManager`) is correct as it stands; what would break with a second instance, and the order to fix it, is `TechDocs/POS_SINGLE_INSTANCE.md`. Production has no Redis (only local `docker-compose` does).
- **`admin/`** — React + Vite SPA for the TikTok LIVE side (session control, live logs). **Retired 2026-09-09**: its nickname-only login endpoint was removed and the login screen is now a notice pointing at the POS, whose `tiktok-live` module owns the broadcast desk (`/live`) and its settings (`/admin/live`). The code and its CI workflow stay; nothing can sign in. Talks to the root API.
- **`pos/`** — React + Vite SPA for the point of sale, with a Tauri 2 desktop shell for an offline cashier kiosk. Own `package.json`, no CI workflow yet. What a store sells is a per-store **vertical** (clothing, flowers, café — the restaurant is the café plus the `tables` module) — see "Sales verticals" below.
- **`site/`** — the marketing site at `the-live.shop` (React + Vite + Tailwind, statically prerendered). Not a fourth deployment: `Dockerfile` stage 1 builds it and the root API serves `site/dist` (`src/api.ts`). See "Marketing site" below.

Each of `admin/` and `pos/` has its own `node_modules`, `tsconfig.json`, and dev server — always `cd` into the subdirectory (or use `npm --prefix`) before running its scripts. Root `npm` scripts only touch `src/`.

```bash

npm run docker:deps                           # Postgres :5433 (nothing in src/ uses Redis)
npm run pos:migrate

```
Logins (`pos:seed` prints them): store `demo-cafe` + seller PIN `1234`, owner `owner@cafe.shop` / `owner123`.

Why a production build and not `npm run dev`: a runtime-loaded module (`vertical-*`, `tiktok-live`, …) resolves `@pos/platform` through the import map that only `dist/` has — under `vite dev` it is bundled through the alias. And why `build:local` and not `build`: `vite.platform-remote.config.ts` bakes `https://the-live.shop` into the shared `@pos/platform` chunk (where the axios client lives) unless `VITE_API_BASE` is set — right for the desktop cashier, wrong here: a plain `npm run build` produces a "local" POS that talks to **production**. `build:local` points it at `http://localhost:3002`, the origin `preview:local` serves, whose proxy forwards `/api` and `/pos-uploads` to :3000, so no CORS. Check what a build will call with `(await import('@pos/platform')).apiOrigin()` in the browser console. `VITE_REMOTE_ALLOW_DEV_KEY=1` makes the host trust the dev signing key the `build:*-remote` scripts sign with. The migrations are re-applied on every start and `036` drops columns older branches still read, so don't aim a checkout at a Postgres that another worktree on an older branch uses. `.claude/launch.json` starts the same three servers (`api`, `cafe-remote`, `pos-web`) from the desktop app.

## Architecture

### Multi-tenant LIVE automation (root `src/`, `admin/`)

The system is **multi-user**, not single-stream: each `User` (a TikTok seller account) has one `UserSettings` row and can run one `Session` at a time. `SessionManager` (`src/sessions/sessions.manager.ts`) keeps an in-memory `Map<user_id, ActiveSession>` holding the live TikTok connector and Telegram bot instance for that user; `sessions.controller.ts` exposes start/stop over HTTP, and `src/api/websocket.ts` streams `SessionLog`s to the admin UI live. Auth for this side is in `src/core/auth.ts`.

Order flow per session: TikTok comment → `parser.ts` (regex product-code/size extraction, EN/UK/RU) → `reservations.ts` (ACID reservation, race-safe, scoped by `user_id`) → `telegram/telegram.instance.ts` bot collects customer details → `orders.ts` → admin confirms payment → `novaposhta.ts` generates a TTN and notifies the customer. A cron job in `src/index.ts` marks expired reservations `expired` every minute; a daily one there also prunes `pos_gtin_lookup_events` past `GTIN_EVENTS_RETENTION_DAYS`, keeping owner corrections.

**All LIVE per-seller configuration lives in `user_settings`, never in the environment** — Telegram bot token/channel, Nova Poshta key/merchant name, and the reservation hold time. The admin SPA's Settings page writes them; `sessionManager.startSession` snapshots the row into the in-memory `ActiveSession` and passes it down to `TikTokInstance` / `TelegramInstance` / `createNovaPoshtaClient`. That snapshot is deliberate: one broadcast runs on one consistent set of settings, and edits take effect only after a stop/start. The `tiktok-live` POS module resolves to the same `users` row through the auth bridge, so it sees exactly the same settings — there is no second copy. Env vars in this backend are infrastructure only (`DATABASE_URL`/`DB_*`, `AUTH_SECRET`, `API_PORT`, `LOG_LEVEL`, `CORS_ORIGINS`, `PUBLIC_BASE_URL`, the POS `OPENDATABOT_*` keys, and `POS_SECRETS_KEY`); the single-user MVP's `TIKTOK_USERNAME` / `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHANNEL_ID` / `NOVAPOSHTA_*` / `RESERVATION_TIMEOUT_MINUTES` are gone, along with the `src/tiktok.ts` and `src/telegram.ts` singletons that read them.

Routes in `src/api.ts` each `await` auth themselves via the local `requireAuth` helper (same pattern as the settings/sessions/POS controllers) and scope their queries by `userId`. Do not reintroduce a `preHandler` auth hook there: the previous one enforced nothing, because it was registered inside `fastify.register(...)` (so its scope covered no routes) and called `ensureAuth` without awaiting.

**Note:** `TechDocs/archive/` holds the design + onboarding docs for the earlier single-user/single-stream MVP (`ARCHITECTURE.md`, `PROJECT_SUMMARY.md`, `IMPLEMENTATION_GUIDE.md`, `START_HERE.md`, `FILE_MANIFEST.md`, `QUICKSTART.md`, `DEPLOYMENT.md`, `fix-instructions.md` — all moved out of the repo root 2026-09-06). They include an `inventory` table that does not exist and predate multi-tenancy, the POS subsystem and the Railway deploy. Treat them as historical notes — `TechDocs/archive/README.md` explains the drift, `TechDocs/NOTES.md` tracks known drift. Prefer reading `src/core/types.ts` and the service files directly. The only current root docs are `README.md`, this file, and `ИНСТРУКЦИЯ.md` (Russian operator guide).

### POS (root `src/pos/`, `pos/`)

Independent subsystem sharing the same Postgres via `pos_*`-prefixed tables (migrations `002`–`035`). Backend is a Fastify plugin (`src/pos/pos.plugin.ts`) mounted at `/api/pos`, registered from `src/index.ts` alongside the LIVE routes; product photo uploads are served statically from `data/pos-uploads` under `/pos-uploads/*` (needs a persistent volume in prod — see `TechDocs/RAILWAY_POS.md`). Route surface (`src/pos/pos.controller.ts`) covers: owner/staff PIN auth, products/variants/tags, customers, stock (adjustments, low-stock, suppliers, stock documents with post/reverse), GTIN barcode lookup/enrichment/learning jobs (plus an owner repair surface over the shared `pos_gtin_cache` — `GET /gtin/cache`, `PATCH /gtin/:code` to correct an entry as `manual`, `DELETE /gtin/:code` to tombstone it, and a supplier price-list import on `/admin/gtin` that feeds `learn/batch` under the `supplier` source; see `TechDocs/POS_GTIN_ENRICHMENT.md`), sales (complete/void/refund, idempotent via `client_uuid`), analytics, and QR payment (`payment method 'qr'`; per-store settings on `pos_stores`; `POST /qr/invoice` proxies Opendatabot for the dynamic-mode QR, `POST /qr/webhook` is the HMAC-verified payment-confirmation callback + a daily `reconcileQrPayments` cron — needs `OPENDATABOT_QR_KEY` / `OPENDATABOT_QR_NAME`). Every `/api/pos` request/response carries an advisory `X-POS-API-Version` header (single integer per side: `src/pos/version.ts`, `pos/src/platform/version.ts`); a mismatch is logged, not rejected, unless `POS_API_STRICT_VERSION=1` — see `TechDocs/POS_API_VERSIONING.md`. `pos_stores.enabled_modules` / `pos_stores.module_remotes` drive the per-store feature-module set and per-module remote-bundle sources, and `pos_stores.nav_overrides` (migration `033`) the **appearance** of the menus built from them — a sparse `{ '<moduleId>:<location>:<path>': { label?, icon?, order? } }` map the owner edits on `/admin/appearance` («Вигляд меню», owned by the core `settings` module), sanitised by `src/pos/core/nav.ts`, travelling with the login (so a cold-offline till keeps its menu) and applied in `selectNavItems` — after the shell/role/`visible()` filters, so it can restyle and reorder an entry but never add or remove one, and online-only modules get it for free; see `TechDocs/POS_NAV_CUSTOMIZATION.md`. A `module_remotes` value is a bare URL string (override a bundled module's code — web **and** the desktop cashier, which skips web-only modules) or a `ModuleRemoteEntry` object `{ url, title, routePath, nav, icon? }` declaring a new **online-only** module the desktop cashier downloads (roadmap #13). A host imports a remote only if its `PLATFORM_VERSION` (`pos/src/platform/version.ts`, the `@pos/platform` surface version, pinned by `src/platform/surface.test.ts` + `npm run platform:snapshot`) is ≥ the manifest's `minHostPlatform` — see `TechDocs/POS_MODULE_PLATFORM_VERSION.md`; bump it by hand when the barrel's exports change (11 since 2026-09-17). A module that keeps **its own offline data** declares `offline: { pendingCount, sync }` on its descriptor; the shell entries register those hooks via `registerOfflineModules` from `@pos/platform` and the offline runtime drives them after its own outbox — first such module is `stocktake` (`pos/src/modules/stocktake/`, till-side inventory count → draft `inventory` document via the staff-level `POST /api/pos/stock/counts`, idempotent on `client_uuid`, migration `025`); see `TechDocs/POS_MODULE_OFFLINE_DATA.md`. `POST /api/pos/client-telemetry` is a dormant module/version-skew sink. A cross-store **super admin** lives at `/super` on the POS web (`pos/src/super/`, routes `src/pos/routes/super.routes.ts`): password from env `POS_SUPER_PASSWORD` (≥ 12 chars, unset = page disabled), stateless 12 h token in the `X-POS-Super-Token` header, edits any store's `vertical` / `enabled_modules` / `module_remotes` through the same validation as the owner's `PATCH /store`, and re-points a module release URL across stores — see `TechDocs/POS_SUPER_ADMIN.md`. It is also the **only** place the marketing site's leads can be read (`/super/leads*`, `TechDocs/CRM_LEADS.md`): migration `070` keeps a person per phone in `crm_leads` (status, note) and every form they send as its own `crm_lead_touches` row with the form, intent, product and the visitor's journey (first/last touch with referrer host+path, UTM and click ids, the last 20 pages and `data-cta` clicks) cleaned by `src/crm/journey.ts`, while the salesperson's labels — the source in words, the «hot» signals, days to lead — are computed on read by `src/crm/sources.ts`; `POST /api/leads` is capped (8 KB, a `website` honeypot, a GLOBAL in-memory limit because `request.ip` is Railway's proxy) and logs the lead id, never the phone, and the old `GET /api/admin/leads` — readable with any LIVE token, which `POST /api/pos/live/session-token` gives any seller — is gone. The module-remote architecture (feature modules under `pos/src/modules/*`, buildable as standalone runtime chunks that carry their own Tailwind CSS — shared `.sq-*`/token layer in `pos/src/styles/tokens.css` — Ed25519-signed via `pos/scripts/sign-remote.mjs` and verified before `import()`; on the Tauri cashier downloaded + verified in Rust and served from an on-disk cache via the `liveshopmodule://` URI scheme) is documented in `TechDocs/POS_MODULE_REMOTE_POC.md` / `POS_MODULE_REMOTE_ROADMAP.md` / `POS_MODULE_REMOTE_SIGNING.md`; what a runtime-loaded module can reach inside the Tauri cashier (app commands are **not** ACL-gated, so the window's `capabilities/default.json` is a minimal one-permission set guarded by `npm run check:tauri-capabilities`) is `TechDocs/POS_MODULE_TAURI_CAPABILITIES.md`. The first real online-only module is **`tiktok-live`** ("Прямий ефір" — the TikTok LIVE comment feed + session start/stop inside the POS shell): source in `pos/src/modules/tiktok-live/`, built by `pos/vite.tiktok-live-remote.config.ts`, and reaching a store only through an object entry in `pos_stores.module_remotes` — the shell ships none of its code. It authenticates through the one deliberate POS→LIVE bridge, `POST /api/pos/live/session-token` (`src/pos/routes/live.routes.ts`), which swaps an authenticated POS session for a LIVE token minted from `pos_stores.live_tiktok_username` (migration `017`, owner-writable via `PATCH /store`); see `TechDocs/POS_LIVE_SELLING_MODULE.md`.

**Sales verticals** (`TechDocs/POS_VERTICALS.md` — design doc *and* resume point, with a phase table). What a store sells is `pos_stores.vertical` (migration `034`), written **only** by the super admin: it decides the product attribute schema, the units the store may sell in, and which module renders the catalog half of the sell screen. The set of verticals lives in code (`src/pos/verticals/{types,index,attributes,clothing,flowers}.ts`, a `BUILT_IN` registry + `registerVertical`/`resetVerticals` test seam, exactly like `fiscal/providers`), not in a CHECK constraint — a new vertical must not need a migration — and a column value this build does not know degrades to clothing at read time (`verticalOrDefault`) rather than failing every login of that store. The owner sees it read-only in Settings; their `PATCH /store` answers 400 for `vertical`, and the column is absent from `STORE_PATCH_COLUMNS`. A fifth vertical, **grocery** (weighed goods through label scales and GS1 weight barcodes, checkout scales, excise goods, sales «під запис»), is at the planning stage: `TechDocs/grocery/README.md` is its resume point (with the owner's decisions of 2026-10-23: sales «під запис» are the vertical's **headline feature** — a non-fiscal entry in a debt journal at handover, its slip **not printed by default** and, if the owner wants paper, routed to a station printer like the kitchen/bar ticket, the fiscal receipt issued at payment; the site, SEO and AEO for the vertical are built around it — its landing `/pos/produkty` is live in «Скоро» mode, see "Marketing site" below; the customers are small shops and market traders, the latter on phones, where nothing writes offline today), `grocery/RESEARCH.md` the 2026-10-23 study (world leaders, forgotten US POS, Ukrainian rules — cash rounds to **50** kopecks since 01.10.2025, e-excise from 01.11.2026, a licence per ПРРО) and `grocery/research-notes/` its sourced notes; `grocery/PLAN.md` is the plan of plans (phases Г2–Г10 with PR boundaries, prerequisites and the owner's decisions Д1–Д15, of which Д1–Д4 were accepted on 2026-10-24 — credit for every vertical, only for a customer with an owner-set limit the till enforces, repayment by whole lines from the oldest: generic slots for feature modules first, then «під запис» as the `debts` module, weighed goods, the phone, label scales), resting on the owner's decision of 2026-10-24 that features and integrations — the debt journal, scales, excise — are **external modules** like `tables`/`tiktok-live`, the host and server gaining only what a module cannot carry (host slots, server route groups, Rust commands, and the sale itself). The slots came first, as phase Г2 (platform **20**, `TechDocs/POS_MODULE_SLOTS.md`, `pos/src/modules/featureSlots.ts` + `ModuleSlots.tsx`): `checkout.Action` beside «Оплатити» (the module makes its own server call and calls `onCompleted`, after which the host empties the cart and bumps `stockEpoch`; none on a pre-order or in an exchange), `customer.Panel` under the chosen customer and on the customer card, `settings.Card`/`analytics.Panels` now from feature modules too, after the vertical's, and `hardware.stations` — data, not a component: «Обладнання» draws the kitchen's printer picker for it under `stationPrinter:<module>:<station>`, with no fallback to the receipt printer. Each module renders in its own `SlotBoundary`; a foreign `vertical-*` never draws, a feature module only in its shells and role and, when bundled, only while enabled. What a module prints goes through `printSlip`, the eleventh Tauri command `print_slip`, which always prints «НЕ Є РОЗРАХУНКОВИМ ДОКУМЕНТОМ» top and bottom and refuses a title with «ЧЕК»/«ФІСКАЛЬН» or a total labelled «До сплати»/«ПДВ»/«Решта». Phase Г3, «під запис», has its design doc and resume point in `TechDocs/grocery/G3_DEBTS.md`, and its server half (PR1, migration `073`) is in: a customer may take goods on credit only under an owner-set `pos_customers.credit_limit_cents` (NULL = never; `credit_locked` stops new handovers, never repayment), and every write to one customer's debt begins with `FOR UPDATE` on that customer's row (`lockCustomer` in `src/pos/debt-lines.service.ts`), so two tills can neither squeeze under one limit nor pay one line twice. The open `pos_debt_items` are the truth about what is owed and the append-only `pos_debt_entries` journal (`issue` / `return` / `payment` / `payment_void` / `writeoff`, signed) the record of every event — the two always sum to the same balance, which every debt test checks, and there is no free-amount correction in v1. A handover (`POST /api/pos/debts/issue`, `src/pos/debts.service.ts`; a core route group, `debts.routes.ts`, `moduleId: null`) prices through `pricePlainLine` and shares a cart discount through `allocateCartDiscount` exactly as a sale does, locks both onto the line, refuses going over the limit with the figures in a 409, and moves stock ONCE, with the new reason `credit` (widened in `006`, the one file that adds that CHECK), through `consumeStockForLine` target `debt` with its snapshot in `pos_debt_item_components`. A repayment (`POST /debts/customers/:id/pay`, `src/pos/debt-payment.service.ts`) is an ordinary sale: `completeSale` with `debt_part` takes the oldest open lines (the till names them; anything else is 409 `not_oldest` / `stale_statement`), carries each line's exact owed sum as its receipt line (`fixed_total_cents`, the discount being the difference), moves no stock, copies the snapshot into `pos_sale_item_components` so a refund of the receipt gives back what left, and writes a `payment` of the goods' total — never the cash rounding; `GET /sales/:id` says `repays_debt`, and under ПРРО it has a bill part's three outcomes (preflight refusal 503 with nothing written, a refused document undone with the goods owed again and no stock moved, an ambiguous one kept `failed` with a warning). `voidSale` now routes a receipt whose lines carry `bill_item_id`/`debt_item_id` to giving those lines back WITHOUT stock (`releasePartLines`, which also fixed a manual `/sales/:id/void` on a table's receipt crediting cooked dinner back onto the shelf, and refuses one whose bill is already closed), and `abortSale` is just `voidSale`. A cashier takes goods back from an unpaid line (stock back as `credit`, priced by `refundLineAmount`'s cumulative rounding, now in `src/pos/lineMoney.ts`), only the owner writes a debt off (with a reason) or reads `GET /debts/summary` — issued, repaid, returned, written off and the closing balance, never inside takings. The demo migrations' catalogue rebuilds clear their store's debt rows behind a `to_regclass` guard, because `073` runs after them on a fresh database. The client half is the **`debts` module** (PR2, `pos/src/modules/debts/`, port 5010, `minHostPlatform` 20, the first feature module in the Г2 slots; an online-only remote opted in through a `module_remotes` object entry with `routePath: '/debts'`): `checkout.Action` «Під запис» beside «Оплатити», whose refusals are `issueBlock` (no customer, offline, a till-assembled bouquet, no limit, locked, over the limit in figures) and under which only the refusal is written, the debt itself being the `customer.Panel` strip one line up; that panel in the cart and on the customer card, where the owner gives credit (limit, lock, take away — «Борги» lists only those who already have one); «Борги» as one page in two frames, `/debts` on the till rail and `/admin/debts` in the cabinet (statement, repayment with the three ПРРО outcomes, return of unpaid goods, the owner's write-off); and three dashboard tiles that draw nothing on any failure. One module-level credit cache (`lib/useCredit.ts`) that every write's answer refreshes keeps the strip, the button and the card in step — on a phone the cart's slots are mounted twice, the hidden sidebar and the sheet. A write's `client_uuid` is made when its sheet opens, kept after no answer and renewed after any definite refusal — and remembered for half an hour by what it would write (`lib/pendingKeys.ts`: a handover by customer + goods + cart discount, anything else by customer + kind), so a sheet opened again after a timeout replays instead of writing twice, the limit not stopping that check — and a repayment always names its `line_ids` (the N oldest the cashier sees), never «everything», so the receipt is exactly the screen. The web and the tablet say «Потрібна мережа» offline; the **desktop writes handovers without a network** (PR3, migration `074`, `G3_DEBTS.md` §6) — never repayments (Д7). It judges them by the module's own Dexie (`cloth-pos-module-debts`): a `credit` **mirror** of who may take credit (the whole `GET /debts?all=1` after every sync pass that sent something and at most once a minute otherwise, plus every online credit answer, which `publishCredit` writes itself; a row written after the list read began stays, a full 500-row page deletes nobody) with this till's unsent handovers added on top, so Д3 still holds and a till that never had the list refuses («Потрібна мережа»); and an `issues` **queue** keyed by the sheet's `client_uuid`, which a write that timed out joins too, under the same key, so its replay can never become a second debt. The `offline` hooks (`data/sync.ts`) send the queue after the shell's outbox with `offline_at` = when the goods left — the server then records rather than judges (no limit, lock, archive or stop-list refusal; still 404/400 for another store's customer or goods), dates the entry and its lines by the till (clamped to the last 90 days, never the future), marks `offline_received_at` (the statement's «без мережі»), prices again and files it under the session that sent it — and refresh the mirror there, there being no snapshot hook. A refused row stays red on «Борги» with «Надіслати ще раз»/«Прибрати»; offline «Борги» is the mirror, read-only; the list and a statement re-read when a row leaves the queue (the reconnect race). Product model (migration `035`): `pos_variants` carries `attributes jsonb` + a **derived, stored** `label` + `unit`, replacing `size`/`color` (`036`, a *later* deploy, drops the old columns — see below). Every variant write goes through `normalizeVariant` (`src/pos/verticals/attributes.ts`): unknown attribute or a unit outside the vertical's set → 400, an update replaces the bag wholesale (so "clear this attribute" is expressible), and `label` is always recomputed — a client never sends one. **Composite products** (migration `037`, `src/pos/composites.service.ts`) — a bouquet now, a tech card in the café phase. `pos_products.kind` is `'simple'` | `'composite'`; `pos_products.stock_mode` says where a composite's quantity lives: `'own'` (assembled in advance, counted on its own `pos_stock` row — selling it must **not** touch the components, the production document already took them) or `'derived'` (assembled when it sells: no stock of its own, availability is `MIN(floor(component_stock / component_qty))` over `pos_product_components`, an empty composition being 0 and never unlimited). Both modes from the start, because a florist runs both off one catalogue card. The composition hangs off the **variant**, not the product (S/M/L bouquets differ precisely in stem count), and a component may not itself be composite — that is what makes cycles impossible without a recursive check. The rule everything rests on: what a sale actually consumed is snapshotted per line into `pos_sale_item_components` (per **one** unit, so a partial refund is exact arithmetic), and a void/refund reverses **that snapshot**, never the current recipe — the recipe is editable, and an ad-hoc till-assembled bouquet has no recipe at all. The snapshot's presence is also the signal, so a reversal never reads `stock_mode` and cannot drift from the write-off. `sales.service.ts` moves stock only through `consumeStockForSaleItem` / `returnStockForSaleItem`; `assertStockable` refuses a derived composite at manual adjustment and at stock-document posting, and `listOnHand`/`listLowStock` leave it out (its own row sits at 0 forever). Writes refuse a derived composite with no composition, with opening stock, a switch to `derived` while stock is still on the shelf, and a switch to `simple` while a composition still exists — all four would lose data silently. A fifth stock-document type, `production` (prefix `ВР`, migration `038` only widens the CHECK), is the other half of `'own'`: its lines name only the composite produced, the component write-off is derived at post time by `produceComposite`, the assembled cost is summed from the components (so `addLine` refuses a typed-in one), a line for a derived or simple variant is refused at **add** time, and the reversal replays the inverse of the movements that document recorded — same reason as a refund, and it fails outright if some of the assembled units have already been sold. On the client, the product card owns the composition (`pos/src/modules/products/components/CompositionEditor.tsx` + `componentOptions.ts`, which offers every active variant of a non-composite product and so enforces the same one-level rule as the server) and edits it wholesale — in the create form **and** in the edit form, where changing an existing product's shape orders its writes around the server's two ordering rules (a simple product may not carry a composition, a composite may not become simple while one exists), so simple → `derived` goes through `own` rather than being one impossible write — and `/admin/stock/production` (`stock` module) is its own screen rather than another `type` on `StockActionPage` — production picks only from what the store assembles in advance and needs the bill of materials and a "will it stretch" read-out on screen. A cart line may also carry **its own** composition (`CompleteSaleItemInput.components`) — a bouquet the cashier assembled at the counter, rung on a catalogue card whose stored recipe is only a default. It runs the same mechanism (`validateComponents` is shared with the catalogue editor; the snapshot and the reversal are unchanged), with three rules that are easy to get backwards: a line carrying a composition is **never merged** with another of the same variant (two custom bouquets are two bouquets, and merging throws one recipe away); the price is **computed** server-side as the sum of the components' prices, never sent, because a freely settable line price is a hole no receipt would show (real markdowns stay in the line/cart discounts); and only a **derived** composite accepts one. `GET /sales/:id` now returns `items[].components`, which for a till-assembled bouquet is the only place its recipe exists. The whole **backend** is now in place (phases 0–4): settings (`GET`/`PATCH /api/pos/fiscal/settings`, owner-only), the `FiscalProvider` adapter contract + error taxonomy (`src/pos/fiscal/{types,errors,mapping,rateLimit}.ts`), the shift lifecycle (`shifts.service.ts` + a `*/5` auto-close cron), the document ledger (`ledger.ts`) and checkout orchestration (`fiscal.service.ts`, wired from `checkout.routes.ts`, + a `*/2` retry cron). The Checkbox adapter ships (`providers/checkbox/`) and so does Cashalot's (`providers/cashalot/`, phase CA5 — no session, `KeyGuid`+`KeyPin`+ФН in every request, the check built by `dps/` from the store's own tax table in `config.taxes`, a repeated `UID` answered by finding the existing document rather than re-sending; selectable only once its bundle lands in CA6), `BUILT_IN = [checkboxProvider, cashalotProvider]`; a store that enables a provider with **no** adapter (`vchasno`, `echeck`) would 503 on every sale, so check `select store_id from pos_fiscal_settings where enabled and provider not in ('checkbox', 'cashalot')` is empty before deploying. **Offline mode** (`TechDocs/prro/POS_FISCAL_OFFLINE.md`, fiscal phase 8б) has its groundwork in (phase 1, migration `027`): an optional `FiscalProvider.offline` capability (Checkbox implements it), a server pool of tax-office offline codes refilled by a `*/10` cron (`src/pos/fiscal/offline/pool.ts`), and a **register holder** lock (`offline/holder.ts`) keyed on the desktop cashier's `X-POS-Device-ID` header (in CORS `allowedHeaders`; the web shell sends none) with `POST /fiscal/register/{claim,release,handover/request|confirm|force}` — all of it enforced only while `pos_fiscal_settings.offline_mode` is on, which the settings service accepts only for a capable provider. Phase 2 (case B — the provider is unreachable from the backend, the till is not) is in: `preflight` opens a **server-held offline session** (`offline/session.ts`, migration `028`) inside a shift that was opened online and the sale is stamped from the code pool (`fiscal.mode: 'offline'`, `status: 'pending'`, fiscal number = tax-office code, no control number/QR until replay) without a provider call; while a session is live every sale is stamped even if the provider is back (an online receipt inside it breaks the `go-offline` date order), refunds/service receipts/manual shift close wait (`offline_session_open`), and `retryPendingFiscalDocs` starts with `replayServerSessions` — probe, pool resync, `go-offline` once, documents in `offline_seq` order, `go-online` ≤ 1/2 min, poll → `closed` (a delivered online document newer than the session start parks it `stuck`). The flat retry never claims `mode='offline'` rows nor a store with a live session. Till-side offline selling (case C, phase 3) and the UI (phase 4) are not built yet. Two rules that are easy to get backwards: the provider owns the shift and `pos_fiscal_shifts` is a mirror; and a committed sale is voided **only** when the document cannot exist at the provider (`mayExistAtProvider`) — voiding on an ambiguous timeout double-fiscalises the cashier's re-ring. The client (phase 5) is in too: the till distinguishes three checkout outcomes (503 wrote nothing / 502 voided the sale / 502 kept it — the last is a **success** screen with a warning, because the customer paid and left), a fiscalising store refuses to queue an offline sale (`OfflineFiscalError`) and probes idempotently on a timeout (`FiscalSaleUnknownError`), the offline outbox gained a terminal `'dead'` status with backoff measured from the last attempt, and `pos/src/pages/admin/FiscalSettingsCard.tsx` owns the ПРРО switch. Both of the pieces a store needs to actually fiscalise are in: the Checkbox adapter (phase 2b) and the provider UI bundle (phase 6, `fiscal-checkbox` — `/admin/fiscal` credentials + attention list, `/fiscal` shift control). Offline mode has its UI too (phase 4): the owner's switch and code-reserve size are in the host's `FiscalSettingsCard` (never in the provider bundle — a bundle that fails to load must not be able to strand a store in offline mode), `fiscal-core` owns the till panels on `/fiscal` (`OfflinePanel` — reserve + session state, `HolderPanel` — the register lock, both silent unless `offline.enabled`; the web shell sends no `X-POS-Device-ID` so it gets facts and no buttons), and `/admin/fiscal` lists parked `stuck` sessions alongside the attention documents and can force a handover. A 409 `register_held` on checkout is its own `CheckoutFailure` kind, and an offline-stamped receipt reads as «ПРРО: офлайн» on the receipt card rather than «реєструється». An offline-stamped receipt also gets its tax-office QR at stamp time (`src/pos/fiscal/taxUrl.ts` — `id`/`date`/`time`/`fn`/`sm`, the format Положення № 13 prescribes; ФН ПРРО is cached in `pos_fiscal_settings.register_fiscal_number`, migration `029`); the контрольне число and the provider's `mac` arrive with the replay, because both come from the ПРРО's offline session, which is Checkbox's, not ours (primary sources snapshotted in `TechDocs/prro/dps/`). Decision 2026-09-12: case C goes the **cloud path** (Checkbox's own `ask-offline-codes` → `sell-offline` → `go-online` model for external systems); the local Checkbox Kasa component is parked. Phase 8в is in: the store's legal requisites, ФН ПРРО and tax letters come from the provider (`FiscalProvider.fetchRequisites`, `src/pos/fiscal/requisites.ts`, cached as `pos_fiscal_settings.requisites` with a 24 h TTL — migration `030` — refreshed at shift open / pool refill / the owner's connection test, never at checkout), travel to the till in `auth.store.fiscal` together with `default_tax_code`, and the `'local'` layout (`pos/src-tauri/src/hardware/receipt.rs` + `pos/src/components/ReceiptPrintable.tsx`, built by `pos/src/lib/receipt.ts`) now prints the Положення № 13 п. 2 rows — header 1–5, rate letters, «СУМА/ПДВ/ДО СПЛАТИ/РЕШТА», «ГОТІВКА/БЕЗГОТІВКОВА», «ФІСКАЛЬНИЙ ЧЕК» + producer, the «ОНЛАЙН/ОФЛАЙН» mark, «ЧЕК №», «ФН ПРРО». An offline stamp needs the cached requisites (the first receipt of a register is online-only), and the admin's `FiscalSettingsCard` shows them read-only. Still per-store, not per-line: the rate letter follows `default_tax_code`. Phase 3 (case C — the till has no network, the shop keeps selling) is in: the register holder leases tax-office codes from the pool (`POST /api/pos/fiscal/offline/lease`, `src/pos/fiscal/offline/lease.ts`, 50 at a time, refreshed at the end of every sync), the desktop till stamps and prints the receipt itself (`pos/src/offline/lease.ts` holds the reserve and the gates; `pos/src/lib/taxUrl.ts` builds the QR without us) and `POST /api/pos/sales/complete` files it afterwards through a `fiscal_offline` stamp — same session, ledger and replay as a server-stamped one, except that a refusal never voids the sale (the goods left during the outage) and only a retryable answer comes back as 503. A handover can optionally close the shift on the way out (`close_shift` on `/fiscal/register/handover/confirm`, off by default, the Z-report sent before the lock moves and a failure leaving the register where it was). The tax office's **monthly** offline allowance (168 h per register, Положення № 13) is counted server-side in `src/pos/fiscal/offline/limits.ts` over the register's sessions clipped to the Kyiv calendar month, refuses a new session and further sales inside a live one (`offline_month_limit`) without parking that session, and travels to the till in the lease answer because the till cannot know it (another till of the same register spends the same hours). Three things are easy to get wrong here: the replay transmits in **fiscal-date** order, not `offline_seq` order (a till's receipts arrive interleaved with sales it rings online while its queue drains); the `go-offline` floor (`offlineChainFloor`) includes a Z-report and the previous session's `go-online`, so a shift that auto-closed during an outage parks the session instead of corrupting the register; and the replay of a session carrying a till's documents waits for that till to report an empty outbox (`ready_at`, migration `031`, with a one-hour grace). A demo-register run on 2026-09-12 (fixtures `src/__tests__/fixtures/checkbox/offline_*.json`) confirmed the two things the design rests on — Checkbox accepts a `go-offline` dated in the past and a `fiscal_date` in the past, returning `control_number` and a `tax_url` with `mac` — and caught two bugs, both fixed: `previous_receipt_id` must **never** be sent (Checkbox refuses the only value we can compute, `receipt.previous_id_last_id_differs`, which would have cost every receipt of an outage after the first), and a receipt may not be dated before its shift opened (`date.fiscal_date_logic`), so `offlineChainFloor` now includes the open shift's `opened_at`. A second run the same day, after both fixes, carried a chain of three receipts through in full (each with its own control number and a `tax_url`); every run now keeps its answers, console output and a `run.json` under `src/__tests__/fixtures/checkbox/runs/<timestamp>/` instead of overwriting the last one. Still open: hardening (phase 5) — offline refunds and service receipts, a second till per register, a duplicate offline code, `go-online` with undelivered documents, and the e2e/desktop run. Receipt printing (phase 8a) follows `pos_fiscal_settings.receipt_source`: `'local'` prints our ESC/POS layout plus a fiscal block (number, date, tax-office QR via the printer's native `GS ( k`); `'provider'` prints the provider's own text, fetched once at fiscalisation time at the store's `receipt_width` (32 = 58mm, 48 = 80mm, migration `026`) and stored as `pos_fiscal_receipts.receipt_text`. The till decides by presence of `receipt_text` only — a failed text fetch (`attachProviderReceiptText` in `fiscal.service.ts`, own 2.5s sub-budget, never fails the document) silently falls back to the local layout.

`pos/src/shell.tsx` is the context that branches shell-specific behavior; `modules/shells.ts` `runsInShell` decides which modules a shell mounts (a remote bundle published with `shells: ['web','cashier']` before the tablet existed still runs there). The desktop cashier is the only surface that **writes** offline (`pos/src/offline/`, IndexedDB via Dexie): it snapshots catalog/tags/customers on first online login, verifies PIN/password locally via a PBKDF2 verifier (never stores the raw PIN), queues sales/customer writes while offline, and syncs (customers first, then sales) once a JWT and network are available. The **tablet PWA** (`TechDocs/POS_PWA.md`, the waiter's `/tablet/` on the same Railway static service as the web) **reads** offline and writes online: `enableOfflineReads()` gives it local login, the catalog snapshot and the `tables` mirror, while `isOfflinePosEnabled()` stays false so it never sends `X-POS-Device-ID` (the server would treat it as a till that can hold the ПРРО register), never queues, and a write without a network throws `OfflineWriteError` on the spot; it also mounts no `ScanWedge` (the hidden scanner input it once rendered was the on-screen keyboard popping up — the component returns `null` under the tablet shell, and `RegisterPage` passes `active=false` to the catalog there so bundles published before that fix are covered too). A hand-written service worker (`pos/sw/tablet-sw.js`, precache list from `scripts/precache.mjs`, scope `/tablet/`) keeps the host build and the remote bundles; a newer build is offered on a banner and otherwise applied on the next launch, never mid-bill; `pos/serve.json` (no `serve -s` — it would shadow the `/tablet/**` rewrite; no `redirects` — serve-handler strips the trailing slash before matching, so `/tablet → /tablet/` looped; and the SPA fallback is `/:path([^.]+)`, not `**`, because serve-handler re-applies the remaining rewrites to a rewrite's result and `**` turned `/tablet.html` into `/index.html`) carries the rewrites and cache headers, and only `npm run check:serve-json` exercises it against the real `serve@14` — Playwright's `vite preview` merely imitates it, which is how both traps reached production in 2.3.0. Two chunk-boundary traps that shipped and are closed: the mode setters must be called through `@pos/platform` (the desktop entry's relative import of `offline/enabled.ts` set a second copy of the flag, so the release till never started its offline runtime — `enabled.ts` is now in the boundary check's `STATE_OWNERS`), and `lib/checkoutError.ts` matches the offline errors by `.name`, not `instanceof`. Web admin always talks to the API directly — no offline path there. `VITE_API_BASE` is baked in at build time (`pos/src/lib/urls.ts`); the desktop build defaults to the production API (`https://the-live.shop`) unless overridden via `pos/.env`. See `TechDocs/POS_DESKTOP.md` for the full offline/sync/CORS/kiosk story and `TechDocs/RAILWAY_POS.md` for deployment.

The POS is being redrawn in the Things look the site already has (`design/README.md`, plan in phases): tokens are RGB-channel variables in `pos/src/styles/tokens.css` that Tailwind's `sq-*` reads (so remotes follow the host), Inter is self-hosted (`src/styles/fonts.css`) with SF under `html.apple` set by `markApplePlatform()` in each entry, and icons are the glyph set — `pos/src/platform/glyphs.tsx`, **generated** by `node scripts/gen-icons.mjs` from `design/icons/` and re-exported by `@pos/platform/ui` (platform 17); `lucide-react` is gone, and `NAV_ICONS` keeps its lucide-named keys because stores store them. ### Marketing site (`site/`)

A multi-page Vite app with no router — one HTML template + one `src/*-main.tsx` entry per page (`index`/`live`/`pos`/`compare`, plus `dovidka.html` shared by `/dovidka`, every `/dovidka/<slug>` and `404.html`). It is **statically prerendered at build time, never SSR'd at runtime**: `npm run build` runs the client build, then `vite build --ssr src/entry-server.tsx`, then `scripts/prerender.mjs`, which renders every entry of the route registry `src/routes.tsx` with `renderToString`, injects the markup into the built template's `<div id="root">` and the SEO head (`src/lib/seo.ts`: title/meta/OG + JSON-LD) at the `<!--app-head-->` placeholder, and writes `dist/<out>`; the entries hydrate via `src/mount.tsx`. The reason: AI/answer-engine crawlers (GPTBot, ClaudeBot, PerplexityBot — all allowed in `public/robots.txt`) do not execute JS, so before this the pages were empty to them. The prerender also emits `dist/sitemap.xml` and `dist/llms.txt` (served by Fastify from `site/dist`, not `public/`) and fails the build if a page lacks `<h1>`/JSON-LD, carries an inline `opacity:0`, or references a missing `/assets/*` file. The sitemap's `<lastmod>` is **not typed by hand**: `site/sitemap-lastmod.json` keeps, per page, a hash of what the page says (`site/scripts/content-hash.mjs` — the text, links and images of its `<main>`, its title, description and JSON-LD; navigation, footer, the lead form's fields and CSS classes are left out, so a redesign, a sitewide footer link or a new field in the form on every page moves no date) and the day that hash last changed. After changing a page run `npm run sitemap:stamp` in `site/` and commit the file: CI builds with `SITEMAP_STRICT=1` and fails on a page whose content no longer matches its stamp, any other build (the Dockerfile's) warns and uses today. Hand-kept dates went stale exactly on the hubs — `/dovidka` sat at 2026-09-30 through a dozen new articles, `/pos` through two FAQ rewrites — and the initial stamps of 2026-10-23 were taken from rebuilding the site at the last commit of every day since 2026-09-21. Fastify maps the pretty URLs to the files (`src/api.ts`: `/`, `/live`, `/pos`, `/pos/:slug`, `/yaku-kasu-obraty`, `/dovidka`, `/dovidka/:slug`, `/about` — the last one prerendered from `AboutPage.tsx` with an `AboutPage` schema since 2026-09-23; the hand-written `public/about.html` and legacy `styles.css` are gone) and its `setNotFoundHandler` returns `dist/404.html` for site paths while `/api/*` keeps the JSON 404 (`src/__tests__/site-routes.test.ts`).

Since 2026-09-24 the site is drawn in the visual language of Things (Cultured Code) — their neutrals, SF/Inter, hand-drawn colour glyphs — with our accents unchanged; `design/README.md` has the tokens and the rules. The look lives in `tailwind.config.js` (same token names, Things values: `mist` is the `#F2F5F7` page, `paper` the white card) and the `@layer components` block of `src/index.css` (`card`, `card-flat`, `band`, `h-display`, `h-section`, `lede`, `btn-pos`/`btn-live`/`btn-quiet`, `link-more`); section heads go through `SectionHeading` (a 48 px glyph over a centred `h2`). Icons are `src/components/glyphs.tsx`, **generated** by `node scripts/gen-icons.mjs` from `design/icons/` — edit the SVGs, never the TSX (CI runs `--check`); `lucide-react` is gone. The font is Inter (`@fontsource-variable/inter`, self-hosted) by default and SF only under `html.apple`, set by an inline script in each template — not a font stack, because Chrome treats `BlinkMacSystemFont` as `system-ui`, i.e. Segoe UI on Windows. ### CORS

`CORS_ORIGINS` (comma-separated, no trailing slash) env var on the API service allowlists POS/admin web origins. The Tauri desktop cashier's origins (`https://tauri.localhost`, `http://tauri.localhost`) are hardcoded in `src/api.ts`, not env-driven.

## Conventions

- Root backend is strict TypeScript (`strict`, `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns` all on) compiled with `tsc`; ESM throughout (`"type": "module"`, `.js` extensions in relative imports even though source is `.ts`).
- ESLint: all three apps share one ruleset — `@typescript-eslint/no-unused-vars` warns and allows `_`-prefixed names, `no-explicit-any` is off, `no-console` allows `warn`/`error` only (root CLI scripts `src/pos/{migrate,seed}.ts` + `gtin/seed-from-dump.ts` override it off; in the rest of the backend use `logger`, `src/logger.ts`, Winston). `admin/` and `pos/` add the `react-hooks` (error) / `react-refresh` (warn) plugins. `npm run lint` passes with zero warnings in all three and is enforced in CI.
- Admin SPA has a real test suite (Vitest + Testing Library + MSW for HTTP mocks, class-mocked WebSocket, Playwright for e2e) — when touching `admin/src/services` or `admin/src/hooks`, keep coverage above the gate. See `admin/TESTING.md` for what's considered P0.
- Root backend tests (`src/__tests__/`) are mostly POS-focused (crypto, money, GTIN normalization/orchestration, sales logic, stock race conditions, stock reports/documents, tags, the products/customers/suppliers/uploads/auth services, and the whole `/api/pos` route surface) plus the order parser. `vitest.config.ts` scopes the root suite to `src/__tests__` — without it vitest's default glob also picks up `admin/` and `pos/`.
- DB-backed tests run against the database in `.env` and share `src/__tests__/helpers/pos-fixtures.ts`: `applyPosMigrations()`, per-file store isolation (`createTestStore` / `dropTestStore`), and `buildPosTestApp()` for driving the real Fastify POS plugin through `app.inject()`. Migrations are applied once per run by `vitest.global-setup.ts`; the ordered list lives in `src/pos/migrations.ts` and is shared with `npm run pos:migrate` — add new migrations there and nowhere else.
