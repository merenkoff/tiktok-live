# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repo layout — three independent apps, one Postgres

This repo actually contains **three separately-deployed apps** that share one Postgres database:

- **root (`src/`)** — Fastify + TypeScript backend. Owns the DB, serves the REST/WebSocket API for both LIVE automation and POS. Deployed as its own Railway service.
- **`admin/`** — React + Vite SPA for the TikTok LIVE side (session control, live logs). **Retired 2026-09-09**: its nickname-only login endpoint was removed and the login screen is now a notice pointing at the POS, whose `tiktok-live` module owns the broadcast desk (`/live`) and its settings (`/admin/live`). The code and its CI workflow stay; nothing can sign in. Talks to the root API.
- **`pos/`** — React + Vite SPA for the point of sale, with a Tauri 2 desktop shell for an offline cashier kiosk. Own `package.json`, no CI workflow yet. What a store sells is a per-store **vertical** (clothing today, flowers next, café later) — see "Sales verticals" below.
- **`site/`** — the marketing site at `the-live.shop` (React + Vite + Tailwind, statically prerendered). Not a fourth deployment: `Dockerfile` stage 1 builds it and the root API serves `site/dist` (`src/api.ts`). See "Marketing site" below.

Each of `admin/` and `pos/` has its own `node_modules`, `tsconfig.json`, and dev server — always `cd` into the subdirectory (or use `npm --prefix`) before running its scripts. Root `npm` scripts only touch `src/`.

#### Running the POS locally against a demo store
```bash
cp .env.example .env                          # DB on localhost:5433 (edit DB_PORT if that port is taken)
npm run docker:deps                           # Postgres :5433 (nothing in src/ uses Redis)
npm run pos:migrate
POS_SEED_VERTICAL_CAFE=1 npm run pos:seed     # demo-cafe + registers vertical-cafe → localhost:5008 (POS_SEED_VERTICAL_FLOWERS=1 → flowers, :5007)
npm run dev                                   # API :3000
cd pos
npm run build:local                           # web build that talks to the local API
npm run build:vertical-cafe-remote && npm run serve:vertical-cafe-remote   # module bundle, :5008
npm run preview:local                         # http://localhost:3002
```
Logins (`pos:seed` prints them): store `demo-cafe` + seller PIN `1234`, owner `owner@cafe.shop` / `owner123`.

Why a production build and not `npm run dev`: a runtime-loaded module (`vertical-*`, `tiktok-live`, …) resolves `@pos/platform` through the import map that only `dist/` has — under `vite dev` it is bundled through the alias. And why `build:local` and not `build`: `vite.platform-remote.config.ts` bakes `https://the-live.shop` into the shared `@pos/platform` chunk (where the axios client lives) unless `VITE_API_BASE` is set — right for the desktop cashier, wrong here: a plain `npm run build` produces a "local" POS that talks to **production**. `build:local` points it at `http://localhost:3002`, the origin `preview:local` serves, whose proxy forwards `/api` and `/pos-uploads` to :3000, so no CORS. Check what a build will call with `(await import('@pos/platform')).apiOrigin()` in the browser console. `VITE_REMOTE_ALLOW_DEV_KEY=1` makes the host trust the dev signing key the `build:*-remote` scripts sign with. The migrations are re-applied on every start and `036` drops columns older branches still read, so don't aim a checkout at a Postgres that another worktree on an older branch uses. `.claude/launch.json` starts the same three servers (`api`, `cafe-remote`, `pos-web`) from the desktop app.

## Architecture

### Multi-tenant LIVE automation (root `src/`, `admin/`)

The system is **multi-user**, not single-stream: each `User` (a TikTok seller account) has one `UserSettings` row and can run one `Session` at a time. `SessionManager` (`src/sessions/sessions.manager.ts`) keeps an in-memory `Map<user_id, ActiveSession>` holding the live TikTok connector and Telegram bot instance for that user; `sessions.controller.ts` exposes start/stop over HTTP, and `src/api/websocket.ts` streams `SessionLog`s to the admin UI live. Auth for this side is in `src/core/auth.ts`.

Order flow per session: TikTok comment → `parser.ts` (regex product-code/size extraction, EN/UK/RU) → `reservations.ts` (ACID reservation, race-safe, scoped by `user_id`) → `telegram/telegram.instance.ts` bot collects customer details → `orders.ts` → admin confirms payment → `novaposhta.ts` generates a TTN and notifies the customer. A cron job in `src/index.ts` marks expired reservations `expired` every minute; a daily one there also prunes `pos_gtin_lookup_events` past `GTIN_EVENTS_RETENTION_DAYS`, keeping owner corrections.

**All LIVE per-seller configuration lives in `user_settings`, never in the environment** — Telegram bot token/channel, Nova Poshta key/merchant name, and the reservation hold time. The admin SPA's Settings page writes them; `sessionManager.startSession` snapshots the row into the in-memory `ActiveSession` and passes it down to `TikTokInstance` / `TelegramInstance` / `createNovaPoshtaClient`. That snapshot is deliberate: one broadcast runs on one consistent set of settings, and edits take effect only after a stop/start. The `tiktok-live` POS module resolves to the same `users` row through the auth bridge, so it sees exactly the same settings — there is no second copy. Env vars in this backend are infrastructure only (`DATABASE_URL`/`DB_*`, `AUTH_SECRET`, `API_PORT`, `LOG_LEVEL`, `CORS_ORIGINS`, the POS `OPENDATABOT_*` keys, and `POS_SECRETS_KEY`); the single-user MVP's `TIKTOK_USERNAME` / `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHANNEL_ID` / `NOVAPOSHTA_*` / `RESERVATION_TIMEOUT_MINUTES` are gone, along with the `src/tiktok.ts` and `src/telegram.ts` singletons that read them.

Routes in `src/api.ts` each `await` auth themselves via the local `requireAuth` helper (same pattern as the settings/sessions/POS controllers) and scope their queries by `userId`. Do not reintroduce a `preHandler` auth hook there: the previous one enforced nothing, because it was registered inside `fastify.register(...)` (so its scope covered no routes) and called `ensureAuth` without awaiting.

**Note:** `TechDocs/archive/` holds the design + onboarding docs for the earlier single-user/single-stream MVP (`ARCHITECTURE.md`, `PROJECT_SUMMARY.md`, `IMPLEMENTATION_GUIDE.md`, `START_HERE.md`, `FILE_MANIFEST.md`, `QUICKSTART.md`, `DEPLOYMENT.md`, `fix-instructions.md` — all moved out of the repo root 2026-09-06). They include an `inventory` table that does not exist and predate multi-tenancy, the POS subsystem and the Railway deploy. Treat them as historical notes — `TechDocs/archive/README.md` explains the drift, `TechDocs/NOTES.md` tracks known drift. Prefer reading `src/core/types.ts` and the service files directly. The only current root docs are `README.md`, this file, and `ИНСТРУКЦИЯ.md` (Russian operator guide).

### POS (root `src/pos/`, `pos/`)

Independent subsystem sharing the same Postgres via `pos_*`-prefixed tables (migrations `002`–`035`). Backend is a Fastify plugin (`src/pos/pos.plugin.ts`) mounted at `/api/pos`, registered from `src/index.ts` alongside the LIVE routes; product photo uploads are served statically from `data/pos-uploads` under `/pos-uploads/*` (needs a persistent volume in prod — see `TechDocs/RAILWAY_POS.md`). Route surface (`src/pos/pos.controller.ts`) covers: owner/staff PIN auth, products/variants/tags, customers, stock (adjustments, low-stock, suppliers, stock documents with post/reverse), GTIN barcode lookup/enrichment/learning jobs (plus an owner repair surface over the shared `pos_gtin_cache` — `GET /gtin/cache`, `PATCH /gtin/:code` to correct an entry as `manual`, `DELETE /gtin/:code` to tombstone it, and a supplier price-list import on `/admin/gtin` that feeds `learn/batch` under the `supplier` source; see `TechDocs/POS_GTIN_ENRICHMENT.md`), sales (complete/void/refund, idempotent via `client_uuid`), analytics, and QR payment (`payment method 'qr'`; per-store settings on `pos_stores`; `POST /qr/invoice` proxies Opendatabot for the dynamic-mode QR, `POST /qr/webhook` is the HMAC-verified payment-confirmation callback + a daily `reconcileQrPayments` cron — needs `OPENDATABOT_QR_KEY` / `OPENDATABOT_QR_NAME`). Every `/api/pos` request/response carries an advisory `X-POS-API-Version` header (single integer per side: `src/pos/version.ts`, `pos/src/platform/version.ts`); a mismatch is logged, not rejected, unless `POS_API_STRICT_VERSION=1` — see `TechDocs/POS_API_VERSIONING.md`. `pos_stores.enabled_modules` / `pos_stores.module_remotes` drive the per-store feature-module set and per-module remote-bundle sources, and `pos_stores.nav_overrides` (migration `033`) the **appearance** of the menus built from them — a sparse `{ '<moduleId>:<location>:<path>': { label?, icon?, order? } }` map the owner edits on `/admin/appearance` («Вигляд меню», owned by the core `settings` module), sanitised by `src/pos/core/nav.ts`, travelling with the login (so a cold-offline till keeps its menu) and applied in `selectNavItems` — after the shell/role/`visible()` filters, so it can restyle and reorder an entry but never add or remove one, and online-only modules get it for free; see `TechDocs/POS_NAV_CUSTOMIZATION.md`. A `module_remotes` value is a bare URL string (override a bundled module's code — web **and** the desktop cashier, which skips web-only modules) or a `ModuleRemoteEntry` object `{ url, title, routePath, nav, icon? }` declaring a new **online-only** module the desktop cashier downloads (roadmap #13). A host imports a remote only if its `PLATFORM_VERSION` (`pos/src/platform/version.ts`, the `@pos/platform` surface version, pinned by `src/platform/surface.test.ts` + `npm run platform:snapshot`) is ≥ the manifest's `minHostPlatform` — see `TechDocs/POS_MODULE_PLATFORM_VERSION.md`; bump it by hand when the barrel's exports change (11 since 2026-09-17). A module that keeps **its own offline data** declares `offline: { pendingCount, sync }` on its descriptor; the shell entries register those hooks via `registerOfflineModules` from `@pos/platform` and the offline runtime drives them after its own outbox — first such module is `stocktake` (`pos/src/modules/stocktake/`, till-side inventory count → draft `inventory` document via the staff-level `POST /api/pos/stock/counts`, idempotent on `client_uuid`, migration `025`); see `TechDocs/POS_MODULE_OFFLINE_DATA.md`. `POST /api/pos/client-telemetry` is a dormant module/version-skew sink. A cross-store **super admin** lives at `/super` on the POS web (`pos/src/super/`, routes `src/pos/routes/super.routes.ts`): password from env `POS_SUPER_PASSWORD` (≥ 12 chars, unset = page disabled), stateless 12 h token in the `X-POS-Super-Token` header, edits any store's `vertical` / `enabled_modules` / `module_remotes` through the same validation as the owner's `PATCH /store`, and re-points a module release URL across stores — see `TechDocs/POS_SUPER_ADMIN.md`. The module-remote architecture (feature modules under `pos/src/modules/*`, buildable as standalone runtime chunks that carry their own Tailwind CSS — shared `.sq-*`/token layer in `pos/src/styles/tokens.css` — Ed25519-signed via `pos/scripts/sign-remote.mjs` and verified before `import()`; on the Tauri cashier downloaded + verified in Rust and served from an on-disk cache via the `liveshopmodule://` URI scheme) is documented in `TechDocs/POS_MODULE_REMOTE_POC.md` / `POS_MODULE_REMOTE_ROADMAP.md` / `POS_MODULE_REMOTE_SIGNING.md`; what a runtime-loaded module can reach inside the Tauri cashier (app commands are **not** ACL-gated, so the window's `capabilities/default.json` is a minimal one-permission set guarded by `npm run check:tauri-capabilities`) is `TechDocs/POS_MODULE_TAURI_CAPABILITIES.md`. The first real online-only module is **`tiktok-live`** ("Прямий ефір" — the TikTok LIVE comment feed + session start/stop inside the POS shell): source in `pos/src/modules/tiktok-live/`, built by `pos/vite.tiktok-live-remote.config.ts`, and reaching a store only through an object entry in `pos_stores.module_remotes` — the shell ships none of its code. It authenticates through the one deliberate POS→LIVE bridge, `POST /api/pos/live/session-token` (`src/pos/routes/live.routes.ts`), which swaps an authenticated POS session for a LIVE token minted from `pos_stores.live_tiktok_username` (migration `017`, owner-writable via `PATCH /store`); see `TechDocs/POS_LIVE_SELLING_MODULE.md`.

**Sales verticals** (`TechDocs/POS_VERTICALS.md` — design doc *and* resume point, with a phase table). What a store sells is `pos_stores.vertical` (migration `034`), written **only** by the super admin: it decides the product attribute schema, the units the store may sell in, and which module renders the catalog half of the sell screen. The set of verticals lives in code (`src/pos/verticals/{types,index,attributes,clothing,flowers}.ts`, a `BUILT_IN` registry + `registerVertical`/`resetVerticals` test seam, exactly like `fiscal/providers`), not in a CHECK constraint — a new vertical must not need a migration — and a column value this build does not know degrades to clothing at read time (`verticalOrDefault`) rather than failing every login of that store. The owner sees it read-only in Settings; their `PATCH /store` answers 400 for `vertical`, and the column is absent from `STORE_PATCH_COLUMNS`.

Product model (migration `035`): `pos_variants` carries `attributes jsonb` + a **derived, stored** `label` + `unit`, replacing `size`/`color` (`036`, a *later* deploy, drops the old columns — see below). Every variant write goes through `normalizeVariant` (`src/pos/verticals/attributes.ts`): unknown attribute or a unit outside the vertical's set → 400, an update replaces the bag wholesale (so "clear this attribute" is expressible), and `label` is always recomputed — a client never sends one. That is what retired the four client-side label composers that had drifted into three separators; the cart, the offline receipt, price tags and stocktake all read the one caption the server built. Search is `label` + the attributes a vertical marks `inSearch` (`jsonb_each_text`), mirrored offline by `filterCatalog(..., searchKeys)`. `quantity` stays INTEGER counted in `unit` (250 g is quantity 250): `quantityMilli` in the ПРРО document, the `i64` in the Rust receipt printer and Checkbox's derived-discount arithmetic all assume whole units. `pos_sale_items.unit` snapshots it next to `variant_label`. Changing a store's vertical relabels its variants in the same transaction (`relabelStoreVariants`) without touching the attribute bags, so moving a florist to clothing and back restores every caption verbatim.

**Composite products** (migration `037`, `src/pos/composites.service.ts`) — a bouquet now, a tech card in the café phase. `pos_products.kind` is `'simple'` | `'composite'`; `pos_products.stock_mode` says where a composite's quantity lives: `'own'` (assembled in advance, counted on its own `pos_stock` row — selling it must **not** touch the components, the production document already took them) or `'derived'` (assembled when it sells: no stock of its own, availability is `MIN(floor(component_stock / component_qty))` over `pos_product_components`, an empty composition being 0 and never unlimited). Both modes from the start, because a florist runs both off one catalogue card. The composition hangs off the **variant**, not the product (S/M/L bouquets differ precisely in stem count), and a component may not itself be composite — that is what makes cycles impossible without a recursive check. The rule everything rests on: what a sale actually consumed is snapshotted per line into `pos_sale_item_components` (per **one** unit, so a partial refund is exact arithmetic), and a void/refund reverses **that snapshot**, never the current recipe — the recipe is editable, and an ad-hoc till-assembled bouquet has no recipe at all. The snapshot's presence is also the signal, so a reversal never reads `stock_mode` and cannot drift from the write-off. `sales.service.ts` moves stock only through `consumeStockForSaleItem` / `returnStockForSaleItem`; `assertStockable` refuses a derived composite at manual adjustment and at stock-document posting, and `listOnHand`/`listLowStock` leave it out (its own row sits at 0 forever). Writes refuse a derived composite with no composition, with opening stock, a switch to `derived` while stock is still on the shelf, and a switch to `simple` while a composition still exists — all four would lose data silently. A fifth stock-document type, `production` (prefix `ВР`, migration `038` only widens the CHECK), is the other half of `'own'`: its lines name only the composite produced, the component write-off is derived at post time by `produceComposite`, the assembled cost is summed from the components (so `addLine` refuses a typed-in one), a line for a derived or simple variant is refused at **add** time, and the reversal replays the inverse of the movements that document recorded — same reason as a refund, and it fails outright if some of the assembled units have already been sold. On the client, the product card owns the composition (`pos/src/modules/products/components/CompositionEditor.tsx` + `componentOptions.ts`, which offers every active variant of a non-composite product and so enforces the same one-level rule as the server) and edits it wholesale — in the create form **and** in the edit form, where changing an existing product's shape orders its writes around the server's two ordering rules (a simple product may not carry a composition, a composite may not become simple while one exists), so simple → `derived` goes through `own` rather than being one impossible write — and `/admin/stock/production` (`stock` module) is its own screen rather than another `type` on `StockActionPage` — production picks only from what the store assembles in advance and needs the bill of materials and a "will it stretch" read-out on screen. A cart line may also carry **its own** composition (`CompleteSaleItemInput.components`) — a bouquet the cashier assembled at the counter, rung on a catalogue card whose stored recipe is only a default. It runs the same mechanism (`validateComponents` is shared with the catalogue editor; the snapshot and the reversal are unchanged), with three rules that are easy to get backwards: a line carrying a composition is **never merged** with another of the same variant (two custom bouquets are two bouquets, and merging throws one recipe away); the price is **computed** server-side as the sum of the components' prices, never sent, because a freely settable line price is a hole no receipt would show (real markdowns stay in the line/cart discounts); and only a **derived** composite accepts one. `GET /sales/:id` now returns `items[].components`, which for a till-assembled bouquet is the only place its recipe exists. Both additions are additive on the wire, so `POS_API_VERSION` stays at 2. The till screen for assembling one is the **florist's bench**, `TechDocs/POS_FLORIST_BENCH.md` — the design doc *and* resume point for it and for the phases that grow out of it, with a phase table B0–B7. Phases B1 (groundwork) and B2 (the bench itself) are in. B1 closed the blocker that `CatalogItem` carried no `kind`/`stock_mode`/`components` and the only endpoint that did was owner-only, so a till could not tell a bouquet card from a rose: `GET /catalog` (already `ensurePosAuth`) now carries all three, which puts the recipe into the offline snapshot for free, and `pos_stores.florist_labour_bps` (migration `040`) is what the shop charges for assembling one — a percentage **on top** of the components' retail sum, not a multiplier of it, because stem prices already carry the shop's margin. B2 is `pos/src/modules/vertical-flowers/bench/`: a full-screen surface (`fixed inset-0`, as `VariantPicker` does — the catalog slot is ~600 px at `lg`, so two panels do not fit) opened by a «Зібрати букет» button or by tapping a `derived` composite card; an `own` one is rung as an ordinary product, because its stems left with the production document. Two rules there are easy to get backwards: the **budget is a hint and never enters the price** (a bouquet that must land on exactly 1500 is a discount, which the cart already expresses — a freely settable line price is a hole no receipt shows), and a tile tap both adds a stem **and selects it** so the always-visible number pad types the count into it — one tap per stem cannot reach the speed budget, since nine roses would be nine taps. The till prices with the very same functions the server does (`withLabour` / `priceOfComponents`, exported from `@pos/platform` rather than copied, and pinned to one table of cases across `pos/src/lib/bouquet.test.ts` and `src/__tests__/pos.bouquet-pricing.test.ts`); the client still never sends a price. A bouquet can also be assembled **for the window** instead of for the customer standing there (`POS_FLORIST_BENCH.md` §11): `POST /api/pos/bench/showcase` (staff level, `stock` module, idempotent on `client_uuid`) makes a one-off catalogue card, its composition, a posted `production` document that takes the stems off the shelf, and an internal EAN-13 for the price tag, all in one transaction. One card per bouquet, because stock is a counter and not a set of distinct objects — a 900 ₴ and a 2400 ₴ bouquet cannot share a row and a price; `pos_products.one_off` (migration `041`) is what separates such a card from a catalogue bouquet like the demo's «Ніжність», which is also composite+own but is assembled in batches from a stored recipe. No composition-snapshot table was needed: `reverseDocument` already replays the movements a production document recorded rather than re-reading the recipe, and a one-off card simply is its own recipe. The price may be rounded on the bench's «На вітрину» sheet — that is a **catalogue** price on a real card, not the freely settable *line* price §3.5 refuses — and is sent only when it differs, so the server stays the single authority. Online only: making the card means the server issuing ids, so the button says «Потрібна мережа» rather than timing out. A bouquet that did not sell is written off from the till through `POST /api/pos/bench/writeoff` on the module's own «Вітрина» screen (`pos/src/modules/vertical-flowers/pages/ShowcasePage.tsx`, the `/flowers` route): what is written off is the **bouquet**, never its stems — production took those when it was assembled, and crediting them back would invent flowers that are in the bin. Deliberately narrower than the owner's write-off screen: the server refuses anything that is not `one_off`, so a mis-tap at the till cannot empty a stem line, and a wilted rose stays the owner's to write off on `/admin/stock/writeoff`. The reason is `damaged` (wilted) or `gift` (given away) and nothing else — `lost` is a stock-taking word, not a counter one. A bouquet is also photographed at the counter (`POST /api/pos/bench/photo`, staff level, reusing `saveProductImage` verbatim — `/uploads` is owner-only and takes a picture for any product, which is a different thing): the tag ties the flowers to the card, the photo is what picks the right one out of a window holding two similar bouquets when the tag has come unstuck. Two capture paths, because one is not enough — `<input capture="environment">` opens the native camera on a tablet, but Tauri's webview ignores that attribute and opens a file picker, so the desktop till uses `getUserMedia` + a canvas grab. The frame is downscaled to 1280 px/q0.8 client-side **before** upload, without which an ordinary tablet photo (3–8 MB) exceeds the 5 MB limit and the feature fails in exactly its own use case. Attaching one afterwards goes through `POST /api/pos/bench/showcase/photo`, `one_off` only and accepting only a `/pos-uploads/<file>` path this backend issued. The bench's third ending is `POST /api/pos/bench/recipe`: keep the composition as a `derived` catalogue template — nothing physical happens, no production document and no stock, and the bouquet stays on the bench, because saving a recipe is not finishing with it. Staff level but `needs_review`, so it lands under the owner's «Потребують перевірки» filter (the same flag the receipt-placeholder path has used since `019`); the name is required and a duplicate is refused, which is also what makes a double tap harmless since there is no document to key a `client_uuid` on. An offline-stamped receipt also gets its tax-office QR at stamp time (`src/pos/fiscal/taxUrl.ts` — `id`/`date`/`time`/`fn`/`sm`, the format Положення № 13 prescribes; ФН ПРРО is cached in `pos_fiscal_settings.register_fiscal_number`, migration `029`); the контрольне число and the provider's `mac` arrive with the replay, because both come from the ПРРО's offline session, which is Checkbox's, not ours (primary sources snapshotted in `TechDocs/dps-prro-api/`). Decision 2026-09-12: case C goes the **cloud path** (Checkbox's own `ask-offline-codes` → `sell-offline` → `go-online` model for external systems); the local Checkbox Kasa component is parked. Phase 8в is in: the store's legal requisites, ФН ПРРО and tax letters come from the provider (`FiscalProvider.fetchRequisites`, `src/pos/fiscal/requisites.ts`, cached as `pos_fiscal_settings.requisites` with a 24 h TTL — migration `030` — refreshed at shift open / pool refill / the owner's connection test, never at checkout), travel to the till in `auth.store.fiscal` together with `default_tax_code`, and the `'local'` layout (`pos/src-tauri/src/hardware/receipt.rs` + `pos/src/components/ReceiptPrintable.tsx`, built by `pos/src/lib/receipt.ts`) now prints the Положення № 13 п. 2 rows — header 1–5, rate letters, «СУМА/ПДВ/ДО СПЛАТИ/РЕШТА», «ГОТІВКА/БЕЗГОТІВКОВА», «ФІСКАЛЬНИЙ ЧЕК» + producer, the «ОНЛАЙН/ОФЛАЙН» mark, «ЧЕК №», «ФН ПРРО». An offline stamp needs the cached requisites (the first receipt of a register is online-only), and the admin's `FiscalSettingsCard` shows them read-only. Still per-store, not per-line: the rate letter follows `default_tax_code`. Phase 3 (case C — the till has no network, the shop keeps selling) is in: the register holder leases tax-office codes from the pool (`POST /api/pos/fiscal/offline/lease`, `src/pos/fiscal/offline/lease.ts`, 50 at a time, refreshed at the end of every sync), the desktop till stamps and prints the receipt itself (`pos/src/offline/lease.ts` holds the reserve and the gates; `pos/src/lib/taxUrl.ts` builds the QR without us) and `POST /api/pos/sales/complete` files it afterwards through a `fiscal_offline` stamp — same session, ledger and replay as a server-stamped one, except that a refusal never voids the sale (the goods left during the outage) and only a retryable answer comes back as 503. A handover can optionally close the shift on the way out (`close_shift` on `/fiscal/register/handover/confirm`, off by default, the Z-report sent before the lock moves and a failure leaving the register where it was). The tax office's **monthly** offline allowance (168 h per register, Положення № 13) is counted server-side in `src/pos/fiscal/offline/limits.ts` over the register's sessions clipped to the Kyiv calendar month, refuses a new session and further sales inside a live one (`offline_month_limit`) without parking that session, and travels to the till in the lease answer because the till cannot know it (another till of the same register spends the same hours). Three things are easy to get wrong here: the replay transmits in **fiscal-date** order, not `offline_seq` order (a till's receipts arrive interleaved with sales it rings online while its queue drains); the `go-offline` floor (`offlineChainFloor`) includes a Z-report and the previous session's `go-online`, so a shift that auto-closed during an outage parks the session instead of corrupting the register; and the replay of a session carrying a till's documents waits for that till to report an empty outbox (`ready_at`, migration `031`, with a one-hour grace). A demo-register run on 2026-09-12 (fixtures `src/__tests__/fixtures/checkbox/offline_*.json`) confirmed the two things the design rests on — Checkbox accepts a `go-offline` dated in the past and a `fiscal_date` in the past, returning `control_number` and a `tax_url` with `mac` — and caught two bugs, both fixed: `previous_receipt_id` must **never** be sent (Checkbox refuses the only value we can compute, `receipt.previous_id_last_id_differs`, which would have cost every receipt of an outage after the first), and a receipt may not be dated before its shift opened (`date.fiscal_date_logic`), so `offlineChainFloor` now includes the open shift's `opened_at`. A second run the same day, after both fixes, carried a chain of three receipts through in full (each with its own control number and a `tax_url`); every run now keeps its answers, console output and a `run.json` under `src/__tests__/fixtures/checkbox/runs/<timestamp>/` instead of overwriting the last one. Still open: hardening (phase 5) — offline refunds and service receipts, a second till per register, a duplicate offline code, `go-online` with undelivered documents, and the e2e/desktop run. Receipt printing (phase 8a) follows `pos_fiscal_settings.receipt_source`: `'local'` prints our ESC/POS layout plus a fiscal block (number, date, tax-office QR via the printer's native `GS ( k`); `'provider'` prints the provider's own text, fetched once at fiscalisation time at the store's `receipt_width` (32 = 58mm, 48 = 80mm, migration `026`) and stored as `pos_fiscal_receipts.receipt_text`. The till decides by presence of `receipt_text` only — a failed text fetch (`attachProviderReceiptText` in `fiscal.service.ts`, own 2.5s sub-budget, never fails the document) silently falls back to the local layout.

Frontend (`pos/src/`) has **three entry points sharing the same components/pages/Zustand store**:
| | Web | Desktop (Tauri) | Tablet (PWA) |
|---|---|---|---|
| HTML/entry | `index.html` / `main.tsx` | `cashier.html` / `cashier-main.tsx` | `tablet.html` / `tablet-main.tsx` |
| Router | `BrowserRouter` | `HashRouter` | `BrowserRouter basename="/tablet"` |
| Routes | full SPA incl. `/admin` | only `/login`, `/register`, `/customers` | the till screens, no `/admin`, no `hardware` |
| Shell context | `PosShellContext = 'web'` | `'cashier'` | `'tablet'` |
| Offline mode (`offline/enabled.ts`) | `off` | `full` | `reads` |

`pos/src/shell.tsx` is the context that branches shell-specific behavior; `modules/shells.ts` `runsInShell` decides which modules a shell mounts (a remote bundle published with `shells: ['web','cashier']` before the tablet existed still runs there). The desktop cashier is the only surface that **writes** offline (`pos/src/offline/`, IndexedDB via Dexie): it snapshots catalog/tags/customers on first online login, verifies PIN/password locally via a PBKDF2 verifier (never stores the raw PIN), queues sales/customer writes while offline, and syncs (customers first, then sales) once a JWT and network are available. The **tablet PWA** (`TechDocs/POS_PWA.md`, the waiter's `/tablet/` on the same Railway static service as the web) **reads** offline and writes online: `enableOfflineReads()` gives it local login, the catalog snapshot and the `tables` mirror, while `isOfflinePosEnabled()` stays false so it never sends `X-POS-Device-ID` (the server would treat it as a till that can hold the ПРРО register), never queues, and a write without a network throws `OfflineWriteError` on the spot. A hand-written service worker (`pos/sw/tablet-sw.js`, precache list from `scripts/precache.mjs`, scope `/tablet/`) keeps the host build and the remote bundles; a newer build is offered on a banner and otherwise applied on the next launch, never mid-bill; `pos/serve.json` (no `serve -s` — it would shadow the `/tablet/**` rewrite) carries the rewrites and cache headers. Two chunk-boundary traps that shipped and are closed: the mode setters must be called through `@pos/platform` (the desktop entry's relative import of `offline/enabled.ts` set a second copy of the flag, so the release till never started its offline runtime — `enabled.ts` is now in the boundary check's `STATE_OWNERS`), and `lib/checkoutError.ts` matches the offline errors by `.name`, not `instanceof`. Web admin always talks to the API directly — no offline path there. `VITE_API_BASE` is baked in at build time (`pos/src/lib/urls.ts`); the desktop build defaults to the production API (`https://the-live.shop`) unless overridden via `pos/.env`. See `TechDocs/POS_DESKTOP.md` for the full offline/sync/CORS/kiosk story and `TechDocs/RAILWAY_POS.md` for deployment.

Design tokens/UI conventions for the POS UI — including price-tag printing to a receipt roll — are documented in `pos/UI_CASHIER.md`; discount/customer rules in `TechDocs/POS_DISCOUNTS_AND_CUSTOMERS.md`; GTIN enrichment pipeline — including the canonical GTIN-14 cache key and the sticky-`manual` merge rule — in `TechDocs/POS_GTIN_ENRICHMENT.md` / `POS_GTIN_SETUP.md` / `POS_GTIN_LEARNING_API.md`.

### Marketing site (`site/`)

A multi-page Vite app with no router — one HTML template + one `src/*-main.tsx` entry per page (`index`/`live`/`pos`/`compare`, plus `dovidka.html` shared by `/dovidka`, every `/dovidka/<slug>` and `404.html`). It is **statically prerendered at build time, never SSR'd at runtime**: `npm run build` runs the client build, then `vite build --ssr src/entry-server.tsx`, then `scripts/prerender.mjs`, which renders every entry of the route registry `src/routes.tsx` with `renderToString`, injects the markup into the built template's `<div id="root">` and the SEO head (`src/lib/seo.ts`: title/meta/OG + JSON-LD) at the `<!--app-head-->` placeholder, and writes `dist/<out>`; the entries hydrate via `src/mount.tsx`. The reason: AI/answer-engine crawlers (GPTBot, ClaudeBot, PerplexityBot — all allowed in `public/robots.txt`) do not execute JS, so before this the pages were empty to them. The prerender also emits `dist/sitemap.xml` and `dist/llms.txt` (served by Fastify from `site/dist`, not `public/`) and fails the build if a page lacks `<h1>`/JSON-LD, carries an inline `opacity:0`, or references a missing `/assets/*` file. Fastify maps the pretty URLs to the files (`src/api.ts`: `/`, `/live`, `/pos`, `/pos/:slug`, `/yaku-kasu-obraty`, `/dovidka`, `/dovidka/:slug`, `/about` — the last one prerendered from `AboutPage.tsx` with an `AboutPage` schema since 2026-09-23; the hand-written `public/about.html` and legacy `styles.css` are gone) and its `setNotFoundHandler` returns `dist/404.html` for site paths while `/api/*` keeps the JSON 404 (`src/__tests__/site-routes.test.ts`).

Rules that follow from this design: **everything the site claims about the product comes from `src/lib/productFacts.ts`** (names, prices, per-feature `'available' | 'coming'` status) — page copy, FAQ answers, `SoftwareApplication.featureList`/`offers` and `llms.txt` all read it, so a feature flips in one line; JSON-LD is built by `src/lib/jsonLd/*` and attached to routes in `routes.tsx`, never rendered from a component (it would land in the body and duplicate); `Reveal`/`FloatingCard` are CSS-only (`html.js` is set by an inline script in each template) so prerendered content is visible without JS — do not reintroduce a JS animation library that writes `opacity:0` inline; browser-only APIs stay inside `useEffect`. Knowledge-base articles («Довідка») are TSX in `src/content/dovidka/<slug>.tsx` (`meta` + `Body`, FAQ shared with the FAQPage schema), listed in `content/dovidka/index.ts` — adding one there puts it in the prerender, sitemap and llms.txt automatically. The four human guides (власник, касир, ресторан і кафе, квітковий) are **not** copied into TSX: `TechDocs/guides/*.md` stays the one text, `site/scripts/guides-plugin.mjs` turns it into the `virtual:guides` module at build time (`marked`, dev-only) and `content/dovidka/guides.ts` adds only the SEO title/lead, dates and order — so a guide lives at `/dovidka/<file name>`, its first `#` line is dropped for the page's own `<h1>`, the «Посібники: …» line is replaced by the page's switcher, `## Часті питання` (`**Q**` + answer) becomes the FAQ and FAQPage schema, relative `other.md` links become `/dovidka/other` (an unknown one fails the build), and editing one means bumping its `updatedAt` there. The Dockerfile's site stage copies `TechDocs/guides/` for this, and the site CI also runs on `TechDocs/guides/**`. A vertical landing links its guide through `VerticalContent.guide` (`{ slug, label }`, checked in `routes.tsx`), never by importing it. GA4 events go through `src/lib/analytics.ts` (`lead_submit`, `download_click`). Since 2026-09-23 the site sells one POS for four businesses: `/pos` is the shared page and `/pos/odyah`, `/pos/kvity`, `/pos/kafe`, `/pos/restoran` are per-vertical landings rendered from one template (`vertical.html` + `src/vertical-main.tsx`, picked by pathname like Довідка) with their copy in `src/content/verticals/<slug>.ts` and their facts (slug, title, tint, feature ids) in `VERTICALS` inside `productFacts.ts`; Fastify serves them from `dist/pos/<slug>/index.html` via `GET /pos/:slug`. Pricing lives in `PRICING.pos` (launch free → per-store monthly plans + the tables add-on; the own-ПРРО plan is `coming` and a PreOrder offer in JSON-LD because no such provider exists in code) and the only competitor figures on the site are in `COMPETITOR_FACTS` with their source URL and the date they were read — `PricingSection.tsx` builds the comparison sentence from them, never by hand. What the site promises next is `ROADMAP` there (per vertical, with an owner-named readiness percentage) rendered by `Roadmap.tsx` as «Скоро» cards and listed in `llms.txt`; `TechDocs/SITE_PROMISES.md` is the developer-facing list of those promises — a feature leaves it when its `FEATURES[id]` becomes `available`. Screenshots of the demo stores come from `pos/scripts/shoot-site-screens.mjs` (Playwright against `pos.the-live.shop`, run by hand, writes `site/src/assets/screenshots/`); the vertical cards' illustrations are the demo stores' SVGs under `public/demo-*/`, so the clothing landing needs migration `055`'s `public/demo-clothing/` deployed. `.claude/launch.json` has a `site-preview` entry for `vite preview` on :4173.

### CORS

`CORS_ORIGINS` (comma-separated, no trailing slash) env var on the API service allowlists POS/admin web origins. The Tauri desktop cashier's origins (`https://tauri.localhost`, `http://tauri.localhost`) are hardcoded in `src/api.ts`, not env-driven.

## Conventions

- Root backend is strict TypeScript (`strict`, `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns` all on) compiled with `tsc`; ESM throughout (`"type": "module"`, `.js` extensions in relative imports even though source is `.ts`).
- ESLint: all three apps share one ruleset — `@typescript-eslint/no-unused-vars` warns and allows `_`-prefixed names, `no-explicit-any` is off, `no-console` allows `warn`/`error` only (root CLI scripts `src/pos/{migrate,seed}.ts` + `gtin/seed-from-dump.ts` override it off; in the rest of the backend use `logger`, `src/logger.ts`, Winston). `admin/` and `pos/` add the `react-hooks` (error) / `react-refresh` (warn) plugins. `npm run lint` passes with zero warnings in all three and is enforced in CI.
- Admin SPA has a real test suite (Vitest + Testing Library + MSW for HTTP mocks, class-mocked WebSocket, Playwright for e2e) — when touching `admin/src/services` or `admin/src/hooks`, keep coverage above the gate. See `admin/TESTING.md` for what's considered P0.
- Root backend tests (`src/__tests__/`) are mostly POS-focused (crypto, money, GTIN normalization/orchestration, sales logic, stock race conditions, stock reports/documents, tags, the products/customers/suppliers/uploads/auth services, and the whole `/api/pos` route surface) plus the order parser. `vitest.config.ts` scopes the root suite to `src/__tests__` — without it vitest's default glob also picks up `admin/` and `pos/`.
- DB-backed tests run against the database in `.env` and share `src/__tests__/helpers/pos-fixtures.ts`: `applyPosMigrations()`, per-file store isolation (`createTestStore` / `dropTestStore`), and `buildPosTestApp()` for driving the real Fastify POS plugin through `app.inject()`. Migrations are applied once per run by `vitest.global-setup.ts`; the ordered list lives in `src/pos/migrations.ts` and is shared with `npm run pos:migrate` — add new migrations there and nowhere else.
